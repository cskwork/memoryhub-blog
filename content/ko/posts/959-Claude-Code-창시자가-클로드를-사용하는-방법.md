2026년 1월 초, Claude Code의 창시자인 Boris Cherny가 긴 스레드에서 자신의 일상적인 설정을 공유했습니다. 그는 이를 "vanilla"라고 부르지만,   
실제로는 작지만 반복 가능한 움직임들이 모여 큰 효과를 내는 체계적인 세트입니다.  
이 글은 그러한 움직임들을 복사하고, 적용하고,   
자신의 워크플로우에서 확장할 수 있는 실용적인 플레이북으로 정리했습니다.  
목표는 정확한 설정을 모방하는 것이 아니라,   
원칙을 빌려와 자신의 팀, 저장소,   
그리고 제약 조건에 적용했습니다.

## 대상 독자

- 이미 Claude Code를 사용하고 있으며 더 일관된 결과를 원하는 분
- 팀 워크플로우를 관리하거나 영향력을 행사하며 공유된 가드레일을 원하는 분
- 간단한 자동화(파일, 훅, 명령어)를 구성하는 데 익숙한 분

## 13가지 방법

### 1) 여러 Claude를 병렬로 실행하고 — 라벨을 붙여라

그는 5개의 터미널 세션을 동시에 실행하고 탭에 번호를 매겨 쉽게 추적합니다.   
또한 시스템 알림(예: iTerm2)을 활용해 다른 작업을 하는 동안에도 세션이 실행될 수 있도록 합니다.   
핵심은 처리량입니다: 하나의 세션이 끝나기를 기다리지 않고 독립적인 작업들에서 추진력을 유지할 수 있습니다.   
번호 매기기는 사소해 보이지만, 탭 사이를 오갈 때 진행 상황을 빠르게 스캔할 수 있게 해줍니다.  

**시도해보기:** 두 개의 세션으로 시작하고, 각각에 목적을 부여하고(예: "리팩토링"과 "테스트"), 커밋까지 분리 상태를 유지하세요.

### 2) 로컬과 웹 세션을 의도적으로 혼합하라

그는 로컬 세션과 함께 여러 브라우저 세션(종종 5-10개)을 유지하고, 작업을 서로 넘깁니다. claude.ai/code의 웹 UI를 사용하고, Chrome에서 세션을 시작하며, 나중을 위해 휴대폰에서 세션을 시작하기도 합니다. 아이디어는 작업에 가장 적합한 인터페이스를 사용하는 것입니다:   
도구와 git이 필요할 때는 터미널, 더 깔끔한 뷰가 필요하거나 모바일일 때는 웹.  

**시도해보기:** "검토 및 추론"용 웹 세션 하나와 "편집 수행"용 로컬 세션 하나를 유지하세요.

### 3) 모델을 선택하고, 코딩에는 그것만 고수하라

그는 거의 모든 것에 단일 모델(thinking이 있는 Opus 4.5)을 사용합니다. 요청당 더 느릴 수 있지만, 왔다 갔다 하는 횟수가 줄어들어 종종 전체적으로는 더 빠릅니다.   
메타 교훈: 일관성이 순수한 속도보다 중요합니다.  

**시도해보기:** 일주일 동안 하나의 모델에 전념하고,   
재프롬프팅을 얼마나 하는지 측정한 후에야 변경 여부를 결정하세요.

### 4) CLAUDE.md를 살아있는 팀 메모리로 취급하라

그는 git에 공유 CLAUDE.md를 유지하고 Claude가 뭔가 잘못할 때마다 업데이트합니다. "반복하지 말 것" 원장 플러스 로컬 스타일 가이드라고 생각하세요. 파일은 짧고, 집중되어 있으며, PR에서 업데이트되어 신선하게 유지됩니다. 그의 팀 파일은 겨우 수천 토큰 정도이며 명령어, 코드 스타일, UI/콘텐츠 가이드라인, 상태 관리, 로깅, 에러 처리, 디버깅, 심지어 PR 템플릿까지 다룹니다.  

다음은 최소한의 편집 가능한 패턴입니다:

```
# Bash 명령어
- pnpm test --filter <name>: 집중 테스트 실행
- pnpm lint: 푸시 전 린트 실행

# 코드 스타일
- 중첩된 if보다 조기 반환 선호
- named export 사용

# 워크플로우
- 사소하지 않은 변경에는 테스트를 먼저 작성
- 동작이 변경되면 문서 업데이트
```

### 5) Plan 모드로 시작하고, 그 다음 auto-accept 편집으로 전환하라

목표가 PR일 때, 그는 Plan 모드(Shift+Tab 두 번)에서 시작하고 코드 변경 전에 계획을 반복합니다. 계획이 확실해지면,   
auto-accept 편집으로 전환하여 빠르게 진행합니다.   
계획이 안전 레일이고; auto-accept가 가속기입니다.  

**시도해보기:** "계획 품질"을 실제 작업으로 취급하세요. 계획이 명확하게 느껴지지 않으면,   
코딩 대신 계획을 계속 다듬으세요.

### 6) 내부 루프 프롬프트를 슬래시 명령어로 전환하라

반복하는 모든 프롬프트는 슬래시 명령어가 됩니다. 이것은 당신의 마찰을 줄이고 Claude가 스스로 같은 워크플로우를 호출할 수 있게 해줍니다. 그는 그 명령어 파일들을 git에 보관해 팀이 공유하고, 인라인 bash를 사용해 컨텍스트를 미리 계산합니다(모델이 요청할 필요가 없도록).  

간단한 예시:

```
---
description: 깔끔한 커밋을 준비하고 PR을 푸시
allowed-tools: Bash(git status:*), Bash(git diff:*), Bash(git commit:*), Bash(git push:*)
---

# 컨텍스트
- 상태: !`git status -sb`
- Diff: !`git diff --stat`

# 작업
커밋 메시지를 작성하고, 커밋하고, 현재 브랜치를 푸시하세요.
```

### 7) 반복되는 역할을 서브에이전트로 승격하라

그는 코드 단순화나 end-to-end 검증 같은 반복 작업에 서브에이전트를 사용합니다. 이것은 메인 스레드를 집중시키고 각 서브에이전트에 명확한 권한을 부여합니다.  

최소 서브에이전트 템플릿:

```
---
name: verify-app
description: 앱을 실행하고, 주요 흐름을 확인하고, 문제를 보고합니다.
tools: Bash, Read
model: inherit
---

프로젝트의 표준 명령어를 사용하여 앱 변경 사항을 검증하세요.
정확한 에러 출력과 재현 단계와 함께 실패를 보고하세요.
```

### 8) 훅을 사용해 마지막 10%를 결정론적으로 만들어라

그는 PostToolUse 훅을 사용해 코드를 포맷하여, 포맷팅이 늦은 서프라이즈가 되지 않도록 합니다. 훅은 "대부분의 경우 이것을 하라"를 "매번 이것을 하라"로 바꾸며, 이것이 CI 노이즈를 피하는 방법입니다.  

예시 훅 설정 (간소화):

```
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npm run format" }
        ]
      }
    ]
  }
}
```

### 9) 안전한 도구를 미리 허용하라, YOLO를 기본으로 하지 마라

그는 기본적으로 권한 건너뛰기를 피합니다. 대신, /permissions와 공유 설정(종종 .claude/settings.json에)을 통해 저장소에 대해 신뢰하는 작은 도구 세트를 미리 허용합니다. 그것이 전면적인 건너뛰기보다 더 안전하고, 끊임없는 프롬프트보다 더 빠릅니다.  

**시도해보기:** "안전한 허용 목록"을 만들고 매월 검토하세요. 위험한 명령어는 기본적으로 제외하세요.

### 10) MCP를 통해 Claude를 실제 시스템에 연결하라

그는 MCP를 사용해 Claude를 Slack, BigQuery, Sentry 같은 도구에 연결하고, .mcp.json에 설정을 공유합니다.   
Claude를 코드 에디터에서 워크플로우 허브로 바꿉니다.  

**시도해보기:** 일일 불편함을 제거하는 하나의 시스템(로그, 분석, 티켓)으로 시작한 다음 확장하세요.

### 11) 장시간 실행 작업에는 백그라운드 검증 단계를 추가하라

시간이 오래 걸리는 작업의 경우, 그는 작업이 완료되면 Claude가 작업을 검증하도록 설정합니다. 이를 위해 백그라운드 에이전트, Stop 훅, 또는 ralph-wiggum 같은 플러그인을 사용합니다. 또한 샌드박스에서 완화된 권한 모드로 실행하여 세션이 프롬프트에서 차단되지 않도록 합니다. 특히 자리를 비울 때 "실행하고 기다리기"를 더 안전하게 만듭니다.  

**시도해보기:** 스모크 테스트를 실행하고 트랜스크립트에 짧은 요약을 게시하는 Stop 훅을 추가하세요.

### 12) Claude에게 검증 루프를 제공하라 (이것이 승수다)

그의 가장 중요한 팁: Claude가 자신의 작업을 검증할 수 있는 방법을 제공하세요. 테스트, CLI 명령어, 브라우저 동작 등 출력을 확인할 수 있을 때 품질이 극적으로 향상됩니다. 그는 심지어 Claude Chrome 확장 프로그램을 사용해 실제 브라우저에서 UI 변경 사항을 테스트하게 합니다.  

**간단한 검증 사다리:**

1. 단일 명령어 (예: pnpm test --filter ...)
2. 작은 테스트 스위트
3. 브라우저에서의 UI 확인 (수동 또는 자동)
4. 다른 서브에이전트에 의한 "리뷰 패스"

### 13) 팀 스킬과 관례를 의도적으로 공유하라

그는 적절한 곳에서 공유 스킬과 설정을 사용하면서도 개인적인 조정을 허용합니다. 핵심은 선을 긋는 것입니다: 팀에 중요한 것(공유) vs 개인적 선호(로컬). Claude Code는 정확히 이 분리를 위해 여러 스킬 디렉토리를 지원합니다.  

**시도해보기:** 프로젝트 스킬은 git에, 개인 스킬은 홈 디렉토리에 보관하고, Claude가 올바른 것을 선택할 수 있도록 명확하게 이름을 지으세요.

## 오늘 바로 복사할 수 있는 스타터 킷

빠른 시작을 원한다면,   
이 네 가지 아티팩트가 80%의 가치를 제공합니다:

1. 명령어, 스타일, 워크플로우 규칙이 있는 짧은 CLAUDE.md
2. 가장 일반적인 루프를 위한 슬래시 명령어 하나
3. 검증 또는 리뷰를 위한 서브에이전트 하나
4. 일관된 CI 노이즈 소스를 제거하는 훅 하나

## 피해야 할 일반적인 함정

- **너무 이른 과잉 자동화:** 열 개가 아닌 하나의 명령어나 훅으로 시작하세요.
- **검증 건너뛰기:** 검증할 수 없다면, 도박하는 것입니다.
- **지저분한 병렬화:** 세션에 라벨을 붙이고 작업을 독립적으로 유지하세요.
- **부풀어 오른 메모리 파일:** CLAUDE.md를 짧게 유지하고 자주 검토하세요.
