"프롬프트를 아무리 잘 써도 AI가 내 의도를 못 알아챈다." 명확한 지시를 줬는데 엉뚱한 답이 나오고, 맥락을 설명해도 핵심을 놓친다. 문제는 AI가 '무엇'을 해야 하는지는 알아도, 사용자가 '무엇을 알고 있는지', '왜 이걸 원하는지'를 파악하지 못하기 때문이다.

**결론부터 말하면, AI에게 "내가 누구이고, 무엇을 알고, 무엇을 원하는지"를 명시하면 답변 품질이 29% 이상 향상된다.**

## 배경

Theory of Mind(마음 이론, ToM)는 원래 심리학 용어다. 타인의 믿음, 욕구, 의도 같은 정신 상태를 추론하는 인간의 인지 능력을 말한다. 6살 아이도 "철수는 사탕이 서랍에 있다고 믿지만, 실제로는 엄마가 옮겼다"는 상황을 이해할 수 있다.

> **마음 이론(Theory of Mind)**: 자신과 타인의 정신 상태(믿음, 의도, 지식)를 추론하고 이해하는 능력

LLM 프롬프팅에서 ToM의 의미는 조금 다르다.

**여기서 LLM이 사용자(나)의 맥락, 지식 수준, 의도를 제대로 파악하게 만드는 것이 핵심이다.**

2024년 ACL 학회에서 Carnegie Mellon 연구팀이 발표한 SimToM은 이 원리를 프롬프팅에 적용했다. 결과는 놀라웠다. 기존 Chain-of-Thought 대비 **+29.5%** 정확도 향상. GPT-4는 적절한 ToM 프롬프팅으로 일부 테스트에서 100% 정확도를 달성했다.

핵심 원리는 단순하다. LLM에게 **"이 사람이 무엇을 알고, 무엇을 모르는지"를 먼저 정리하게 하면** 답변이 정확해진다.

## 핵심 기법: SimToM 2단계 프롬프팅

SimToM의 구조는 인간이 타인을 이해하는 방식을 모방한다. "저 사람 입장이 되어보면..."이라고 생각하는 것, 그것이 관점 전환이다.

**1단계 - 관점 전환**: 특정 주체가 알고 있는 정보만 필터링한다.

**2단계 - 질문 응답**: 필터링된 정보만으로 답한다.

LLM은 전체 정보를 한꺼번에 처리하면 혼란스러워한다. 하지만 "이 사람이 아는 것만 추려서"라고 단계를 나누면 정확도가 급상승한다.

## 실습: 3가지 핵심 예제

### 예제 1: 기본 SimToM 구조

ToM의 원리를 가장 잘 보여주는 고전적인 False Belief 테스트다.

**상황**

```
Noor는 바리스타다. 고객이 오트밀크를 요청했다.
Noor는 피처에 오트밀크를 채웠다.
동료가 Noor 몰래 아몬드밀크로 바꿨다.
Noor는 동료가 바꾸는 것을 봤다.

질문: Noor는 피처에 무엇이 들어있다고 믿는가?
```

**일반 프롬프팅**

```
위 상황을 읽고 질문에 답하세요.
```

→ 많은 LLM이 "오트밀크"라고 오답. "Noor가 봤다"는 정보를 놓침.

**SimToM 프롬프팅**

```
[1단계] 
Noor의 관점에서, Noor가 직접 경험하거나 목격한 사건만 나열하세요.

[2단계] 
위에서 정리한 Noor의 지식만을 바탕으로,
Noor는 피처에 무엇이 들어있다고 믿는가?
```

**결과**: 1단계에서 "Noor는 동료가 우유를 바꾸는 것을 목격함"이 명시되고, 정확히 "아몬드밀크"가 도출된다.

왜 이런 차이가 생길까? LLM은 모든 정보를 "전지적 시점"으로 처리하려는 경향이 있다. 1단계에서 강제로 특정 관점의 정

보만 추출하게 하면, 2단계에서 그 관점에 충실한 답을 내놓는다.

### 예제 2: 사용자 맥락 전달 (LLM이 '나'를 이해하게)

실무에서 가장 바로 적용하기 좋은 패턴이다. LLM에게 "내가 누구인지"를 알려주는 것.

**상황**: 코드 리뷰를 요청하는데, 내 숙련도에 맞는 피드백을 받고 싶다.

**일반 프롬프팅**

```
이 Python 코드를 리뷰해줘.
[코드]
```

→ LLM이 내 수준을 모르므로 너무 기초적이거나 너무 고급인 피드백이 섞여 나옴.

**ToM 적용 프롬프팅**

```
[내가 알고 있는 것]
- Python 3년 사용, 백엔드 개발 경험
- 비동기 처리(asyncio) 익숙함
- 타입 힌트 사용 중

[내가 익숙하지 않은 것]
- 메모리 최적화, 프로파일링
- C 확장 모듈

[이 코드의 맥락]
- 프로덕션 배포 예정
- 초당 1000건 요청 처리 필요

[요청]
위 맥락을 고려해서 코드를 리뷰해줘.
내가 이미 아는 부분은 간략히, 
내가 놓치기 쉬운 메모리/성능 이슈 위주로 상세히.
```

**결과**: LLM이 비동기 문법 같은 기초 설명은 생략하고, 메모리 누수 가능성이나 GC 이슈 같은 "내가 모르는 영역"에 집중한 피드백을 제공한다.

핵심은 **"알고 있는 것 / 모르는 것"을 명시적으로 구분**하는 것이다. 이 구조만 지켜도 LLM의 답변 품질이 크게 달라진다.

### 예제 3: 다중 관점 시뮬레이션

여러 이해관계자의 반응을 예측하거나, 협상 연습을 할 때 유용한 패턴이다.

**상황**: 새 기능 제안서에 대해 다양한 이해관계자 반응을 예측하고 싶다.

**일반 프롬프팅**

```
이 제안서에 대한 피드백을 줘.
[제안서: 결제 시스템에 암호화폐 옵션 추가]
```

→ 일반적이고 두루뭉술한 피드백.

**ToM 적용 프롬프팅**

```
다음 제안서를 읽고, 각 이해관계자 관점에서 분석해줘.

[제안서]
결제 시스템에 암호화폐 결제 옵션 추가

---
[CFO 관점 시뮬레이션]
이 사람이 알고 있는 것:
- 회사 재무 상태, ROI 기준
- 암호화폐 가격 변동성

이 사람이 모르는 것:
- 기술 구현 난이도
- 젊은 고객층의 암호화폐 사용 비율

→ 이 관점에서 어떤 질문과 우려가 나올까?

---
[개발팀장 관점 시뮬레이션]
이 사람이 알고 있는 것:
- 현재 결제 시스템 아키텍처
- 팀 리소스 상황

이 사람이 모르는 것:
- 암호화폐 규제 현황
- 마케팅 효과 예측

→ 이 관점에서 어떤 기술적 우려를 제기할까?
```

**결과**: 각 역할이 "아는 것"과 "모르는 것"이 다르기 때문에, 현실적이고 구체적인 시뮬레이션이 나온다. CFO는 ROI 질문을, 개발팀장은 구현 복잡도 우려를 제기한다.

이 패턴은 협상 연습, 프레젠테이션 준비, 이해관계자 분석 등에 바로 적용할 수 있다.

## 모범사례/패턴 비교

| 프롬프팅 기법 | 장점 | 주의점 |
| --- | --- | --- |
| Zero-Shot | 간편함 | ToM 과제에서 정확도 낮음 |
| Chain-of-Thought | 복잡한 추론에 효과적 | ToM에서는 제한적 개선 |
| SimToM (2단계) | ToM 정확도 29%+ 향상 | 프롬프트가 길어짐 |
| 맥락 명시 (알고/모르는 것) | 실무 적용 쉬움 | 사전에 맥락 정리 필요 |

가장 간단한 ToM 트리거는 **"그리고 왜?"**를 질문 끝에 추가하는 것이다. "Sam은 가방에 무엇이 있다고 믿는가?"보다 "Sam은 가방에 무엇이 있다고 믿는가? **왜 그렇게 믿는가?**"가 더 정확한 답을 유도한다. "왜"를 설명하려면 LLM이 해당 인물의 지식 상태를 추론해야 하기 때문이다.

## 마치며

- ToM 프롬프팅의 핵심은 LLM에게 **"이 사람(또는 나)이 무엇을 알고, 무엇을 모르는지"**를 명시하는 것이다
- SimToM의 2단계 구조(관점 필터링 → 답변)로 ToM 과제에서 29% 이상 정확도가 향상된다
- 실무에서는 프롬프트에 **[알고 있는 것] / [모르는 것] / [목표]** 구조를 추가하는 것만으로 효과를 볼 수 있다

**실전 팁: 다음 프롬프트에 "나는 ~를 알고 있고, ~는 익숙하지 않다"를 추가해보세요. LLM이 당신의 눈높이에 맞춰 답할 것이다.**
