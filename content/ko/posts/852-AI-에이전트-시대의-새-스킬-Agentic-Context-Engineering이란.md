프롬프트 엔지니어링만으로는 부족했던 이유가 있습니다. 최근 몇 달 사이 AI 개발자들 사이에서 "Context Engineering"이라는 용어가 떠오르며, 실무자들은 "이제 프롬프트가 아니라 컨텍스트를 설계해야 한다"는 이야기를 하고 있습니다. 특히 AI 에이전트처럼 여러 단계를 거쳐 복잡한 작업을 수행하는 시스템에서는 단순히 좋은 질문을 던지는 게 아니라, 어떤 정보를 언제 어떻게 제공할지 전략적으로 큐레이션하는 능력이 성패를 가릅니다.

이 글을 통해 실무에서 바로 적용 가능한 컨텍스트 엔지니어링의 핵심 개념과 최신 연구 결과(ACE 프레임워크)를 배울 수 있습니다.

**한줄요약**

Agentic Context Engineering은 AI 에이전트가 작업을 수행하는 동안 제한된 컨텍스트 윈도우에 들어갈 최적의 정보를 순환적으로 큐레이션하는 기술이며, 프롬프트 작성을 넘어 시스템 전체의 정보 흐름을 설계하는 분야입니다.

## 배경

### 프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로

초기 LLM 활용은 대부분 단발성 작업이었습니다. 분류, 요약, 텍스트 생성 같은 일회성 과제에서는 프롬프트만 잘 작성하면 충분했습니다. 하지만 AI 에이전트 시대가 열리면서 상황이 바뀌었습니다.

| 구분 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
| --- | --- | --- |
| 초점 | 시스템 프롬프트 작성 최적화 | 컨텍스트 윈도우 전체 상태 관리 |
| 적용 시점 | 단일 작업 시작 전 | 멀티턴 추론 전 과정 |
| 정보 범위 | 주로 지시사항 | 프롬프트 + 도구 + 메모리 + 외부 데이터 |
| 업데이트 주기 | 정적 | 순환적, 반복적 |

AI 에이전트는 여러 단계에 걸쳐 도구를 호출하고, 환경과 상호작용하며, 장기적인 작업을 수행합니다. 이 과정에서 컨텍스트 윈도우는 빠르게 채워지고, 관련 없는 정보로 오염되거나(Context Poisoning), 중요한 정보를 잃게 되는(Context Collapse) 문제가 발생합니다.

### 컨텍스트란 무엇인가

컨텍스트는 LLM이 샘플링할 때 포함되는 토큰의 집합입니다.

구체적으로는:

- 시스템 프롬프트 및 지시사항
- 사용자 입력과 질문
- 단기 메모리 (대화 기록)
- 장기 메모리 (과거 작업 정보)
- 검색된 지식베이스 정보
- 도구 설명 및 MCP 프로토콜
- 외부 API 응답 데이터

Andrej Karpathy는 "LLM은 새로운 운영체제이며, 컨텍스트 윈도우는 RAM과 같다"고 표현했습니다. 제한된 용량 안에서 다음 단계에 필요한 정확한 정보를 채워 넣는 섬세한 작업이 바로 컨텍스트 엔지니어링입니다.

### 왜 에이전트에서 더 중요한가

AI 에이전트는 다음 문제들로 인해 컨텍스트 관리가 훨씬 더 어렵습니다:

- 토큰 한계 초과: 장시간 작업 시 컨텍스트 윈도우가 가득 참
- 비용과 지연: 불필요한 정보가 많을수록 API 비용 증가, 응답 속도 저하
- 성능 저하: 노이즈 정보가 추론 품질을 떨어뜨림
- 도구 혼란: 너무 많은 도구 설명이 제공되면 어떤 도구를 써야 할지 헷갈림

## 핵심

> Agentic Context Engineering은 AI 에이전트가 각 추론 단계마다 제한된 컨텍스트 윈도우에 적합한 정보를 선택, 압축, 저장, 격리하는 전략적 설계 방법론입니다.

Anthropic은 컨텍스트 엔지니어링을 "다음 단계에 적절한 정보로 컨텍스트 윈도우를 채우는 예술이자 과학"으로 정의합니다. 이는 프롬프트 엔지니어링의 자연스러운 진화이며, 복잡한 에이전트 시스템 구축의 필수 기술입니다.

### ACE 프레임워크: 컨텍스트를 진화시키는 에이전트

2025년 10월, Stanford와 UC Berkeley 연구팀이 발표한 ACE(Agentic Context Engineering) 프레임워크는 컨텍스트를 정적인 프롬프트가 아니라 진화하는 플레이북으로 다룹니다.

기존 방식의 문제점:

- Brevity Bias: 요약 과정에서 중요한 도메인 지식이 누락됨
- Context Collapse: 반복적인 재작성으로 디테일이 점점 사라짐

ACE는 세 가지 역할로 작동합니다:

1. Generator: 추론 과정을 실행하고 결과 생성
2. Reflector: 성공과 실패에서 구체적인 인사이트 추출
3. Curator: 인사이트를 구조화된 컨텍스트 업데이트로 통합

핵심 설계 원칙:

- 증분 델타 업데이트: 전체를 다시 쓰지 않고 새로운 항목만 추가
- Grow-and-Refine: 유용한 히스토리를 보존하며 점진적으로 개선
- 구조화된 누적: 지식을 체계적으로 축적하여 장기 컨텍스트 활용

실증 결과:

- AppWorld 에이전트 벤치마크: 기존 대비 +10.6% 성능 향상
- 금융 도메인 추론: +8.6% 정확도 개선
- 지연시간: 82~92% 감소
- 토큰 비용: 75~84% 절감

특히 ACE를 적용한 오픈소스 모델(DeepSeek-V3.1)이 GPT-4.1 기반 프로덕션 에이전트(IBM CUGA)와 동등한 성능을 보여, 컨텍스트 설계만으로도 모델 성능 격차를 메울 수 있음을 입증했습니다.

## 실습

실무에서 컨텍스트 엔지니어링을 구현하는 방법을 단계별로 살펴보겠습니다.

### 1. 컨텍스트 전략 수립: Write, Select, Compress, Isolate

Lance Martin이 제시한 4가지 패턴을 적용합니다:

**Write (작성)**: 컨텍스트 윈도우 외부에 정보 저장

- 작업 히스토리를 데이터베이스에 저장
- 학습된 패턴을 별도 파일로 관리
- 에이전트 메모리를 벡터 DB에 인덱싱

**Select (선택)**: 필요한 정보만 컨텍스트로 가져오기

- RAG로 관련 문서만 검색
- 도구 설명 필터링: 시맨틱 유사도 기반 도구 선택
- 코드 에이전트의 경우 AST 파싱으로 의미 있는 청크만 임베딩

**Compress (압축)**: 핵심만 남기기

- 대화 요약: 최근 3턴만 전체 유지, 나머지는 요약본
- 토큰 최적화: 중복 제거, 축약형 사용
- 프롬프트 압축 기법 적용

**Isolate (격리)**: 컨텍스트 분리로 혼란 방지

- 멀티 에이전트: 각 에이전트별 독립 컨텍스트
- 도메인 분리: 금융/법률 작업 시 전용 컨텍스트
- 계층 구조: 메인 에이전트와 서브 에이전트 컨텍스트 격리

### 2. 도구 관리 최적화

에이전트가 너무 많은 도구를 보면 혼란스러워합니다.

구현 방법:

```
사용자 쿼리: "최근 판매 데이터 분석해줘"

1단계: 도구 설명 임베딩
   - 전체 50개 도구를 벡터화

2단계: 쿼리와 시맨틱 유사도 계산
   - 상위 5개 도구만 선택
   - "sales_data_fetch", "analytics_tool", "chart_generator" ...

3단계: 선택된 도구만 컨텍스트에 포함
   - 도구 선택 정확도 3배 향상 (최근 연구 결과)
```

### 3. 메모리 시스템 설계

단기/장기 메모리를 명확히 구분합니다:

단기 메모리 (Short-term):

- 최근 3~5턴 대화 전체 유지
- 현재 작업의 중간 결과
- 임시 변수와 상태

장기 메모리 (Long-term):

- 사용자 선호도
- 과거 성공한 전략 패턴
- 도메인 특화 지식
- ACE 스타일 플레이북

저장 위치:

- 단기: 컨텍스트 윈도우 내
- 장기: 벡터 DB, 그래프 DB, 키-밸류 스토어

### 4. 반복 개선 루프 구축

ACE 프레임워크에서 영감을 받은 실무 프로세스:

```
반복 사이클:

[실행] 
→ 에이전트가 작업 수행
→ 실행 결과 및 피드백 수집

[반영]
→ 무엇이 잘 작동했는가?
→ 어떤 정보가 부족했는가?
→ 어떤 패턴이 반복되는가?

[큐레이션]
→ 인사이트를 구조화된 항목으로 변환
→ 플레이북에 델타 업데이트 추가
→ 기존 항목과 충돌 시 병합 규칙 적용

[적용]
→ 업데이트된 컨텍스트로 다음 작업 수행
```

### 5. 컨텍스트 품질 모니터링

실시간으로 컨텍스트 상태를 추적합니다:

모니터링 지표:

- 컨텍스트 윈도우 사용률 (70~90% 유지 권장)
- 관련 정보 vs 노이즈 비율
- 도구 호출 성공률
- 작업 완료 시간
- API 토큰 소비량

Cognizant는 2025년 8월, ContextFabric 플랫폼을 통해 1,000명의 컨텍스트 엔지니어를 배치한다고 발표했습니다. 이들은 기업의 운영 모델, 워크플로우, 정책을 에이전트가 이해할 수 있는 컨텍스트로 변환하는 역할을 맡습니다. 이는 컨텍스트 엔지니어링이 단순한 기술이 아니라 전문 직무로 자리잡고 있음을 보여줍니다.

## 모범사례/패턴 비교

| 패턴 | 장점 | 주의점 |
| --- | --- | --- |
| 정적 프롬프트 (Static Prompt) | 구현 간단, 예측 가능 | 복잡한 에이전트 작업에 부적합, 적응력 없음 |
| 동적 요약 (Dynamic Summary) | 컨텍스트 크기 제어 가능 | Brevity Bias로 중요 정보 손실, Context Collapse 위험 |
| RAG 기반 선택 (RAG Selection) | 관련성 높은 정보만 제공 | 검색 품질에 의존, 임베딩 모델 성능 중요 |
| 델타 업데이트 (Delta Update/ACE) | 정보 누적, 디테일 보존, 확장 가능 | 구현 복잡도 높음, 피드백 품질 의존적 |
| 멀티 에이전트 격리 (Multi-Agent Isolation) | 역할별 전문화, 컨텍스트 혼란 방지 | 에이전트 간 조율 필요, 오버헤드 증가 |
| 계층적 메모리 (Hierarchical Memory) | 단기/장기 정보 명확히 구분 | 메모리 시스템 설계 및 유지 비용 |

## 마치며

AI 에이전트의 성능은 모델만으로 결정되지 않습니다. 어떤 정보를 언제 제공하느냐가 성패를 가릅니다. 프롬프트 엔지니어링이 "무엇을 물을 것인가"였다면, 컨텍스트 엔지니어링은 "무엇을 보여줄 것인가"입니다. ACE 프레임워크가 입증했듯이, 오픈소스 모델도 적절한 컨텍스트 설계로 프리미엄 모델과 경쟁할 수 있습니다.

실무 팁:

다음 AI 에이전트 프로젝트를 시작할 때 "우리 에이전트는 매 단계마다 정말 필요한 정보만 보고 있는가?"라는 질문부터 던져보세요. Write-Select-Compress-Isolate 패턴으로 컨텍스트 전략을 재설계하면, 성능 향상과 비용 절감을 동시에 달성할 수 있습니다.
