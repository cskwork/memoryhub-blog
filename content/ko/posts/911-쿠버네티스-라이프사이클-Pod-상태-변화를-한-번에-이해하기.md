- `kubectl get pods`를 봤을 때 STATUS가 `CrashLoopBackOff`, `Error`, `Terminating`으로만 가득 차 있으면 어디부터 봐야 할지 막막해집니다.
- 사실 이 메시지들은 전부 “라이프사이클”이라는 큰 흐름 속에서 벌어진 단계적 사건들입니다.
- 흐름을 이해하면 장애가 났을 때 *어디부터* 확인해야 할지, *어디까지* 기다려야 할지가 명확해집니다.
- 이 글에서는 Pod 중심 라이프사이클을 개념→실습→모범 패턴 순서로 정리해, 실무 트러블슈팅에 바로 써먹을 수 있게 정리합니다.

**쿠버네티스 라이프사이클은 “Pod/컨테이너가 생성 → 준비 → 서비스 → 종료되는 전체 여정”이며, Phase·Condition·Container State를 함께 보면 장애 원인이 눈에 보입니다.**

## 배경

- **왜 라이프사이클을 알아야 할까?**
  - “그냥 Deployment 만들면 알아서 돌아가잖아?” → 장애가 나면 결국 Pod 단위 상태를 봐야 합니다.
  - 오토스케일링, 롤링 업데이트, 헬스 체크, graceful shutdown 같은 운영 기능은 모두 라이프사이클 위에서 동작합니다.
- **이 글에서 다루는 라이프사이클 범위**
  - Pod 라이프사이클 (핵심)
  - 컨테이너 라이프사이클 & Hooks (postStart / preStop)
  - 간단히 Job/버전 라이프사이클 언급
- **용어 정리**

| 용어 | 의미 | 예시/비고 |
| --- | --- | --- |

## 핵심

> 쿠버네티스 라이프사이클은 Pod·컨테이너가 **생성→스케줄링→실행→헬스체크→종료→정리**되는 전체 흐름이다.

- **핵심 요약**
  - Pod는 `Pending → Running → (Succeeded | Failed | Unknown)`의 Phase를 가진다.([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle"))
  - 동시에 Condition(Ready 여부)와 Container State(Waiting/Running/Terminated)가 별도로 움직인다.
  - 종료 시에는 `preStop → SIGTERM → Grace Period → SIGKILL → 리소스 정리` 흐름을 따른다.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
  - Job/CronJob, Deployment 등의 상위 리소스는 이 Pod 라이프사이클 위에서 재시도·롤링 업데이트를 orchestrate 한다.([Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/job/?utm_source=chatgpt.com "Jobs"))

### 1) Pod Phase – “큰 그림” 상태

- **Phase 종류** (Kubernetes 공식 정의 기준)([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle"))
  - `Pending`: 스펙은 생성되었지만 아직 Node에 스케줄링 중이거나 이미지 풀링 등으로 컨테이너가 뜨지 않은 상태
  - `Running`: Node에 스케줄됐고 컨테이너들이 생성되었으며, 최소 하나는 실행 중
  - `Succeeded`: 모든 컨테이너가 0(exit code)으로 정상 종료, 재시작 안 됨 (주로 Job)
  - `Failed`: 모든 컨테이너가 종료되었고, 하나 이상이 비정상 종료 코드
  - `Unknown`: 노드와 통신 문제 등으로 상태를 알 수 없음
- STATUS 컬럼에 보이는 `CrashLoopBackOff`, `ImagePullBackOff` 등은 **Phase가 아니라 세부 Reason**임을 기억하세요.

### 2) Pod Conditions – “서비스 가능 여부”

- 주요 Condition ([LeeHosu](https://leehosu.github.io/k8s-pod-lifecycle/?utm_source=chatgpt.com "쿠버네티스에서 Pod의 생애주기 - LakeScript"))
  - `PodScheduled`: 어떤 Node에 배치되었는가
  - `Initialized`: Init 컨테이너들이 모두 성공했는가
  - `ContainersReady`: 모든 컨테이너가 준비되었는가
  - `Ready`: 이 Pod에 트래픽을 보내도 되는가 (서비스 로드밸런싱 풀에 포함 여부)
- 실무에서는 **`kubectl describe pod`로 Condition의 변화 시간**을 보는 것만으로도 “언제부터 트래픽을 받기 시작했는지” 파악 가능합니다.

### 3) Container State – “디테일”

- 컨테이너마다 상태가 따로 있다: `Waiting`, `Running`, `Terminated`.([Velog](https://velog.io/%40jayoh/%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4-%ED%8C%A8%ED%84%B4-5%EC%9E%A5-%EC%88%98%EB%AA%85%EC%A3%BC%EA%B8%B0-%EA%B4%80%EB%A6%AC?utm_source=chatgpt.com "쿠버네티스 패턴 - 5장 수명주기 관리"))
  - `Waiting`: 이미지를 받는 중, Secret/Config 적용 중 등
  - `Running`: 정상 실행 중
  - `Terminated`: 종료 완료(성공/실패 코드와 함께)
- Phase가 `Running`인데 컨테이너 State가 `Waiting`이면 대개 이미지 풀링, 시작 지연, postStart hook 문제 등을 의심합니다.

### 4) 시작 라이프사이클 (Activation)

1. 사용자가 Pod 스펙 제출 (`kubectl apply -f ...`).
2. API Server가 etcd에 저장 → 스케줄러가 노드를 선택.
3. 선택된 노드의 kubelet이 이미지 풀링, 컨테이너 생성, 볼륨 마운트 수행.
4. Init 컨테이너 → 메인 컨테이너 순서로 실행.
5. 컨테이너가 올라오고, Readiness Probe가 성공하여 `Ready=True`가 되면 서비스 트래픽 대상에 포함.

### 5) 종료 라이프사이클 (Termination)

1. `kubectl delete pod` 또는 상위 리소스(Deployment, Job)에서 Pod 삭제 요청.
2. API Server가 Pod에 `deletionTimestamp` 설정 → UI에서는 `Terminating`으로 표시.
3. Endpoints에서 Pod 제거 → 더 이상 새 트래픽은 들어오지 않음.
4. 컨테이너에 `preStop` hook 실행 → 이어서 `SIGTERM` 전송.
5. `terminationGracePeriodSeconds` 동안 정상 종료를 기다렸다가, 안 끝나면 `SIGKILL`로 강제 종료.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
6. 종료 후 Pod 정보가 etcd에서 제거.

## 실습

## Kubernetes v1.34.x (2025년 11월 기준 최신 안정 버전) ([Kubernetes](https://kubernetes.io/releases/?utm_source=chatgpt.com "Releases"))

`kubectl` 사용 가능, 최소 1노드 클러스터 (minikube, kind, EKS, GKE 등)

1. **환경 확인 및 네임스페이스 준비**
   - 클러스터/클라이언트 버전 확인:
   - `kubectl version --short
     kubectl get nodes`
   - 실습용 네임스페이스 생성:
   - `kubectl create ns lifecycle-demo
     kubectl config set-context --current --namespace=lifecycle-demo`
2. **기본 Pod 배포 후 Phase/Condition 관찰**
   - **Pod 매니페스트 작성 (언어: YAML, 대상: Kubernetes v1, v1.34 기준)**  
     `simple-pod.yaml`:
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: demo-pod
     labels:
     app: lifecycle-demo
     spec:
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo START && sleep 300"]`
   - 배포 및 상태 확인:
   - `kubectl apply -f simple-pod.yaml
     kubectl get pods -w`
   - 예상 출력(텍스트 캡처 대체):
   - `NAME READY STATUS RESTARTS AGE
     demo-pod 0/1 Pending 0 3s
     demo-pod 1/1 Running 0 10s`
   - 세부 상태 확인:
     - 출력에서 `Status: Running`, Conditions에 `Ready=True`, 컨테이너 State가 `Running`인 것을 확인합니다.
   - `kubectl describe pod demo-pod`
3. **실패하는 Pod로 Failed/CrashLoopBackOff 경험하기**
   - 바로 종료되는 컨테이너 예제 (`fail-pod.yaml`):
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: fail-pod
     spec:
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo FAILING && exit 1"]
     restartPolicy: OnFailure`
   - 배포 후 상태 관찰:
   - `kubectl apply -f fail-pod.yaml
     kubectl get pods -w`
   - 예상 텍스트 출력 예:
   - `NAME READY STATUS RESTARTS AGE
     fail-pod 0/1 Error 0 5s
     fail-pod 0/1 CrashLoopBackOff 1 15s`
   - `kubectl get pod fail-pod -o yaml | grep phase` 로 Phase를 보면 `Failed`일 수 있고, 이벤트에는 exit code 1이 기록됩니다.
   - 여기서 볼 수 있는 것:
     - STATUS 컬럼의 `Error/CrashLoopBackOff`는 **컨테이너 재시작 정책과 실패 기록의 결과**.
     - Pod Phase는 “전체 수명 요약”, 이벤트/State는 “상세 원인”이라는 점을 체감할 수 있습니다.
4. **preStop Hook으로 종료 라이프사이클 보기**
   - graceful 종료를 시뮬레이션하는 Pod (`hook-pod.yaml`):
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: hook-pod
     labels:
     app: lifecycle-demo
     spec:
     terminationGracePeriodSeconds: 20
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo RUNNING && while true; do date; sleep 2; done"]
     lifecycle:
     preStop:
     exec:
     command: ["sh", "-c", "echo PRESTOP START; sleep 10; echo PRESTOP END"]`
   - 배포 및 로그 보기:
   - `kubectl apply -f hook-pod.yaml
     kubectl logs -f hook-pod`
   - 다른 터미널에서 Pod 삭제:
   - `kubectl delete pod hook-pod
     kubectl get pod hook-pod -w`
   - 예상 로그/상태 흐름(텍스트 캡처 대체):
   - `# 로그
     RUNNING
     Fri Nov 14 00:00:01 UTC 2025
     Fri Nov 14 00:00:03 UTC 2025
     PRESTOP START
     PRESTOP END
     # 상태
     NAME READY STATUS AGE
     hook-pod 1/1 Running 20s
     hook-pod 1/1 Terminating 32s
     hook-pod 0/1 Terminating 40s
     hook-pod 0/1 Completed 41s (이후 목록에서 사라짐)`
   - 여기서 볼 수 있는 것:
     - `kubectl delete` 직후 STATUS가 `Terminating`으로 바뀌고, 그 시간 동안 **preStop + SIGTERM + Grace Period**가 함께 진행됩니다.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
     - preStop에서 10초를 사용했으니, graceful 종료 시간이 여유 있게 20초 이상으로 설정된 것이 중요합니다.

## 모범사례/패턴 비교

| 패턴 | 장점 | 주의점 |
| --- | --- | --- |
| Readiness/Liveness Probe + 라이프사이클 기반 배포 | 장애 컨테이너를 자동으로 재시작하고, 준비 안 된 Pod에 트래픽이 가지 않음 | Probe의 timeout/failureThreshold 값을 너무 공격적으로 잡으면 정상 기동 지연도 장애로 인식될 수 있음 ([Velog](https://velog.io/%40jayoh/%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4-%ED%8C%A8%ED%84%B4-5%EC%9E%A5-%EC%88%98%EB%AA%85%EC%A3%BC%EA%B8%B0-%EA%B4%80%EB%A6%AC?utm_source=chatgpt.com "쿠버네티스 패턴 - 5장 수명주기 관리")) |
| preStop Hook + 충분한 Grace Period 설정 | DB 커넥션 정리, 세션 플러시 등 안정적인 종료 가능 | `terminationGracePeriodSeconds`보다 preStop 작업이 오래 걸리면 결국 SIGKILL로 강제 종료됨; 훅은 가볍게 설계해야 함 ([Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/?utm_source=chatgpt.com "Container Lifecycle Hooks")) |
| Job/CronJob에 `backoffLimit`·`restartPolicy` 명시 | 일회성/배치 작업에 대해 재시도 횟수와 실패 기준을 명확히 제어 가능 | 기본값(예: backoffLimit=6)을 그대로 쓰면, 실패한 Job이 너무 오래 재시도되어 자원을 잠식할 수 있음 ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/job/?utm_source=chatgpt.com "Jobs")) |
| Pod 상태 모니터링 시 Phase + Condition + Container State를 함께 보는 패턴 | STATUS 한 줄이 아닌, “언제 Ready 되었고 왜 실패했는지”를 빠르게 파악 | 대시보드에서 Phase만 보는 습관이 들면, 실제 원인(이미지 풀 실패, 훅 오류, 프로브 실패 등)을 놓치기 쉽다 ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle")) |
| 버전 라이프사이클에 맞춘 정기 업그레이드 (예: v1.34 트랙 유지) | 지원 종료 전 업그레이드로 보안·버그 패치를 안정적으로 반영 | 클러스터/애플리케이션 테스트 전략을 세우지 않으면, 업그레이드가 “대형 이벤트”가 되어 진행이 어려워짐 ([Kubernetes](https://kubernetes.io/releases/?utm_source=chatgpt.com "Releases")) |

## 마치며

- 쿠버네티스 라이프사이클은 “한 번에 외워야 하는 개념”이 아니라, Pod 상태를 읽어내기 위한 **해석 프레임**입니다.
- Phase(큰 그림) → Condition(서비스 가능 여부) → Container State/이벤트(디테일) 순서로 확인하면 트러블슈팅 속도가 확실히 빨라집니다.
- (실제 적용 팁 한 마디)
  - 팀 미팅에서 이렇게 정리해 보세요: **“STATUS는 겉표지일 뿐이고, Pod 라이프사이클을 같이 봐야 진짜 장애 원인이 보입니다.”**
