# 

Claude Code를 써본 개발자라면 한 번쯤 이런 경험이 있을 것이다. 대규모 리팩토링을 맡겼는데 컨텍스트 윈도우가 바닥나고, PR 리뷰를 시켰더니 보안 이슈는 잘 잡지만 성능 문제는 놓친다. 하나의 AI 에이전트에게 모든 것을 기대하는 건,

한 명의 개발자에게 프론트엔드부터 백엔드, 테스트, 문서화까지 동시에 맡기는 것과 다르지 않다.

**Claude Code Agent Teams는 여러 AI 에이전트가 각자 역할을 분담하고, 서로 소통하며 병렬로 협업하는 멀티 에이전트 오케스트레이션 시스템이다.**

결론부터 말하면, Agent Teams는 단일 에이전트의 컨텍스트 한계를 해결하고 복잡한 작업을 병렬 처리할 수 있게 해주는 Claude Code의 실험적 기능이며, 적절한 상황에서 사용하면 개발 효율을 크게 끌어올릴 수 있다.

## 배경

2025년 12월, 한 개발자가 Claude Code 바이너리에 `strings` 명령을 실행하다가 흥미로운 것을 발견했다. TeammateTool이라는 이름의 완전한 멀티 에이전트 오케스트레이션 레이어가 피처 플래그 뒤에 숨어 있었던 것이다. 이 발견은 Hacker News에서 200개가 넘는 댓글이 달리며 큰 반향을 일으켰고, 커뮤니티에서는 비공식 접근 도구까지 만들었다.

그리고 2026년 초, Anthropic은 이 기능을 공식 문서에 Agent Teams라는 이름으로 등록했다.

이 기능이 등장한 배경에는 산업 전체의 흐름이 있다. Gartner에 따르면 멀티 에이전트 시스템에 대한 문의가 2024년 1분기 대비 2025년 2분기에 1,445% 급증했다. 2026년 말까지 기업 애플리케이션의 40%가 태스크 특화 AI 에이전트를 포함할 것으로 전망된다.

단일 에이전트에서 팀 오케스트레이션으로의 전환은 소프트웨어 개발 역사에서 모놀리식에서 마이크로서비스로 전환된 것과 유사한 패러다임 시프트라 할 수 있다.

> Agent Teams란, 하나의 리더 세션이 여러 개의 독립된 Claude Code 인스턴스(팀원)를 생성하고, 공유 태스크 리스트와 메시지 시스템을 통해 병렬 작업을 조율하는 멀티 에이전트 협업 시스템이다.

그렇다면 기존의 서브에이전트(Subagent)와는 무엇이 다른가. 이 차이를 이해하는 것이 Agent Teams를 제대로 활용하는 첫 걸음이다.

## 서브에이전트 vs Agent Teams, 핵심 차이

회사 조직에 비유하면 이해하기 쉽다. 서브에이전트는 **심부름꾼**이다.

팀장이 "이거 조사해와"라고 시키면 결과만 보고하고 돌아온다.

다른 심부름꾼과 대화할 수 없고, 팀장만 결과를 받는다.

반면 Agent Teams의 팀원은 **프로젝트 팀 멤버**다.

각자 독립된 업무 공간이 있고, 서로 메시지를 주고받으며, 공유 칸반 보드(태스크 리스트)를 보면서 자율적으로 일을 진행한다.

| 비교 항목 | 서브에이전트 (Subagent) | 에이전트 팀 (Agent Teams) |
| --- | --- | --- |
| 컨텍스트 | 자체 컨텍스트 윈도우, 결과만 호출자에게 반환 | 자체 컨텍스트 윈도우, 완전히 독립적 |
| 소통 방식 | 메인 에이전트에게만 결과 보고 | 팀원끼리 직접 메시지 교환 가능 |
| 조율 방식 | 메인 에이전트가 모든 작업 관리 | 공유 태스크 리스트 기반 자율 조율 |
| 적합한 상황 | 결과만 필요한 집중 작업 | 토론과 협업이 필요한 복잡한 작업 |
| 토큰 비용 | 상대적으로 저렴 (결과가 요약되어 반환) | 상대적으로 비쌈 (각 팀원이 별도 인스턴스) |

**핵심은 이것이다.** 작업자들이 서로 소통해야 하는가?

소통이 필요 없다면 서브에이전트, 서로 발견한 내용을 공유하고 도전해야 한다면 Agent Teams가 맞다.

## 아키텍처, 어떻게 작동하는가

Agent Teams의 구조는 네 가지 핵심 구성요소로 이루어져 있다.

**팀 리더(Team Lead)** 는 메인 Claude Code 세션이다. 팀을 만들고, 팀원을 생성하며, 전체 작업을 조율한다.

위임 모드(Delegate Mode)를 사용하면 리더가 직접 코드를 작성하지 않고 순수하게 조율에만 집중하도록 설정할 수도 있다.

**팀원(Teammates)** 은 각각 독립된 Claude Code 인스턴스다. 자체 컨텍스트 윈도우를 갖고,

프로젝트의 CLAUDE.md와 MCP 서버 등 기본 컨텍스트를 로드하지만, 리더의 대화 기록은 이어받지 않는다.

이 설계가 중요한데, 각 팀원이 신선한(fresh) 컨텍스트 윈도우에서 시작하기 때문에 **단일 에이전트가 80-90%까지 채우던 컨텍스트를 팀원당 약 40% 수준으로 유지**할 수 있다.

**태스크 리스트(Task List)** 는 공유 칸반 보드와 같다. 태스크는 pending, in progress, completed 세 가지 상태를 가지며,

태스크 간 의존성(dependency)도 설정할 수 있다.

한 태스크가 완료되면 그것에 의존하던 다음 태스크가 자동으로 해제(unblock)된다.

파일 잠금(file locking)으로 여러 팀원이 동시에 같은 태스크를 가져가는 경합 상태도 방지한다.

**메일박스(Mailbox)** 는 에이전트 간 메시징 시스템이다. message는 특정 팀원에게, broadcast는 전체 팀원에게 보낸다.

팀원이 메시지를 보내면 수신자에게 자동 전달되며, 팀원이 작업을 마치고 멈추면 리더에게 자동 알림이 간다.

이 모든 데이터는 로컬 파일 시스템에 저장된다.

```
~/.claude/
├── teams/{team-name}/
│   ├── config.json        # 팀 메타데이터, 멤버 목록
│   └── messages/          # 에이전트 간 메시지 수신함
└── tasks/{team-name}/     # 팀 태스크 리스트
```

클라우드 서버가 아닌 로컬 파일 기반이라는 점이 특징적이다. 복잡한 인프라 없이 파일 시스템만으로 에이전트 간 조율이 이루어진다.

## 실습

### 1단계: Agent Teams 활성화

Agent Teams는 실험적 기능이므로 기본적으로 비활성화되어 있다. 환경변수를 설정하거나 settings.json에 추가해야 한다.

```
// ~/.claude/settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

또는 쉘 환경에서 직접 설정할 수도 있다.

```
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

### 2단계: 팀 생성 및 작업 지시

활성화 후 Claude Code를 실행하고, 자연어로 팀 구성과 작업을 지시한다.

중요한 것은 **각 역할이 독립적으로 수행 가능한 작업**을 할당하는 것이다.

```
CLI 개발 도구의 UX를 검토할 에이전트 팀을 만들어줘.
한 명은 사용자 경험, 한 명은 기술 아키텍처,
한 명은 악마의 변호인(devil's advocate) 역할로 구성해줘.
```

Claude가 팀을 생성하고, 태스크 리스트를 만들고, 팀원을 각 역할에 배치하여 작업을 시작한다.

### 3단계: 디스플레이 모드 선택

팀원들의 작업을 확인하는 두 가지 모드가 있다.

**In-process 모드**는 기본 설정이다. 모든 팀원이 하나의 터미널 안에서 실행된다. `Shift+Up/Down`으로 팀원을 선택하고 직접 메시지를 보낼 수 있다. 별도 설정이 필요 없어 가장 간편하다.

**Split-pane 모드**는 각 팀원이 별도의 터미널 창을 갖는다. tmux 또는 iTerm2가 필요하며, 모든 팀원의 출력을 동시에 볼 수 있다.

```
// settings.json에서 설정
{
  "teammateMode": "in-process"   // 또는 "tmux"
}
```

### 4단계: 팀원과 직접 대화

각 팀원은 완전한 독립 Claude Code 세션이다. 리더를 거치지 않고 팀원에게 직접 지시를 내리거나 추가 질문을 할 수 있다.

- In-process 모드: `Shift+Up/Down`으로 팀원 선택 후 입력
- Split-pane 모드: 해당 팀원의 창을 클릭하여 직접 상호작용

### 5단계: 작업 완료 및 정리

작업이 끝나면 팀원을 종료하고 리소스를 정리한다. 이 순서가 중요하다.

```
연구 담당 팀원을 종료해줘      # 팀원 개별 종료
(모든 팀원 종료 후)
팀을 정리해줘                  # 리더가 공유 리소스 정리
```

팀원이 아직 실행 중인데 정리를 시도하면 실패한다. 반드시 팀원을 먼저 종료하고 리더가 정리해야 한다. 팀원이 정리를 실행하면 리소스가 불일치 상태로 남을 수 있으므로, **정리는 항상 리더를 통해** 수행한다.

## 실전 활용 시나리오

### 병렬 코드 리뷰

단일 리뷰어는 한 번에 한 가지 유형의 이슈에 치중하는 경향이 있다. 보안, 성능, 테스트 커버리지를 각각 독립 도메인으로 분리하면 모든 관점에서 철저한 리뷰가 동시에 이루어진다.

```
PR #142를 리뷰할 에이전트 팀을 만들어줘.
- 한 명은 보안 취약점 집중
- 한 명은 성능 영향 분석
- 한 명은 테스트 커버리지 검증
각자 리뷰 후 결과를 보고하도록 해줘.
```

### 경쟁 가설 기반 디버깅

원인이 불분명한 버그에 대해 한 에이전트가 하나의 가설을 찾고 탐색을 멈추는 문제를 해결한다.

여러 팀원이 각자 다른 가설을 세우고, **서로의 이론을 반증하려는 토론 구조**를 만들면 생존하는 이론이 실제 근본 원인일 확률이 높아진다.

```
사용자가 메시지 하나 보낸 후 앱이 종료되는 문제를 조사해줘.
5명의 팀원이 각각 다른 가설을 세우고,
서로의 이론을 반증하려 토론하도록 해줘.
과학적 토론처럼 진행하고, 합의된 결론을 문서에 업데이트해줘.
```

### 크로스 레이어 기능 개발

프론트엔드, 백엔드, 테스트가 동시에 변경되어야 하는 기능 개발에서 각 레이어를 별도 팀원이 담당하면 파일 충돌 없이 병렬 작업이 가능하다.

## 모범사례/패턴 비교

| 패턴 | 장점 | 주의점 |
| --- | --- | --- |
| 계획 승인 모드 (Plan Approval) | 팀원이 구현 전에 계획을 리더에게 제출하고 승인받음. 위험한 변경 사전 차단 가능 | 리더가 자율 판단하므로 "테스트 커버리지 포함된 계획만 승인해" 등 기준을 프롬프트에 명시해야 함 |
| 위임 모드 (Delegate Mode) | 리더가 코딩 대신 조율에만 집중. 리더가 태스크를 가로채는 문제 방지 | `Shift+Tab`으로 활성화. 리더가 직접 코드를 작성해야 할 때는 비활성화 필요 |
| 팀원당 5-6개 태스크 | 팀원이 유휴 상태 없이 계속 작업. 막히는 팀원의 작업 재배치 가능 | 태스크가 너무 작으면 조율 오버헤드가 이득을 초과. 명확한 산출물 단위로 설계 |
| 파일 소유권 분리 | 팀원마다 다른 파일 세트를 담당. 병렬 편집 시 덮어쓰기 방지 | 같은 파일을 두 팀원이 편집하면 충돌 발생. 사전에 파일 경계 설정 필수 |

## 알아두어야 할 제약사항

Agent Teams는 아직 실험적 기능이라는 점을 반드시 인지해야 한다. 현재 알려진 주요 제약은 다음과 같다.

**세션 재개 불가**: in-process 팀원은 `/resume`이나 `/rewind`로 복원되지 않는다. 세션 재개 후 리더가 이미 없는 팀원에게 메시지를 보내려 할 수 있으므로, 새 팀원을 생성하라고 지시해야 한다.

**태스크 상태 지연**: 팀원이 작업 완료 후 태스크 상태를 갱신하지 않는 경우가 있다. 의존성이 있는 후속 태스크가 차단될 수 있으므로 수동으로 확인이 필요하다.

**세션당 팀 하나**: 리더 하나가 동시에 하나의 팀만 관리할 수 있다. 새 팀을 시작하려면 기존 팀을 먼저 정리해야 한다.

**중첩 팀 불가**: 팀원이 자체적으로 팀이나 팀원을 생성할 수 없다. 오직 리더만 팀을 관리한다.

**토큰 비용 증가**: 각 팀원이 별도의 컨텍스트 윈도우를 사용하므로 토큰 사용량이 팀원 수에 비례하여 증가한다.

연구, 리뷰, 신규 기능 개발처럼 병렬 탐색의 가치가 높은 작업에서는 추가 비용이 정당화되지만,

일상적인 작업에는 단일 세션이 더 효율적이다.

## 마치며

- Agent Teams는 여러 Claude Code 인스턴스를 팀으로 운영하여 병렬 탐색과 상호 검증이 필요한 복잡한 작업에서 진가를 발휘하는 멀티 에이전트 오케스트레이션 기능이다.
- 서브에이전트와의 핵심 차이는 팀원 간 직접 소통과 공유 태스크 리스트 기반 자율 조율에 있으며, 파일 충돌 방지를 위한 소유권 분리가 성공적 운영의 전제 조건이다.
- 실전 팁: 먼저 코드 리뷰나 버그 조사처럼 코드 작성이 필요 없는 읽기 전용 작업으로 시작해보자. 병렬 탐색의 가치를 체감한 뒤 기능 개발로 확장하면 된다.
