# 

컴파일러는 컴퓨터 과학에서 가장 복잡한 소프트웨어 중 하나입니다. GCC는 수백 명의 개발자가 40년 넘게 다듬어온 결과물이고, LLVM도 20년 이상의 역사를 가지고 있습니다. 그런데 2026년 2월, AI 에이전트 16개가 2주 만에 10만 줄짜리 C 컴파일러를 만들었습니다.

리눅스 커널을 실제로 빌드하고 부팅까지 성공한 컴파일러를 말입니다. 단순히 "AI가 코드를 잘 짠다"는 이야기가 아닙니다.

**소프트웨어를 만드는 방식 자체가 달라지고 있다는 신호입니다.**

**한줄요약:** 결론부터 말하면, Anthropic의 에이전트 팀 실험은 AI 코딩의 패러다임이 '1인 보조'에서 '자율 팀 협업'으로 전환되고 있음을 보여주며, 개발자의 역할도 '코드 작성자'에서 '시스템 설계자'로 이동하고 있습니다.

## 배경

> 에이전트 팀(Agent Teams)이란, 여러 개의 AI 인스턴스가 하나의 코드베이스에서 병렬로 작업하며 사람의 개입 없이 프로젝트를 완성하는 방식입니다.

AI 코딩 도구의 발전 과정을 돌아보면, 변화의 속도가 놀랍습니다. 초기에는 IDE에서 탭 자동완성이 전부였습니다. 이후 GitHub Copilot이 함수 본문을 완성해주기 시작했고, Claude Code나 Cursor 같은 도구가 페어 프로그래밍을 가능하게 만들었습니다.

하지만 이 모든 도구에는 공통된 전제가 있었습니다. "사람이 작업을 정의하고, AI가 몇 초에서 몇 분간 실행하고,

다시 사람에게 돌아온다"는 구조입니다.

에이전트 팀은 이 전제를 깨뜨렸습니다. Anthropic의 Safeguards팀 연구원 Nicholas Carlini는 Claude Opus 4.6 모델 16개를 각각 독립된 Docker 컨테이너에 넣고, 하나의 Git 저장소를 공유하며, 무한 루프 안에서 자율적으로 작업하도록 설정했습니다.

중앙 관리자 역할의 AI도 없었습니다. 각 에이전트가 스스로 "지금 가장 중요한 문제가 무엇인지" 판단하고 움직였습니다.

이 실험의 결과물이 바로 **CCC(Claude's C Compiler)**, Rust로 작성된 10만 줄 규모의 C 컴파일러입니다.

## 프로젝트 개요: 숫자로 보는 CCC

이 프로젝트의 규모를 먼저 정리하면 다음과 같습니다.

| 항목 | 수치 |
| --- | --- |
| 투입 에이전트 수 | 16개 (Claude Opus 4.6) |
| 총 Claude Code 세션 | 약 2,000회 |
| 소요 기간 | 약 2주 |
| 입력 토큰 | 약 20억 개 |
| 출력 토큰 | 약 1억 4천만 개 |
| 총 비용 | 약 2만 달러 (약 2,900만 원) |
| 코드 규모 | 약 10만 줄 (Rust) |
| 외부 의존성 | 없음 (Rust 표준 라이브러리만 사용) |

컴파일 가능한 프로젝트 목록도 인상적입니다. Linux 6.9 커널(x86, ARM, RISC-V 아키텍처), QEMU, FFmpeg, SQLite, PostgreSQL, Redis를 성공적으로 컴파일했고, GCC torture 테스트 수트에서 99% 통과율을 기록했습니다.

개발자들의 궁극적 리트머스 테스트라 할 수 있는 Doom 컴파일과 실행에도 성공했습니다.

Carlini는 "이 컴파일러를 직접 만들었다면 비용이 훨씬 더 들었을 것이고, 팀을 꾸렸다면 말할 것도 없다"고 밝혔습니다. 2만 달러는 비싼 실험이지만, 인간 개발팀 대비로는 파격적인 수준입니다.

## 핵심 설계 원칙: 에이전트 팀은 어떻게 작동했나

이 실험에서 가장 흥미로운 부분은 컴파일러 자체가 아닙니다. **에이전트가 자율적으로 협업할 수 있도록 만든 환경 설계**입니다.

Carlini가 대부분의 시간을 쏟은 것도 코드가 아니라 테스트와 환경이었습니다.

### 1. 에이전트 루프: 끝나지 않는 작업 사이클

기존 Claude Code는 작업을 마치면 사람의 입력을 기다립니다. Carlini는 이 구조를 바꿔 무한 루프를 만들었습니다.

```
#!/bin/bash
while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"
    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

에이전트는 하나의 작업을 끝내면 즉시 다음 작업을 시작합니다. 멈추는 조건이 없기 때문에, 에이전트 프롬프트에서 "문제를 작은 조각으로 나누고, 진행 상황을 추적하며, 완벽해질 때까지 계속하라"고 지시합니다. 한 에이전트가 실수로 `pkill -9 bash`를 실행해 자기 자신을 종료시킨 일화도 있었다고 합니다.

### 2. 병렬 협업: Git 기반의 단순한 동기화

16개 에이전트의 협업 메커니즘은 놀라울 만큼 단순합니다.

각 에이전트는 작업을 시작할 때 `current_tasks/` 디렉토리에 텍스트 파일을 생성해 해당 작업을 "잠급니다."

예를 들어 한 에이전트가 `current_tasks/parse_if_statement.txt`를 생성하면, 다른 에이전트는 이 작업을 건드리지 않습니다. 두 에이전트가 동시에 같은 작업을 잠그려 하면, Git의 머지 충돌이 자연스럽게 중재자 역할을 합니다.

작업을 마친 에이전트는 upstream에서 pull하고, 다른 에이전트의 변경사항을 머지한 뒤, 자신의 변경사항을 push하고 잠금을 해제합니다.

별도의 오케스트레이션 에이전트나 복잡한 통신 프로토콜이 없습니다.

Git이라는 이미 검증된 도구 위에서 최소한의 규칙만으로 협업이 이루어진 것입니다.

### 3. 테스트 하네스: AI를 위한 테스트 설계

Carlini가 가장 강조한 교훈은 "테스트를 AI의 관점에서 설계해야 한다"는 것이었습니다. 사람을 위한 테스트와 AI를 위한 테스트는 다릅니다.

**컨텍스트 오염 방지가 핵심입니다.** 테스트 하네스가 수천 줄의 로그를 출력하면 AI의 컨텍스트 윈도우를 잡아먹습니다. 대신 핵심 요약만 출력하고, 상세 로그는 파일에 저장합니다. 에러가 발생하면 "ERROR"라는 단어와 원인을 같은 줄에 써서 grep으로 쉽게 찾을 수 있게 했습니다.

**시간 감각 부재를 보완해야 합니다.** Claude는 시간 개념이 없어서, 방치하면 몇 시간이고 테스트만 돌립니다. 이를 해결하기 위해 `--fast` 옵션으로 1%에서 10% 랜덤 샘플만 실행하되, 에이전트별로 결정적(deterministic)이면서 VM 간에는 랜덤한 서브샘플을 사용했습니다. 모든 파일을 커버하면서도 각 에이전트가 회귀(regression)를 정확히 식별할 수 있는 구조입니다.

**자기 기록을 유지하게 해야 합니다.** 각 에이전트는 새 컨테이너에 떨어질 때마다 맥락 없이 시작합니다. 이를 돕기 위해 README와 진행 상황 파일을 자주 업데이트하도록 지시했습니다. 에이전트가 막히면 실패한 접근법과 남은 작업을 문서화하는 습관도 생겼습니다.

## 난관과 돌파: 리눅스 커널이라는 벽

독립적인 테스트 케이스가 많을 때 병렬화는 쉽습니다. 각 에이전트가 다른 실패 테스트를 선택하면 됩니다.

테스트 수트가 99% 통과율에 도달한 뒤에는 각 에이전트가 서로 다른 오픈소스 프로젝트(SQLite, Redis, libjpeg, Lua 등)를 컴파일하는 방식으로 분업했습니다.

하지만 리눅스 커널은 달랐습니다. 커널 컴파일은 하나의 거대한 작업이기 때문에, 16개 에이전트가 모두 같은 버그에 부딪혀서 같은 수정을 시도하고, 서로의 변경사항을 덮어쓰는 상황이 벌어졌습니다. 16개 에이전트를 돌리나 1개를 돌리나 차이가 없는 상태였습니다.

Carlini는 **GCC를 "정답 오라클"로 활용하는 전략**을 고안했습니다. 커널 파일 대부분을 GCC로 컴파일하고, 일부만 CCC로 컴파일합니다. 커널이 작동하면 CCC 담당 파일에는 문제가 없는 것이고, 커널이 깨지면 CCC 파일 안에 버그가 있다는 뜻입니다.

범위를 더 좁히려면 CCC 파일 일부를 다시 GCC로 바꿔가며 확인합니다.

이 방식으로 하나의 거대한 문제가 여러 개의 작고 독립적인 문제로 분해되었고,

각 에이전트가 서로 다른 파일의 버그를 병렬로 추적할 수 있게 되었습니다.

이 전략은 개발자라면 친숙한 **이분 탐색(bisect)** 기법의 변형입니다.

다만 사람이 아닌 AI 에이전트 16개가 동시에 수행했다는 점이 다릅니다.

## 역할 전문화: 모든 에이전트가 같은 일을 하지 않는다

병렬성의 또 다른 이점은 **전문화**입니다. 모든 에이전트가 기능 구현에만 매달리는 것이 아니라, 서로 다른 역할을 맡았습니다.

| 역할 | 담당 업무 |
| --- | --- |
| 기능 구현 에이전트 | 파서, 코드 제너레이터 등 핵심 기능 개발 |
| 중복 제거 에이전트 | 코드베이스에서 중복 구현된 기능 통합 |
| 성능 최적화 에이전트 | 컴파일러 자체의 실행 속도 개선 |
| 출력 최적화 에이전트 | 컴파일된 바이너리의 효율성 개선 |
| 코드 품질 에이전트 | Rust 개발자 관점에서 구조적 개선 제안 |
| 문서화 에이전트 | README, 아키텍처 문서 유지보수 |

LLM이 작성하는 코드는 기존 기능을 재구현하는 경향이 강합니다.

중복 제거 전담 에이전트를 둔 것은 이 약점을 보완하기 위한 설계입니다. 이런 역할 분화는 인간 개발팀의 구조와 닮아 있습니다.

시니어 개발자가 아키텍처를 잡고, 주니어가 구현하고, QA가 검증하고, 테크라이터가 문서를 쓰는 것처럼요.

## 한계: AI가 아직 넘지 못한 선

Carlini는 이 프로젝트의 한계를 솔직하게 밝혔습니다. 결과물의 인상적인 면만큼이나 한계를 이해하는 것이 중요합니다.

**생성 코드의 효율성 문제가 심각합니다.** CCC가 모든 최적화를 켜고 생성한 바이너리가, GCC가 모든 최적화를 끈 상태에서 생성한 바이너리보다 느립니다. 한 평론가의 표현을 빌리면 "문법은 맞지만 중학생 독후감 수준으로 읽히는 에세이"와 비슷한 상태입니다.

**16비트 x86 코드 제너레이터를 구현하지 못했습니다.** 리눅스를 리얼 모드에서 부팅하려면 16비트 코드가 필요한데, CCC가 생성하는 16비트 코드는 60KB를 넘겨 리눅스의 32KB 제한을 초과합니다. 결국 이 단계에서는 GCC를 호출하는 방식으로 우회했습니다.

ARM과 RISC-V에서는 CCC 단독으로 전체 컴파일이 가능합니다.

**코드베이스가 커질수록 문제가 심화됩니다.** 약 10만 줄을 넘어서자, 새 기능을 추가하거나 버그를 수정할 때마다 기존 기능이 깨지는 일이 잦아졌습니다. 이는 인간 개발팀에서도 흔히 겪는 문제이지만,

AI 에이전트에서는 "전체 코드베이스를 이해하는 능력의 한계"가 더 빠르게 드러났습니다.

**Rust 코드 품질은 "합리적"이지만 전문가 수준은 아닙니다.** Carlini는 이를 "현재 모델 기준으로 자율적 에이전트 코딩의 실질적 한계선"이라고 평가했습니다.

## 모범사례/패턴 비교

이 실험에서 드러난 에이전트 팀 설계 원칙을 정리하면 다음과 같습니다.

| 설계 원칙 | 장점 | 주의점 |
| --- | --- | --- |
| 무한 루프 하네스 | 사람 없이 연속 작업 가능 | 에이전트가 예상치 못한 명령으로 자기를 종료할 수 있음 |
| Git 기반 락 파일 동기화 | 기존 인프라 활용, 구현 단순 | 머지 충돌이 빈번하지만 에이전트가 해결 가능 |
| 오라클 비교 테스트 | 거대 작업을 병렬화 가능한 단위로 분해 | 신뢰할 수 있는 기준 컴파일러(GCC) 필요 |
| 역할 전문화 | 코드 품질, 문서화 등 부차적 작업도 병행 | 역할 간 경계 설정이 모호하면 중복 작업 발생 |
| 컨텍스트 친화적 로그 | AI의 판단 정확도 향상 | 로그 설계에 별도 노력 필요 |
| 랜덤 서브샘플 테스트 | 속도와 커버리지 균형 | 전수 테스트가 필요한 최종 단계에서는 한계 |

## 개발자에게 주는 시사점

이 실험을 "AI가 개발자를 대체한다"는 이야기로 읽으면 핵심을 놓칩니다. Carlini 자신이 강조했듯,

에이전트가 잘 작동한 이유는 테스트 하네스와 환경 설계가 정교했기 때문입니다. 에이전트는 테스트의 품질만큼만 똑똑합니다.

이것이 의미하는 바는 명확합니다.

**개발자의 핵심 역량이 "코드를 작성하는 능력"에서 "AI가 올바르게 작동할 수 있는 시스템을 설계하는 능력"으로 이동하고 있다는 것입니다.**

구체적으로는 아키텍처 설계, 테스트 수트 구축, 성공 기준 정의, 검증 파이프라인 설계 같은 역량이 더 중요해집니다.

Carlini는 과거 침투 테스트(penetration testing) 분야에서 일했던 경험을 언급하며 우려도 표했습니다.

"개발자가 직접 검증하지 않은 소프트웨어가 배포되는 상황은 심각한 우려를 낳는다"는 것입니다.

테스트가 통과한다고 작업이 끝난 것은 아니라는 점,

자율 개발에는 새로운 차원의 검증이 필요하다는 점을 잊지 말아야 합니다.

## 마치며

- AI 에이전트 팀은 단순한 코파일럿의 확장이 아니라, 소프트웨어 개발의 단위를 "작업(task)"에서 "프로젝트(project)"로 바꾸는 패러다임 전환입니다.
- 에이전트의 성능은 모델의 지능이 아니라 테스트 환경의 품질에 의해 결정되며, "검증 엔지니어링"이 핵심 역량으로 부상하고 있습니다.
- 실전 팁: 지금 진행 중인 프로젝트의 테스트 수트를 "AI가 이 테스트 결과만 보고 다음에 뭘 해야 할지 판단할 수 있는가?"라는 기준으로 점검해보세요.
