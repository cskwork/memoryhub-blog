우리 모두가 MCP를 잘못 사용하고 있었다는 사실이 밝혀졌습니다.

현재 대부분의 에이전트는 MCP의 "도구"를 LLM에 직접 노출하는 방식으로 사용합니다.

하지만 우리는 다른 방법을 시도했습니다. MCP 도구를 TypeScript API로 변환한 다음, LLM에게 이 API를 호출하는 코드를 작성하도록 요청한 것입니다.

결과는 놀라웠습니다.

도구를 직접 제공하는 대신 TypeScript API로 제공했을 때, 에이전트가 훨씬 더 많고 복잡한 도구를 처리할 수 있었습니다. 아마도 LLM의 학습 데이터에는 실제 TypeScript 코드가 엄청나게 많지만, 도구 호출의 인위적인 예시는 적기 때문일 것입니다.

이 접근 방식은 특히 에이전트가 여러 호출을 연결해야 할 때 빛을 발합니다. 기존 방식에서는 각 도구 호출의 출력이 LLM의 신경망을 거쳐 다음 호출의 입력으로 단순히 복사되어야 하므로, 시간과 에너지, 토큰을 낭비합니다. 하지만 LLM이 코드를 작성할 수 있다면 이 모든 과정을 건너뛰고 필요한 최종 결과만 읽어올 수 있습니다.

요약하자면, LLM은 MCP를 직접 호출하는 것보다 MCP를 호출하는 코드를 작성하는 데 더 뛰어납니다.

## MCP란 무엇인가?

생소한 분들을 위해 설명하자면, 모델 컨텍스트 프로토콜(Model Context Protocol)은 AI 에이전트에게 외부 도구에 대한 접근 권한을 부여하는 표준 프로토콜입니다. 단순히 대화만 하는 것이 아니라 직접 작업을 수행할 수 있게 해줍니다.

다른 관점에서 보면, MCP는 다음을 통합적으로 제공하는 방법입니다:

- 무언가를 수행하기 위한 API 노출
- LLM이 이해하는 데 필요한 문서
- 대역 외에서 처리되는 인증

MCP는 2025년 내내 AI 에이전트의 기능을 크게 확장하면서 큰 주목을 받아왔습니다.

MCP 서버가 노출하는 "API"는 일련의 "도구"로 표현됩니다. 각 도구는 본질적으로 원격 프로시저 호출(RPC) 함수입니다. 매개변수와 함께 호출되면 응답을 반환합니다. 대부분의 최신 LLM은 "도구"를 사용할 수 있는 기능(때로는 "함수 호출"이라고도 함)을 갖추고 있습니다. 즉, 도구를 호출하고자 할 때 특정 형식으로 텍스트를 출력하도록 훈련되어 있습니다. LLM을 호출하는 프로그램은 이 형식을 인식하고 지정된 대로 도구를 호출한 다음, 결과를 다시 LLM에 입력으로 전달합니다.

## 도구 호출의 구조

내부적으로 LLM은 출력을 나타내는 "토큰" 스트림을 생성합니다. 토큰은 단어, 음절, 구두점 또는 기타 텍스트 구성 요소를 나타낼 수 있습니다.

하지만 도구 호출에는 텍스트와 동등한 것이 없는 토큰이 포함됩니다. LLM은 "다음은 도구 호출로 해석되어야 한다"는 의미의 특수 토큰과 "도구 호출의 끝"을 의미하는 또 다른 특수 토큰을 출력할 수 있도록 훈련(또는 더 자주 파인튜닝)됩니다. 이 두 토큰 사이에 LLM은 일반적으로 호출을 설명하는 JSON 메시지에 해당하는 토큰을 작성합니다.

예를 들어, 날씨 정보를 제공하는 MCP 서버에 에이전트를 연결하고 텍사스 오스틴의 날씨를 물어보면, LLM은 내부적으로 다음과 같은 출력을 생성할 수 있습니다. 여기서 `<|`와 `|>` 사이의 단어는 특수 토큰을 나타내지만, 실제로는 텍스트를 나타내지 않습니다. 이는 설명을 위한 것입니다.

```
텍사스 오스틴의 날씨를 알아보기 위해 날씨 MCP 서버를 사용하겠습니다.

<|tool_call|>
{
  "name": "get_current_weather",
  "arguments": {
    "location": "Austin, TX, USA"
  }
}
<|end_tool_call|>
```

출력에서 이러한 특수 토큰을 발견하면, LLM의 하네스는 이 시퀀스를 도구 호출로 해석합니다. 종료 토큰을 확인한 후 하네스는 LLM 실행을 일시 중지합니다. JSON 메시지를 파싱하고 구조화된 API 결과의 별도 구성 요소로 반환합니다. LLM API를 호출하는 에이전트는 도구 호출을 확인하고 관련 MCP 서버를 호출한 다음 결과를 LLM API로 다시 보냅니다. 그러면 LLM의 하네스는 또 다른 특수 토큰 세트를 사용하여 결과를 LLM에 다시 전달합니다:

```
<|tool_result|>
{
  "location": "Austin, TX, USA",
  "temperature": 93,
  "unit": "fahrenheit",
  "conditions": "sunny"
}
<|end_tool_result|>
```

LLM은 사용자의 입력을 읽는 것과 똑같은 방식으로 이러한 토큰을 읽습니다. 단, 사용자는 이러한 특수 토큰을 생성할 수 없으므로 LLM은 이것이 도구 호출의 결과임을 알 수 있습니다. 그런 다음 LLM은 정상적으로 출력을 계속 생성합니다.

LLM마다 도구 호출에 다른 형식을 사용할 수 있지만, 기본 아이디어는 이와 같습니다.

## 무엇이 문제인가?

도구 호출에 사용되는 특수 토큰은 LLM이 실제 환경에서 본 적이 없는 것들입니다. 합성 학습 데이터를 기반으로 도구를 사용하도록 특별히 훈련되어야 합니다. 그래서 항상 잘하는 것은 아닙니다. LLM에 너무 많은 도구나 지나치게 복잡한 도구를 제공하면 올바른 도구를 선택하거나 올바르게 사용하는 데 어려움을 겪을 수 있습니다. 그 결과, MCP 서버 설계자들은 개발자에게 노출하는 기존 API에 비해 크게 단순화된 API를 제공하도록 권장됩니다.

한편, LLM은 코드 작성에 정말 능숙해지고 있습니다. 사실, 개발자에게 일반적으로 노출되는 완전하고 복잡한 API를 대상으로 코드를 작성하라는 요청을 받은 LLM은 큰 어려움 없이 처리하는 것 같습니다. 그렇다면 왜 MCP 인터페이스는 "단순화"해야 할까요? 코드 작성과 도구 호출은 거의 같은 일인데, LLM은 한 가지를 다른 것보다 훨씬 잘하는 것 같습니다.

답은 간단합니다. LLM은 많은 코드를 보았습니다. "도구 호출"은 많이 보지 못했습니다. 사실, LLM이 본 도구 호출은 아마도 LLM 자체 개발자들이 훈련을 위해 구성한 인위적인 학습 세트에 국한되었을 것입니다. 반면에 수백만 개의 오픈 소스 프로젝트에서 실제 코드를 보았습니다.

도구 호출로 LLM에게 작업을 수행하게 하는 것은 셰익스피어에게 한 달간의 중국어 수업을 시킨 후 중국어로 희곡을 쓰라고 하는 것과 같습니다. 그의 최고 작품이 나올 수는 없습니다.

## 하지만 MCP는 여전히 유용합니다. 통일성 때문에

MCP는 도구 호출을 위해 설계되었지만, 실제로 그렇게 사용할 필요는 없습니다.

MCP 서버가 노출하는 "도구"는 실제로는 첨부된 문서가 있는 RPC 인터페이스일 뿐입니다. 이를 도구로 제공할 필요는 없습니다. 도구를 가져와서 프로그래밍 언어 API로 변환할 수 있습니다.

하지만 프로그래밍 언어 API가 이미 독립적으로 존재하는데 왜 그렇게 할까요? 거의 모든 MCP 서버는 기존의 전통적인 API를 감싸는 래퍼일 뿐입니다. 왜 그 API를 노출하지 않나요?

MCP는 실제로 매우 유용한 다른 일을 합니다. API에 연결하고 배우는 통일된 방법을 제공합니다.

AI 에이전트는 특정 MCP 서버에 대해 에이전트 개발자가 전혀 들어본 적이 없고, MCP 서버 개발자도 특정 에이전트에 대해 전혀 들어본 적이 없더라도 MCP 서버를 사용할 수 있습니다. 과거의 전통적인 API에서는 이런 일이 거의 없었습니다. 일반적으로 클라이언트 개발자는 항상 자신이 코딩하는 API가 정확히 무엇인지 알고 있었습니다. 그 결과, 모든 API는 기본 연결, 인증, 문서화와 같은 작업을 조금씩 다르게 수행할 수 있었습니다.

이러한 통일성은 AI 에이전트가 코드를 작성할 때도 유용합니다. AI 에이전트가 우리가 제공하는 도구에만 접근할 수 있도록 샌드박스에서 실행되기를 원합니다. MCP는 AI 코드와 독립적으로 표준 방식으로 연결과 인증을 처리함으로써 에이전트 프레임워크가 이를 구현할 수 있게 합니다. 또한 AI가 문서를 찾기 위해 인터넷을 검색할 필요가 없습니다. MCP는 프로토콜에서 직접 문서를 제공합니다.

## 그렇다면 어떻게 작동할까요?

우리는 이미 Cloudflare Agents SDK를 확장하여 이 새로운 모델을 지원합니다!

예를 들어, ai-sdk로 구축한 앱이 다음과 같다고 가정해 보겠습니다:

```
const stream = streamText({
  model: openai("gpt-5"),
  system: "You are a helpful assistant",
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ],
  tools: {
    // 도구 정의 
  }
})
```

`codemode` 헬퍼로 도구와 프롬프트를 래핑하여 앱에서 사용할 수 있습니다:

```
import { codemode } from "agents/codemode/ai";

const {system, tools} = codemode({
  system: "You are a helpful assistant",
  tools: {
    // 도구 정의 
  },
  // ...설정
})

const stream = streamText({
  model: openai("gpt-5"),
  system,
  tools,
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ]
})
```

이 변경으로 앱은 이제 정의한 도구(MCP 서버 포함)를 호출하는 코드를 생성하고 실행하기 시작합니다. 가까운 미래에 다른 라이브러리에 대한 변형을 소개할 예정입니다. 자세한 내용과 예시는 문서를 참조하세요.

## MCP를 TypeScript로 변환

"코드 모드"에서 MCP 서버에 연결하면, Agents SDK는 MCP 서버의 스키마를 가져와서 스키마를 기반으로 한 문서 주석과 함께 TypeScript API로 변환합니다.

예를 들어, `https://gitmcp.io/cloudflare/agents`의 MCP 서버에 연결하면 다음과 같은 TypeScript 정의가 생성됩니다:

```
interface FetchAgentsDocumentationInput {
  [k: string]: unknown;
}
interface FetchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsDocumentationInput {
  /**
   * 관련 문서를 찾기 위한 검색 쿼리
   */
  query: string;
}
interface SearchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsCodeInput {
  /**
   * 관련 코드 파일을 찾기 위한 검색 쿼리
   */
  query: string;
  /**
   * 검색할 페이지 번호 (1부터 시작). 각 페이지는 30개의 결과를 포함합니다.
   */
  page?: number;
}
interface SearchAgentsCodeOutput {
  [key: string]: any;
}

interface FetchGenericUrlContentInput {
  /**
   * 가져올 문서 또는 페이지의 URL
   */
  url: string;
}
interface FetchGenericUrlContentOutput {
  [key: string]: any;
}

declare const codemode: {
  /**
   * GitHub 저장소 cloudflare/agents에서 전체 문서 파일을 가져옵니다.
   * 일반적인 질문에 유용합니다. cloudflare/agents에 대해 질문받으면
   * 항상 이 도구를 먼저 호출하세요.
   */
  fetch_agents_documentation: (
    input: FetchAgentsDocumentationInput
  ) => Promise<FetchAgentsDocumentationOutput>;

  /**
   * GitHub 저장소 cloudflare/agents에서 가져온 문서 내에서
   * 의미론적으로 검색합니다. 특정 쿼리에 유용합니다.
   */
  search_agents_documentation: (
    input: SearchAgentsDocumentationInput
  ) => Promise<SearchAgentsDocumentationOutput>;

  /**
   * GitHub 검색 API(정확히 일치)를 사용하여 GitHub 저장소
   * "cloudflare/agents" 내에서 코드를 검색합니다.
   * 관련이 있을 경우 추가로 쿼리할 수 있는 일치하는 파일을 반환합니다.
   */
  search_agents_code: (
    input: SearchAgentsCodeInput
  ) => Promise<SearchAgentsCodeOutput>;

  /**
   * robots.txt 규칙을 준수하여 모든 절대 URL에서 콘텐츠를 가져오는
   * 범용 도구입니다. 이전에 가져온 문서에서 언급된 참조 URL
   * (절대 URL)을 검색하는 데 사용하세요.
   */
  fetch_generic_url_content: (
    input: FetchGenericUrlContentInput
  ) => Promise<FetchGenericUrlContentOutput>;
};
```

이 TypeScript는 에이전트의 컨텍스트에 로드됩니다. 현재는 전체 API가 로드되지만, 향후 개선 사항으로 에이전트가 API를 더 동적으로 검색하고 탐색할 수 있게 할 수 있습니다. 마치 에이전트 코딩 어시스턴트가 하는 것처럼 말입니다.

## 샌드박스에서 코드 실행

연결된 모든 MCP 서버의 모든 도구를 제공받는 대신, 에이전트는 TypeScript 코드를 실행하는 단 하나의 도구만 제공받습니다.

그런 다음 코드는 안전한 샌드박스에서 실행됩니다. 샌드박스는 인터넷으로부터 완전히 격리되어 있습니다. 외부 세계에 대한 유일한 접근은 연결된 MCP 서버를 나타내는 TypeScript API를 통해서입니다.

이러한 API는 에이전트 루프로 다시 호출하는 RPC 호출로 지원됩니다. 거기서 Agents SDK는 호출을 적절한 MCP 서버로 전달합니다.

샌드박스 코드는 명백한 방식으로 에이전트에 결과를 반환합니다. 바로 `console.log()`를 호출하는 것입니다. 스크립트가 완료되면 모든 출력 로그가 에이전트로 다시 전달됩니다.

## 동적 Worker 로딩: 여기엔 컨테이너가 없습니다

이 새로운 접근 방식은 임의의 코드를 실행할 수 있는 안전한 샌드박스에 대한 접근이 필요합니다. 그렇다면 어디서 찾을 수 있을까요? 컨테이너를 실행해야 할까요? 비용이 많이 들까요?

아닙니다. 컨테이너는 없습니다. 훨씬 더 나은 것이 있습니다. 바로 아이솔레이트(isolates)입니다.

Cloudflare Workers 플랫폼은 항상 V8 아이솔레이트, 즉 V8 JavaScript 엔진으로 구동되는 격리된 JavaScript 런타임을 기반으로 했습니다.

아이솔레이트는 컨테이너보다 훨씬 가볍습니다. 아이솔레이트는 단 몇 메가바이트의 메모리만 사용하여 몇 밀리초 만에 시작할 수 있습니다.

아이솔레이트가 너무 빠르기 때문에 에이전트가 실행하는 모든 코드 조각마다 새로운 아이솔레이트를 만들 수 있습니다. 재사용할 필요가 없습니다. 사전 준비할 필요도 없습니다. 필요할 때 만들고, 코드를 실행하고, 버리면 됩니다. 모든 것이 너무 빨라서 오버헤드가 무시할 만합니다. 마치 코드를 직접 `eval()`하는 것과 거의 같습니다. 하지만 보안은 유지됩니다.

## Worker Loader API

하지만 지금까지는 Worker가 임의의 코드를 포함하는 아이솔레이트를 직접 로드할 방법이 없었습니다. 모든 Worker 코드는 Cloudflare API를 통해 업로드되어야 했고, 그러면 어디서나 실행될 수 있도록 전역적으로 배포되었습니다. 하지만 에이전트에는 그렇게 하고 싶지 않습니다. 코드가 에이전트가 있는 곳에서 바로 실행되기를 원합니다.

이를 위해 Workers 플랫폼에 새로운 API인 Worker Loader API를 추가했습니다. 이를 통해 Worker 코드를 온디맨드로 로드할 수 있습니다. 다음과 같이 생겼습니다:

```
// 주어진 ID로 Worker를 가져옵니다. 해당 Worker가 아직 없으면 생성합니다.
let worker = env.LOADER.get(id, async () => {
  // Worker가 아직 존재하지 않으면 이 콜백이 호출되어 코드를 가져옵니다.

  return {
    compatibilityDate: "2025-06-01",

    // Worker의 코드(모듈 파일) 지정
    mainModule: "foo.js",
    modules: {
      "foo.js":
        "export default {\n" +
        "  fetch(req, env, ctx) { return new Response('Hello'); }\n" +
        "}\n",
    },

    // 동적 Worker의 환경(`env`) 지정
    env: {
      // 기본 직렬화 가능한 데이터 타입을 포함할 수 있습니다...
      SOME_NUMBER: 123,

      // ... 그리고 새로운 `ctx.exports` 루프백 바인딩 API를 사용하여
      // 부모 Worker의 내보낸 RPC 인터페이스에 대한 바인딩
      SOME_RPC_BINDING: ctx.exports.MyBindingImpl({props})
    },

    // Worker의 `fetch()` 및 `connect()`를 부모 Worker를 통해
    // 프록시하도록 리디렉션하여 모든 인터넷 접근을 모니터링하거나 필터링합니다.
    // `null`을 전달하여 인터넷 접근을 완전히 차단할 수도 있습니다.
    globalOutbound: ctx.exports.OutboundProxy({props}),
  };
});

// 이제 Worker의 엔트리포인트를 가져와서 요청을 보낼 수 있습니다.
let defaultEntrypoint = worker.getEntrypoint();
await defaultEntrypoint.fetch("http://example.com");

// 기본이 아닌 엔트리포인트도 가져올 수 있으며,
// 엔트리포인트에 전달할 `ctx.props` 값을 지정할 수 있습니다.
let someEntrypoint = worker.getEntrypoint("SomeEntrypointClass", {
  props: {someProp: 123}
});
```

Wrangler를 사용하여 로컬에서 workerd를 실행할 때 이 API를 지금 바로 사용할 수 있으며(문서 확인), 프로덕션에서 사용하려면 베타 액세스에 등록할 수 있습니다.

## Workers는 더 나은 샌드박스입니다

Workers의 설계는 특히 이 사용 사례에서 샌드박싱에 유난히 뛰어납니다. 몇 가지 이유가 있습니다:

### 더 빠르고, 저렴하고, 일회용 샌드박스

Workers 플랫폼은 컨테이너 대신 아이솔레이트를 사용합니다. 아이솔레이트는 훨씬 가볍고 시작 속도가 빠릅니다. 새로운 아이솔레이트를 시작하는 데 단 몇 밀리초가 걸리며, 너무 저렴해서 에이전트가 생성하는 모든 코드 조각마다 새로운 아이솔레이트를 만들 수 있습니다. 재사용을 위해 아이솔레이트를 풀링하거나 사전 준비하는 것에 대해 걱정할 필요가 없습니다.

Worker Loader API에 대한 가격 책정은 아직 확정하지 않았지만, 아이솔레이트를 기반으로 하기 때문에 컨테이너 기반 솔루션보다 훨씬 저렴한 비용으로 제공할 수 있을 것입니다.

### 기본적으로 격리되지만 바인딩으로 연결

Workers는 격리를 처리하는 데 훨씬 더 뛰어납니다.

코드 모드에서는 샌드박스 워커가 인터넷과 통신하는 것을 금지합니다. 전역 `fetch()` 및 `connect()` 함수는 오류를 발생시킵니다.

하지만 대부분의 플랫폼에서는 이것이 문제가 됩니다. 대부분의 플랫폼에서 개인 리소스에 접근하는 방법은 일반적인 네트워크 접근으로 시작하는 것입니다. 그런 다음 해당 네트워크 접근을 사용하여 특정 서비스에 요청을 보내고 일종의 API 키를 전달하여 개인 접근을 승인합니다.

하지만 Workers는 항상 더 나은 답을 가지고 있었습니다. Workers에서 "환경"(env 객체)은 단순히 문자열만 포함하는 것이 아니라 "바인딩"이라고도 하는 라이브 객체를 포함합니다. 이러한 객체는 일반적인 네트워크 요청 없이 개인 리소스에 직접 접근할 수 있습니다.

코드 모드에서는 샌드박스에 연결된 MCP 서버를 나타내는 바인딩에 대한 접근 권한을 부여합니다. 따라서 에이전트는 일반적인 네트워크 접근 없이도 해당 MCP 서버에 구체적으로 접근할 수 있습니다.

바인딩을 통해 접근을 제한하는 것이 네트워크 수준 필터링이나 HTTP 프록시를 통해 하는 것보다 훨씬 깔끔합니다. 필터링은 LLM과 감독자 모두에게 어렵습니다. 경계가 종종 불명확하기 때문입니다. 감독자는 API와 통신하는 데 합법적으로 필요한 트래픽을 정확히 식별하는 데 어려움을 겪을 수 있습니다. 한편, LLM은 어떤 종류의 요청이 차단될지 추측하는 데 어려움을 겪을 수 있습니다. 바인딩 접근 방식을 사용하면 명확하게 정의됩니다. 바인딩은 JavaScript 인터페이스를 제공하며, 해당 인터페이스를 사용할 수 있습니다. 이 방식이 훨씬 낫습니다.

### API 키 유출 없음

바인딩의 추가적인 이점은 API 키를 숨긴다는 것입니다. 바인딩 자체가 MCP 서버에 대한 이미 인증된 클라이언트 인터페이스를 제공합니다. 여기서 이루어지는 모든 호출은 먼저 에이전트 감독자로 이동하며, 감독자는 액세스 토큰을 보유하고 MCP로 전송되는 요청에 추가합니다.

이는 AI가 키를 유출하는 코드를 작성할 수 없음을 의미하며, 오늘날 AI가 작성한 코드에서 흔히 볼 수 있는 보안 문제를 해결합니다.
