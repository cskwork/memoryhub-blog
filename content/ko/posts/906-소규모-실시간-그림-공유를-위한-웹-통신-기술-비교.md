선생님 1명과 학생 최대 12명이 참여하는 수업에서, 선생님이 캔버스에 그린 그림을 거의 **실시간(****지연 1****초** **이내)**으로 모든 학생에게 공유하는 웹 애플리케이션을 만들려고 합니다. 기본적으로 **그림** **그리기** **권한은** **선생님**에게 있지만, 경우에 따라 **학생이** **그림을** **그려** **선생님에게** **전달**하기도 합니다. 전체 접속자는 **1** **대 12**의 소규모이며, **실시간성**이 매우 중요합니다 (1초 이내 반응). 이 시나리오에서 사용할 수 있는 웹 통신 기술로 **WebSocket**, **WebRTC**, **Server-Sent Events (SSE)**, **HTTP Polling(****폴링)** 등이 거론되는데, 각각의 **장단점**과 **구현** **시** **고려사항**을 비교해보겠습니다. 아래 표는 이러한 기술들을 주요 측면에서 비교한 것입니다:

## WebSocket vs WebRTC vs SSE vs HTTP Polling비교

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **구분** | **WebSocket** (웹소켓) | **WebRTC** (웹 RTC) | **Server-Sent Events** (SSE) | **HTTP Polling** (폴링) |
|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| **통신** **방식** | - **지속적** **서버-****클라이언트** **연결** (TCP 기반): 초기 HTTP 핸드셰이크 후 전용 WebSocket 프로토콜로 업그레이드하여 **중앙** **서버를** **통해** 양방향 메시지 교환[[1]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%ED%86%B5%EC%8B%A0%EC%97%90%EC%84%9C%20%EB%B9%A0%EB%A5%B4%EA%B3%A0%20%ED%9A%A8%EC%9C%A8%EC%A0%81%EC%9D%B8%20%EC%A0%84%EC%86%A1%EC%9D%84%20%EC%A7%80%EC%9B%90%ED%95%A9%EB%8B%88%EB%8B%A4). 한 번 연결되면 동일 세션에 다수 메시지를 주고받음 (풀-이중 통신). | - **피어-****투-****피어(P2P)** **직통** **연결**: 브라우저들 간 직접 데이터 교환. 주로 **UDP** **기반** 미디어 스트림 (영상/음성) + **SCTP** **기반** **데이터** **채널** 사용[[2]](https://getstream.io/blog/webrtc-websockets/#:~:text=WebRTC%20WebSockets%20Architecture%20Peer,between%20a%20client%20and%20server)[[3]](https://getstream.io/blog/webrtc-websockets/#:~:text=getUserMedia,type%20of%20media%20they%20want). 중앙 서버를 통하지 않아도 되지만, **초기** **시그널링**에 서버 사용.<br>- 기본 **메시** **교차** **연결**: n명의 피어는 최대 *n(n-1)/2*개의 연결 형성 (예: 10명일 때 45개 연결) → 참가자 많을수록 P2P 복잡도 증가[[4]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=In%20a%20large%20group%2C%20however%2C,and%20almost%20impossible%20to%20debug). | - **서버→****클라이언트** **단방향** **스트리밍**: **기존 HTTP** 연결을 유지해 서버가 일방적으로 데이터 푸시[[5]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%EC%9E%AC%EC%97%B0%EA%B2%B0%EC%9D%84%20%EC%8B%9C%EB%8F%84%ED%95%98%EB%8A%94%20%EA%B8%B0%EB%8A%A5%EC%9D%B4%20%EB%82%B4%EC%9E%A5%EB%90%98%EC%96%B4%20%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4). text/event-stream MIME 타입으로 지속적인 응답 스트림을 보내는 방식 (클라이언트는 EventSource API로 수신).<br>- **HTTP** **기반** **프로토콜**: 별도 업그레이드 없이 작동하며, HTTP/1.1 또는 HTTP/2의 **장기** **연결** 기능 활용. | - **주기적 HTTP** **요청**: 클라이언트가 일정 주기로 서버에 새로운 업데이트가 있는지 요청(polling)하거나, **Long Polling** 방식으로 서버가 데이터 준비될 때까지 요청을 지연시켰다가 응답[[6]](https://rxdb.info/articles/websockets-sse-polling-webrtc-webtransport.html#:~:text=client%20repeatedly%20requests%20data%20from,time%20technologies%20like%20WebSockets). 요청-응답 후 매번 새로운 연결 재시작. |
| **양방향** **데이터**<br>**전송** **지원** | - **양방향(full-duplex)** 지원: 서버와 클라이언트 **모두** **자유롭게** 데이터 전송 가능[[7]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%ED%86%B5%EC%8B%A0%EC%97%90%EC%84%9C%20%EB%B9%A0%EB%A5%B4%EA%B3%A0%20%ED%9A%A8%EC%9C%A8%EC%A0%81%EC%9D%B8%20%EC%A0%84%EC%86%A1%EC%9D%84%20%EC%A7%80%EC%9B%90%ED%95%A9%EB%8B%88%EB%8B%A4). 교사가 그림 그린 내용을 학생들에게 전송하고, 학생의 그림 피드백도 동일 채널로 서버 통해 전송 가능. | - **양방향 P2P** 지원: DataChannel 등을 통해 **클라이언트** **간** **직접** 실시간 데이터 교환 가능[[3]](https://getstream.io/blog/webrtc-websockets/#:~:text=getUserMedia,type%20of%20media%20they%20want). 선생님과 각 학생이 각각 P2P 연결 맺어 데이터 주고받을 수 있음. (다만 n명이면 P2P 연결 수 급증). | - **단방향**: **서버 →** **클라이언트** 전용. 클라이언트에서 서버로 보내는 데이터는 SSE로 보낼 수 없고, 별도 AJAX/페치 요청 등 사용 필요[[8]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Full). 이 시나리오에서 학생→선생님 전달은 SSE만으로 처리 어렵고 추가 채널 필요. | - **의사** **양방향**: 기본적으로 **클라이언트** **요청 ->** **서버** **응답** 형태의 반이중. 실시간 쌍방향을 구현하려면 클라이언트->서버는 폴링, 서버->클라이언트는 응답/긴응답 방식으로 에뮬레이트해야 함. 자연스러운 동시 양방향 상호작용은 어려움. |
| **지연 (****실시간성)** | - **낮은** **지연**: 초기 연결 후에는 **지속** **연결상태**에서 데이터를 바로 전송하므로 추가 핸드셰이크 없이 **즉각적** **전달** 가능[[9]](https://ably.com/blog/websockets-vs-sse#:~:text=,user%20realtime%20apps%20highly%20performant). 메시지에 HTTP 헤더 반복 없어서 **레이터시** **최소화**[[10]](https://ably.com/blog/websockets-vs-sse#:~:text=connection%20can%20handle%20a%20high,chat%20and%20live%20data%20updates). 실사용 테스트에서도 WebSocket이 **가장** **높은** **실시간** **성능**을 보임[[11]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Image%3A%20The%20performance%20of%20WebSockets,Sent%20Events). 거의 실시간에 가까운 (<0.1초 수준) 업데이트도 가능[[12]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Jakob%20Nielsen%2C%20a%20retired%20principal,than%20simply%20displaying%20the%20result)[[11]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Image%3A%20The%20performance%20of%20WebSockets,Sent%20Events). | - **아주** **낮은** **지연**: P2P 직통 연결 및 UDP 사용으로 패킷 손실 시 재전송 부담 적고, 미디어 스트림은 프로토콜이 지연 최소화 설계. 따라서 **오디오/****비디오** **등** **실시간** 스트림에 최적[[13]](https://getstream.io/blog/webrtc-websockets/#:~:text=WebRTC%20and%20WebSockets%20are%20among,and%20make%20communication%20more%20efficient). 그림 데이터 전송도 지연 자체는 매우 낮게 유지 가능. 다만 **초기** **연결** **설정**(SDP 교환, NAT 트래버설 등) 에 시간이 조금 들 수 있음. 또한 **동시** **피어** **수** **증가** **시** P2P mesh에서는 지연 제어 복잡. | - **낮은** **지연**: 서버에서 이벤트 발생 시 **즉시** **모든** **클라이언트로** **푸시** 가능하므로, 전송 자체는 실시간에 가까움. 1초 이내의 빈번한 업데이트도 SSE 스트림으로 가능. 단, **전송** **데이터가** **텍스트**이므로 바이너리 데이터인 그림은 인코딩 필요해 약간의 오버헤드와 지연 증가 요인. 그래도 작은 텍스트 이벤트 위주라면 지연은 WebSocket과 비슷하게 매우 작음. | - **비교적** **높음**: 폴링 주기를 촘촘히 설정하지 않으면 이벤트 발생 후 **다음** **요청** **때까지** **대기**해야 해서 지연 발생. 1초 주기로 폴링하면 평균 0.5초 정도 지연이 생기며, 주기를 줄이면 서버 부하 상승[[14]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). Long polling은 이벤트가 생기자마자 응답 보내 지연을 줄일 수 있지만, **응답** **후** **재연결** **시간**이 있어 연속 이벤트엔 불리. 전반적으로 다른 기술 대비 실시간성 떨어짐. |
| **데이터** **형식**<br>**및** **대역폭** | - **텍스트/****바이너리** **모두** **지원**: WebSocket은 **이진** **데이터** **프레임**을 지원하므로 그림의 **비트맵** **이미지** **데이터를** **그대로** **전송** 가능[[7]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%ED%86%B5%EC%8B%A0%EC%97%90%EC%84%9C%20%EB%B9%A0%EB%A5%B4%EA%B3%A0%20%ED%9A%A8%EC%9C%A8%EC%A0%81%EC%9D%B8%20%EC%A0%84%EC%86%A1%EC%9D%84%20%EC%A7%80%EC%9B%90%ED%95%A9%EB%8B%88%EB%8B%A4)[[15]](https://ably.com/blog/websockets-vs-sse#:~:text=the%20client%2C%20and%20both%20can,such%20as%20images%20and%20video). 추가 인코딩 불필요해 효율적.<br>- **오버헤드** **적음**: 연결 유지로 각 메시지에 HTTP 헤더가 붙지 않으며, **프레임** **단위** 통신으로 매우 작은 용량의 메시지도 효율적으로 다룸[[10]](https://ably.com/blog/websockets-vs-sse#:~:text=connection%20can%20handle%20a%20high,chat%20and%20live%20data%20updates). 그림을 자주 보내도 헤더 반복 전송이 없어 **대역폭** **효율** 높음. | - **미디어** **스트림** **최적화**: WebRTC는 영상/음성 등의 **연속** **스트림** **전송**에 특화. 대용량 **바이너리** **데이터**(예: 영상 프레임)를 UDP로 전송하며 네트워크 품질 따라 **대역폭** **조절** 가능. 그러나 **P2P** 구조에서는 동일 데이터를 참가자마다 각각 전송해야 함. 예를 들어 선생님이 12명에게 그림 전송 시 **동일** **이미지 12****회** **업로드**해야 하므로, **교사** **측** **업링크에** **부하** 큼. (SFU 서버 사용하면 하나 업로드 후 분배 가능하나, 그럴 바엔 WebSocket과 큰 차이 없음.) 따라서 간단한 그림 공유에서는 **대역폭** **대비** **비효율**일 수 있음. | - **텍스트** **기반** **전송**: **UTF-8** **텍스트** **스트림**만 지원하므로 이미지 바이너리를 보내려면 Base64 인코딩 등으로 텍스트화 해야 함[[16]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Data%20Type%20Support). 이로 인해 **추가 30%** **이상** **용량** **증가** 및 인코딩/디코딩 비용 발생. 그림을 빈번히 보낼 경우 SSE에서는 이 부분이 비효율.<br>- **방송** **효율성**: 서버는 각 클라이언트에 **동일한** **텍스트** **이벤트를** **각각** **전송**하지만, **HTTP/2** 환경에선 단일 연결 다중화로 어느 정도 완화 가능. 그래도 대량 이진 데이터보다는 작은 텍스트 이벤트 스트림에 적합. | - **HTTP** **헤더** **오버헤드**: 매 요청마다 HTTP 헤더 왕복 전송으로 **부가** **데이터량** **많음**. 빈번한 폴링 시 실제 유효 페이로드보다 헤더가 차지하는 대역폭 비율이 커져 **비효율적**[[14]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). <br>- **불필요한** **데이터** **전송**: 변화가 없어도 정기 요청마다 응답을 주고받아 **불필요한** **대역폭** **소비**[[17]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). 그림 데이터를 자주 보내면 동일한 이미지가 반복 전송되거나 변경 없는데도 요청 발생 가능. 전반적으로 소규모에는 가능해도, 실시간 대량 전송에는 부적합. |
| **서버** **구성**<br>**및** **구현** **난이도** | - **전용** **서버** **필요**: WebSocket을 처리할 **백엔드** **서버**(예: Node.js의 ws나 Socket.IO 라이브러리 등) 구축 필요[[18]](https://ably.com/blog/websockets-vs-sse#:~:text=To%20get%20started%20with%20WebSockets%2C,side%20WebSockets%20API). 서버는 다수의 지속 연결을 관리하도록 **이벤트** **루프** 기반 등으로 구현해야 함. 부하분산기나 리버스 프록시 사용 시 **WebSocket** **프로토콜** **지원** **설정** 필요 (HTTP Upgrade 지원)[[19]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=,load%20balancer%2C%20proxy%2C%20etc).<br>- **구현** **난이도**: 브라우저는 기본 WebSocket API 제공으로 비교적 쉽게 연결 가능하지만, **인증/****재연결/****확장** **처리** 등 추가 코딩 필요. Socket.IO 같은 라이브러리로 구현 편의 향상 가능. | - **복잡한** **인프라** **요구**: **시그널링** **서버**(초기 연결 협상용)와 **STUN/TURN** **서버**(P2P 경로 확보용) 필요[[20]](https://getstream.io/blog/webrtc-websockets/#:~:text=When%20users%20aren%27t%20on%20the,servers%20to%20enable%20IP%20access). 또한 13명이 모두 P2P로 연결하려면 **연결** **관리** **복잡성** 급증[[21]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=is%20essentially%20zero%2C%20so%20your,and%20almost%20impossible%20to%20debug). 일반적으로 WebRTC 다자간 통신엔 SFU/MCU **미디어** **서버**를 도입하는데, 이는 전문 솔루션(예: Janus, mediasoup 등)으로 구현 난이도 높음.<br>- **구현** **난이도**: WebRTC API 자체는 브라우저에 있지만, **피어** **연결** **수락/****관리,** **오류** **처리** 등이 어려움[[22]](https://www.designveloper.com/guide/webrtc-vs-websocket/#:~:text=,install%20an%20extra%20signaling%20server). P2P로만 구성 시 앱이 복잡해지고, 서버중계 구조로 쓰자니 굳이 WebRTC를 쓸 이점 감소. | - **구현** **용이**: SSE는 **HTTP** **응답** **스트림**만 생성하면 되어, 기존 웹 서버(예: Express 등)에서 Content-Type: text/event-stream으로 응답을 지속 열어두는 것으로 구현 간단[[23]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=3,%EC%8A%A4%ED%8A%B8%EB%A6%BC%20%EB%8D%B0%EC%9D%B4%ED%84%B0%EB%A5%BC%20%EB%B0%9B%EC%9D%84%20%EC%88%98%20%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4). 클라이언트도 브라우저 **EventSource API**로 쉽게 수신 가능. 특별한 프로토콜 업그레이드나 복잡한 핸드셰이크 불필요.<br>- **서버** **부하** **처리**: 각 클라이언트마다 **응답** **스트림** **커넥션을** **상시** **유지**하므로, 스레드/커넥션에 효율적인 **비동기** **서버**가 유리. HTTP/2 사용 시 단일 TCP 연결로 여러 SSE 채널 다중화 가능하나, 브라우저 구현 이슈 조금 존재[[24]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=,in%20older%20browsers%20or%20HTTP%2F2). | - **구현** **난이도** **낮음**: **특별한** **서버** **기능** **불필요**하여 단순 REST API로 구현 가능. 클라이언트에서도 setInterval이나 재귀 fetch로 반복 요청 구현 쉬움. Legacy 환경에서도 동작.<br>- **서버** **부하** **관리**: 구현은 쉽지만 **폴링** **주기** 조절이 관건. 주기를 짧게 하면 서버 요청 폭주, 길게 하면 실시간성 저하. Long polling 구현 시 서버에서 요청을 일정 시간 홀딩해야 하므로, 쓰레드나 비동기 처리 신경 써야 함. |
| **브라우저** **호환성** | - **광범위** **지원**: WebSocket (RFC 6455)은 현재 **모든** **주요** **브라우저**에서 기본 지원[[25]](https://ably.com/blog/websockets-vs-sse#:~:text=,on%20MDN%20for%20more%20details). IE10 이상, 크롬/파이어폭스/사파리/엣지 등 모두 호환. 모바일도 WebView 등에서 지원되어 호환성 매우 높음. | - **최신** **브라우저** **및** **앱**: Chrome, Firefox, Safari, Edge 등 **현대적** **브라우저**들에서 지원. 모바일 앱은 WebRTC 네이티브 API 활용. 그러나 **구형** **브라우저(****예:** **구 IE)**에서는 미지원이고, 브라우저별 구현 차이로 간혹 호환성 이슈 있을 수 있음[[26]](https://getstream.io/blog/webrtc-websockets/#:~:text=%2A%20Multi,WebRTC%2C%20ensuring%20compatibility%20and%20accessibility). 또한 사설망 환경에서 P2P 제약 등으로 **TURN** **서버** 없으면 동작 문제 발생 가능. | - **제한적** **호환**: **EventSource API**는 크롬, 파폭, 사파리 등에서 지원되나 **구형 IE** **브라우저에서는** **지원하지** **않음**[[24]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=,in%20older%20browsers%20or%20HTTP%2F2). (Edge도 Chromium 이전 버전은 SSE 미지원) 따라서 해당 브라우저 대상으론 폴백(예: 숨은 iframe이나 폴링) 필요. 그 외 대부분 브라우저엔 호환 양호. | - **보편적** **호환**: **HTTP** **요청**만 사용하므로 모든 브라우저에서 동작. 특별한 API가 아니어서 구형 환경 포함 호환성 최고. (실제로 AJAX가 되는 환경이면 어디서든 구현 가능.) |
| **확장성**<br>**(****다수** **접속)** | - **서버** **자원** **소모**: WebSocket은 연결 유지를 위해 서버에 소켓이 계속 열려 있고, **접속자** **수↑** **시** **메모리/****커넥션** **자원** 사용 증가[[27]](https://getstream.io/blog/webrtc-websockets/#:~:text=,In%20this%20case%2C%20you). 1:12 규모는 큰 문제 없으나, 수천 명 규모 시는 수평 확장이나 별도 메시지 브로커 등 고려 필요. 그래도 **서버당** **수만** **연결**도 실사용 사례 있음. | - **P2P** **스케일** **제한**: 피어 증가 시 연결 수 폭증으로 **사실상 3~4****명** **이상** **그룹에선 P2P Mesh** **실용적이지** **않음**[[21]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=is%20essentially%20zero%2C%20so%20your,and%20almost%20impossible%20to%20debug). 12명 수업에 전원 P2P 연결은 관리 어려움. 대규모로 가려면 SFU 등을 써야 하나, 이 경우 서버에 부하가 쏠리고 복잡성 증가. 요컨대 WebRTC는 **소규모(****몇** **명)** **실시간** **통신에** **적합**하고, 10명 이상 동시 참여에는 부적합[[4]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=In%20a%20large%20group%2C%20however%2C,and%20almost%20impossible%20to%20debug). | - **서버** **부하** **증가**: 서버는 이벤트 발생 시 **클라이언트** **수만큼** **메시지**를 보내야 하므로, 접속자가 많을수록 부하 상승. 또한 **브라우저별** **연결** **제한**(도메인당 6개 등) 영향으로, 다수 탭 사용 시 새 SSE 연결 제한 가능[[28]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Connection%20Limits). 12명 수준은 문제 없지만, 수천 명 대상 SSE는 브라우저 제약 및 서버 메모리 사용 고려해야 함. | - **비선형** **부하** **증가**: 클라이언트 수가 늘어나면 **요청** **횟수가** **그만큼** **증가**하므로, 예를 들어 12명이 1초마다 폴링하면 초당 12req, 100명이면 100req로 선형 증가. 서버 입장에서는 대부분 불필요한 응답을 처리하는 부하까지 감안하면 **확장성** **가장** **낮음**. 큰 규모 서비스에선 폴링은 네트워크 과부하 및 서버 비용을 높임. |

**초저지연 P2P** **통신**: 미디어(영상/음성)를 **고품질** **낮은** **지연**으로 전송하도록 설계되어 화상회의, 라이브 스트리밍 등에 최적[[31]](https://getstream.io/blog/webrtc-websockets/#:~:text=Real,compatible%20browser%2C%20signaling%20server%2C%20TURN%2FSTUN). 중앙 서버 거치지 않아 **참가자** **간** **직접** **통신**으로 대역폭 효율 (소수 참여 시) 및 프라이버시 향상[[32]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=WebSockets%20are%20strictly%20client,to%20go%20through%20the%20server).<br>- **멀티미디어** **및 P2P** **협업** **기능**: 카메라/마이크 접근 등 **실시간** **미디어** **공유** 및 화면공유, 파일전송 등 중앙 서버 없이 구현 가능. 또한 데이터채널로 P2P **파일** **전송이나** **문서** **협업** 등도 가능. | - **구현** **간편** **및** **자동** **재접속**: 서버 푸시 기능을 **간단히** **구현**할 수 있고, 브라우저에서 **자동** **재연결**을 지원하여 네트워크 일시 불안정 시에도 복구 용이[[5]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%EC%9E%AC%EC%97%B0%EA%B2%B0%EC%9D%84%20%EC%8B%9C%EB%8F%84%ED%95%98%EB%8A%94%20%EA%B8%B0%EB%8A%A5%EC%9D%B4%20%EB%82%B4%EC%9E%A5%EB%90%98%EC%96%B4%20%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4). 특별한 프레임워크 없이도 HTTP 스트림으로 동작하므로 비교적 쉽고 가볍게 실시간 기능 추가 가능.<br>- **HTTP** **친화적**: 기존 **방화벽/****프록시** **투과**에 유리하고, HTTP 환경에 자연스럽게 통합[[33]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Firewall%20Handling). 별도 프로토콜을 쓰는 WebSocket보다 인프라 변경 최소화. | - **단순함** **및** **보편성**: 개념적으로 **가장** **단순**하여 구현 쉬움. 추가 프로토콜 없이 주기적으로 REST API를 호출하는 방식이라 **디버깅도** **용이**. 기존 시스템(legacy)이나 제한된 환경에서도 동작해 호환성 높음.[[34]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A)<br>- **특별한** **서버** **설정** **불필요**: 일반 웹 서버만으로 동작하므로, 작은 규모나 예산이 적은 시스템에서 **빠르게** **적용** 가능[[34]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). |
| **대표적** **단점** | - **서버** **및** **인프라** **부담**: 지속 연결을 유지하므로, 서버가 **다중** **연결** **처리**를 잘 못 하면 메모리/소켓 고갈 위험. 또한 **프록시/****방화벽** **제약**으로 WebSocket 트래픽이 차단되는 경우도 있어 대응(fallback) 필요[[35]](https://ably.com/blog/websockets-vs-sse#:~:text=,IO).<br>- **수동** **재연결**: 기본 WebSocket API에는 연결 끊김 시 자동 재시도 기능이 없어 **별도** **구현** **필요**[[36]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Reconnection). (Socket.IO 등은 내장 지원). 보안상도 초기 핸드셰이크 이후엔 별도 헤더가 없으므로 **인증/****권한** **부여** 로직을 직접 관리해야 함. | - **구현** **복잡성/****확장** **한계**: 여러 서버 컴포넌트(STUN/TURN 등)와 복잡한 절차(WebRTC 신호 교환)를 요구하여 **학습** **곡선** **높고** **디버깅** **어려움**. 브라우저 간 호환성 이슈도 존재. 또한 **P2P****는** **참가자** **증가** **시** **급격히** **복잡해져** 대규모 확장에 부적합[[21]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=is%20essentially%20zero%2C%20so%20your,and%20almost%20impossible%20to%20debug).<br>- **중앙** **제어** **어려움**: 서버를 거치지 않으므로 **모든** **데이터가** **분산**되어 중앙에서 로그 수집이나 통제 어렵고, P2P 망 구성 실패시 처리도 난해. (사실상 다자간에는 결국 서버 도움 필요하여 WebSocket 대비 장점 희석.) | - **단방향** **한계**: 클라이언트->서버 송신 경로 부재로 **완전한** **양방향** **애플리케이션에** **사용** **곤란**. 이 경우 SSE + AJAX 혼합 등으로 복잡해질 수 있음. 실시간 협업 도구보다는 일방향 피드에 국한됨.[[8]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Full)<br>- **바이너리** **데이터** **비효율**: 이진 데이터를 직접 보낼 수 없어 텍스트로 변환해야 하므로 CPU/용량 부담. 대용량 실시간 데이터 전송에는 적합하지 않음 (예: 고해상도 캔버스 연속 전송 등은 부담). 또한 구형 브라우저 호환성 이슈 존재. | - **낮은** **효율 &** **지연**: 폴링 간격을 짧게 잡으면 불필요 요청 남발로 **서버** **부하**와 **네트워크** **낭비** 발생[[14]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). 반대로 간격 길면 **실시간성** **악화** 딜레마. 장기적으로 보면 다른 기술 대비 효율 낮고, 업데이트가 잦을수록 부담이 커짐.<br>- **실시간** **대량전송** **부적합**: 폴링은 설계상 실시간 대량 이벤트 스트림엔 맞지 않음. 서버 푸시를 흉내낼 뿐이므로, 사용자 수나 이벤트 빈도가 높아지면 금세 한계 도달. |

**주요** **고려사항** **요약:** 소규모 수업(1 대 12) 환경에서 **실시간** **그림** **공유**를 구현하려면, **양방향** **통신**과 **낮은** **지연**, 그리고 **효율적인** **데이터** **전송**이 핵심입니다. 위 비교를 종합해 보면:

- **HTTP Polling**은 구현은 쉽지만 지연과 오버헤드 측면에서 가장 불리합니다. 1초 미만의 지연을 맞추려면 매우 자주 폴링해야 하고, 이는 **대역폭** **낭비와** **서버** **부하**로 이어집니다[[14]](https://dev.to/haraf/server-sent-events-sse-vs-websockets-vs-long-polling-whats-best-in-2025-5ep8#:~:text=%E2%9C%85%20Pros%3A). **Long Polling**으로 개선해도 빈번한 그림 갱신에는 한계가 있습니다. **→** **따라서** **본** **시나리오에는** **부적합**합니다.
- **Server-Sent Events (SSE)**는 서버->클라이언트 일방향 스트리밍이라 **교사가** **그림을** **학생에게** **방송**하는 데에는 적합하고, **자동** **재연결** 등 편의도 있습니다[[5]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%EC%9E%AC%EC%97%B0%EA%B2%B0%EC%9D%84%20%EC%8B%9C%EB%8F%84%ED%95%98%EB%8A%94%20%EA%B8%B0%EB%8A%A5%EC%9D%B4%20%EB%82%B4%EC%9E%A5%EB%90%98%EC%96%B4%20%EC%9E%88%EC%8A%B5%EB%8B%88%EB%8B%A4). 실시간성도 충분합니다. 그러나 **학생→****선생님으로의** **그림** **전송**은 SSE만으로 처리 못 하므로 별도 AJAX 요청이 필요하고, 결국 **완전** **실시간** **양방향**에는 어색합니다[[8]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Full). 또한 **이미지** **바이너리** 전송시 SSE는 **텍스트로** **부호화**해야 하므로 비효율적입니다[[16]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Data%20Type%20Support). **→** **양방향** **그림** **공유에는** **한계**가 있습니다.
- **WebRTC**는 **소수** **참가자의** **영상/****음성** 공유에 뛰어나지만, **13****명** **모두와 P2P** **연결**을 맺는 것은 현실적으로 어렵습니다 (10명만 서로 연결해도 45개 연결 필요, 3~4명 초과 그룹엔 P2P Mesh “사실상 불가능”[[21]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=is%20essentially%20zero%2C%20so%20your,and%20almost%20impossible%20to%20debug)). 이를 피하려면 SFU 같은 **복잡한** **서버**가 추가되어야 하고, 구현 난이도가 매우 높아집니다[[37]](https://stackoverflow.com/questions/71943205/websocket-vs-webrtc-for-multiple-users-in-same-channel#:~:text=four%20participants%2C%20but%20unworkable%20beyond,that). 그림 공유는 영상만큼 연속적이지도 않고, 굳이 P2P로 직접 연결하지 않아도 성능에 지장 없는 소규모 시나리오입니다. **→ WebRTC****는** **이** **용도에** **과도한** **선택**이며, 구현 복잡성과 인프라 부담에 비해 이점이 크지 않습니다.
- **WebSocket**은 **지속** **연결을** **통한** **양방향** **통신**으로, 교사의 그림을 모든 학생에게 **실시간** **브로드캐스트**하기에 적합하고, 필요시 학생이 그린 것을 교사에게 보내는 것도 **동일** **채널로** **처리**할 수 있습니다[[1]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%ED%86%B5%EC%8B%A0%EC%97%90%EC%84%9C%20%EB%B9%A0%EB%A5%B4%EA%B3%A0%20%ED%9A%A8%EC%9C%A8%EC%A0%81%EC%9D%B8%20%EC%A0%84%EC%86%A1%EC%9D%84%20%EC%A7%80%EC%9B%90%ED%95%A9%EB%8B%88%EB%8B%A4). **지연도** **매우** **낮아** 1초 이내 업데이트에 거뜬하며, 실제로 많은 **실시간** **협업** **툴(****예:** **화이트보드)**이 WebSocket을 채택하고 있습니다[[30]](https://getstream.io/blog/webrtc-websockets/#:~:text=Team%20Collaboration%3A%20It%27s%20also%20ideal,for%20more%20productive%2C%20collaborative%20experiences). 또한 **구현** **난이도**도 WebRTC보다 훨씬 낮고, **바이너리** **데이터**도 바로 보내기 용이합니다[[7]](https://velog.io/@son93/WebSocket-vs-SSE-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C-feat.-Spring-Webflux#:~:text=,%ED%86%B5%EC%8B%A0%EC%97%90%EC%84%9C%20%EB%B9%A0%EB%A5%B4%EA%B3%A0%20%ED%9A%A8%EC%9C%A8%EC%A0%81%EC%9D%B8%20%EC%A0%84%EC%86%A1%EC%9D%84%20%EC%A7%80%EC%9B%90%ED%95%A9%EB%8B%88%EB%8B%A4). 서버와 브라우저 지원도 성숙되어 있어 안정적입니다.

**결론적으로,** **이** **수업** **시나리오에는 WebSocket** **방식이** **가장** **추천됩니다.** WebSocket은 **실시간** **양방향성**, **낮은** **지연**, **효율적인** **방송**이라는 요구조건을 모두 충족하면서, 구현과 운영 면에서도 비교적 수월합니다[[30]](https://getstream.io/blog/webrtc-websockets/#:~:text=Team%20Collaboration%3A%20It%27s%20also%20ideal,for%20more%20productive%2C%20collaborative%20experiences)[[11]](https://www.freecodecamp.org/news/server-sent-events-vs-websockets/#:~:text=Image%3A%20The%20performance%20of%20WebSockets,Sent%20Events). SSE는 일대다 방송용 보조 기술로 쓸 수는 있으나 양방향 한계가 있고, Polling은 현대적 실시간성 요구에 못 미치며, WebRTC는 불필요하게 복잡합니다. 따라서 **소규모** **실시간** **그림** **공유** **웹앱의** **최적** **기술은 WebSocket**이라고 할 수 있습니다.
