## 문제 정의: 암묵적 규칙의 딜레마

실무 개발 환경에서 가장 큰 어려움 중 하나는 문서화되지 않은 개발 규칙들입니다. 기존 프로젝트에 새로 합류한 개발자나 AI 코딩 도구들이 다음과 같은 상황에 직면하게 됩니다:

- Repository 패턴을 사용하는 프로젝트에서 Service 레이어에서 직접 SQL 호출
- 팀 내 암묵적 네이밍 규칙을 모르고 일관성 없는 코드 작성
- 특정 비즈니스 로직 처리 순서를 무시한 구현

이러한 문제를 해결하기 위해 AI를 활용한 체계적인 규칙 추출 방법론을 제시합니다.

## 핵심 방법론: 메타 프롬프트 기반 규칙 추출

### 1단계: 기본 개발 규칙 추출 프롬프트

```
이 코드베이스를 분석하여 개발 시 준수해야 할 명시적인 규칙들을 추출해주세요. 
추측이 아닌 실제 코드에서 관찰되는 패턴만을 기반으로 해주세요.

**분석 영역:**

1. **네이밍 컨벤션**
   - 클래스, 메소드, 변수명 패턴 분석
   - 파일 및 패키지 네이밍 규칙
   - 상수 및 enum 네이밍 방식

2. **코드 구조 패턴**
   - 레이어 간 의존성 규칙
   - 파일 조직 및 디렉토리 구조
   - Import 정리 방식

3. **에러 처리 전략**
   - Exception 처리 위치 및 방식
   - 로깅 레벨 및 메시지 형식
   - 사용자 대상 에러 응답 패턴

4. **데이터 접근 패턴**
   - ORM/SQL 사용 규칙
   - 트랜잭션 경계 설정
   - 데이터 검증 위치

**출력 형식:**
각 규칙에 대해 다음 정보를 제공:
- 규칙 명세 (MUST/SHOULD/MAY 수준으로 분류)
- 코드 증거 (파일명과 라인 번호 포함)
- 일관성 비율 (관찰된 사례 중 준수 비율)
- 예외 사항 (규칙을 벗어난 경우와 그 이유)

**분석 조건:**
- 최소 10개 이상의 서로 다른 파일 검토
- 70% 이상 일관성을 보이는 패턴만 규칙으로 인정
- 설정 파일(.editorconfig, checkstyle.xml 등)도 함께 검토
```

### 2단계: 비즈니스 도메인 규칙 추출

```
코딩 스타일을 넘어선 비즈니스 로직과 도메인 특화 규칙을 분석해주세요.

**도메인 분석 항목:**

1. **워크플로우 패턴**
   - 사용자 액션에 따른 처리 순서
   - 상태 변경 시퀀스 및 제약조건
   - 승인/검토 프로세스 구현

2. **데이터 무결성 규칙**
   - 필수 필드 조합 패턴
   - 참조 무결성 보장 방식
   - 비즈니스 규칙 검증 로직

3. **외부 연동 패턴**
   - API 호출 시 재시도 로직
   - 타임아웃 설정 및 에러 처리
   - 데이터 동기화 전략

**추출 방법:**
- 완전한 사용자 시나리오를 코드에서 추적
- 조건문과 검증 로직에서 비즈니스 규칙 식별
- 설정 파일에서 도메인 관련 상수 및 제약사항 확인
```

## 실전 적용 예시

### 추출된 규칙 예시

**코딩 스타일 규칙:**

```
MUST: Controller 메소드는 @Valid를 사용한 입력 검증 필수
- 증거: UserController.java:23, OrderController.java:45, PaymentController.java:67
- 일관성: 89% (34개 중 30개 메소드에서 확인)
- 예외: 내부 API용 AdminController는 이 규칙을 따르지 않음

SHOULD: Service 클래스는 인터페이스와 구현체로 분리
- 증거: UserService/UserServiceImpl, OrderService/OrderServiceImpl
- 일관성: 75% (8개 중 6개 서비스)
- 예외: UtilService, ConfigService는 단일 클래스로 구현
```

**비즈니스 규칙 예시:**

```
MUST: 결제 처리 전 사용자 권한 및 잔액 검증 필수
- 구현 위치: PaymentService.processPayment() 메소드 시작부
- 검증 순서: 1) 사용자 활성화 상태, 2) 결제 권한, 3) 잔액 충분성
- 실패 시: PaymentException 발생 및 audit 로그 기록

SHOULD: 주문 상태 변경 시 이메일 알림 발송
- 패턴: OrderService.updateStatus() → EmailService.sendStatusUpdate()
- 비동기 처리: @Async 어노테이션 사용
- 실패 처리: 이메일 발송 실패가 주문 처리에 영향 없음
```

### 규칙 준수 검증 프롬프트

```
다음 코드 변경사항이 추출된 프로젝트 규칙을 준수하는지 검증해주세요:

[코드 변경사항 삽입]

**검증 체크리스트:**
- 네이밍 컨벤션 준수 여부
- 레이어 아키텍처 규칙 준수
- 에러 처리 패턴 일치성
- 비즈니스 규칙 준수 여부
- 테스트 코드 포함 여부

**출력 형식:**
✅ PASS: [준수하는 규칙들]
❌ FAIL: [위반하는 규칙들과 수정 방법]
⚠️ WARNING: [개선 가능한 부분들]
```

## 도구 활용 전략

### Claude Code와의 통합

Claude Code 사용 시 프로젝트 루트에 .claude/CLAUDE.md 파일 생성:

```
# 프로젝트 개발 규칙

## 필수 준수 사항 (MUST)
- Controller에서 @Valid 어노테이션 사용
- Service 레이어에서 비즈니스 로직 검증
- Repository 패턴을 통한 데이터 접근

## 권장 사항 (SHOULD)  
- 인터페이스와 구현체 분리
- 비동기 처리 시 @Async 사용
- 트랜잭션 경계 명확히 설정

## 금지 사항
- Controller에서 직접 Entity 반환
- Service에서 HttpServletRequest 직접 접근
- 하드코딩된 설정값 사용
```

### GitHub Copilot 최적화

IDE 설정에서 다음과 같은 컨텍스트 파일들을 우선 참조하도록 설정:

- DEVELOPMENT\_RULES.md / AGENTS.md : 추출된 개발 규칙
- ARCHITECTURE\_GUIDE.md: 아키텍처 패턴 가이드
- DOMAIN\_CONSTRAINTS.md: 비즈니스 규칙 정리

## 한계점과 주의사항

### 방법론의 한계

**관찰 편향**: 코드에서 보이는 패턴이 항상 의도된 규칙은 아닙니다. 레거시 코드나 임시 구현이 잘못된 규칙으로 인식될 수 있습니다.

**컨텍스트 부족**: AI는 비즈니스 요구사항의 변화나 기술적 의사결정의 배경을 완전히 이해하지 못할 수 있습니다.

**정적 분석의 한계**: 런타임 동작이나 환경별 설정 차이는 코드 분석만으로 파악하기 어렵습니다.

### 검증 과정의 중요성

추출된 규칙은 반드시 다음 검증 과정을 거쳐야 합니다:

1. **팀 리뷰**: 시니어 개발자의 규칙 검토 및 승인
2. **실전 테스트**: 실제 개발 작업에서 규칙 적용 테스트
3. **지속적 업데이트**: 프로젝트 진화에 따른 규칙 갱신

## 운영 가이드라인

### 규칙 관리 프로세스

**월간 규칙 검토**:

- 새로 추가된 코드의 패턴 분석
- 기존 규칙의 준수율 측정
- 팀 피드백을 통한 규칙 개선

**분기별 전체 재추출**:

- 프로젝트 전체 코드베이스 재분석
- 아키텍처 변화 반영
- 새로운 도메인 규칙 발견

### 팀 온보딩 프로세스

신규 팀 멤버 합류 시:

1. **1주차**: 추출된 규칙 문서 숙지
2. **2주차**: 간단한 작업으로 규칙 적용 연습
3. **3주차**: 규칙 준수 검증 도구 활용한 실제 개발
4. **4주차**: 규칙 개선 제안 및 피드백

## 효과 측정

이 방법론의 도입 효과는 다음 지표로 측정할 수 있습니다:

**정량적 지표**:

- 코드 리뷰 시간 단축 비율
- 규칙 위반으로 인한 버그 감소율
- 새 팀원의 첫 PR 승인까지 소요 시간

**정성적 지표**:

- 팀 내 코드 일관성 만족도
- AI 도구 생성 코드의 품질 개선 체감도
- 온보딩 과정의 체계성 평가

## 결론

메타 프롬프트를 활용한 개발 규칙 추출은 단순한 도구가 아닌 팀의 개발 문화를 체계화하는 방법론입니다. 이를 통해 암묵적 지식을 명시적으로 만들어 팀 전체의 생산성과 코드 품질을 향상시킬 수 있습니다.

중요한 것은 추출된 규칙이 살아있는 문서가 되어야 한다는 점입니다. 프로젝트의 성장과 함께 규칙도 진화해야 하며, 팀원들의 지속적인 피드백을 통해 실용성을 유지해야 합니다.

이러한 체계적 접근을 통해 AI 시대의 개발 팀이 더 효율적이고 일관성 있는 코드를 생산할 수 있는 기반을 마련할 수 있을 것입니다.
