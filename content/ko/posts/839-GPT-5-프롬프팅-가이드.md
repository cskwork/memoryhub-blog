## 개요

GPT-5는 에이전트형(Agentic) 작업 수행, 코딩, 순수 지능, 그리고 조종(steerability) 면에서 큰 도약을 이뤄낸 최신 플래그십 모델입니다. 이미 광범위한 도메인에서 “바로 사용”만으로도 훌륭하게 동작하지만, 이 글에서는 실제 업무 적용 과정에서 얻은 프롬프팅 요령을 공유합니다. 에이전트형 작업 성능 개선, 지시 준수, 신규 API 기능 활용, 프런트엔드/소프트웨어 엔지니어링 코딩 최적화—특히 AI 코드 에디터 Cursor가 GPT-5와 함께 수행한 프롬프트 튜닝 인사이트—를 다룹니다.  
여기 소개하는 모범사례와 권장 도구로 큰 성과를 확인했지만, 프롬프팅은 언제나 정답이 하나가 아닙니다.

여러분의 문제에 가장 맞는 해법을 찾기 위해, 이 가이드를 토대로 실험하고 반복 개선하길 권합니다.

## Agentic workflow predictability (에이전트형 워크플로의 예측 가능성)

개발자 경험을 최적화하기 위해 GPT-5는 도구 호출, 지시 준수, 롱컨텍스트 이해를 중점 강화했습니다. 에이전트/도구 호출 플로우에서 GPT-5를 채택한다면 **Responses API**로 업그레이드하길 권장합니다. 이 API는 **도구 호출 간에도 추론을 보존**해 더 효율적이고 영리한 출력을 유도합니다.

### Agentic eagerness(적극성) 제어

에이전트 스캐폴딩은 모델에 결정을 많이 위임하는 쪽부터, 프로그램적 분기 로직으로 강하게 리드하는 쪽까지 스펙트럼이 넓습니다. GPT-5는 모호한 상황에서의 상위 의사결정부터, 정확히 정의된 작업까지 이 스펙트럼 전반에서 잘 작동하도록 훈련되었습니다.

본 절에서는 **모델의 주도성(프로액티브함)과 대기 자세** 사이의 균형을 잡는 법을 다룹니다.

#### 적극성을 낮추고 싶을 때 (Prompting for less eagerness)

기본적으로 GPT-5는 정답 보장을 위해 컨텍스트를 충분히 수집하려는 경향이 있습니다.

도구 호출의 ‘새는’ 탐색을 줄이고 최종 답변까지의 지연을 최소화하려면:

- **reasoning\_effort를 낮추세요.** 탐색 깊이는 줄지만 효율과 응답 지연이 개선됩니다. 많은 워크플로는 medium이나 low로도 일관된 결과를 냅니다.
- **문제 탐색 기준을 프롬프트에 명시하세요.** 모델이 불필요하게 많은 아이디어를 검토하지 않도록, 탐색 방식을 구체화합니다:

<context\_gathering>

Goal: Get enough context fast. Parallelize discovery and stop as soon as you can act. Method: - Start broad, then fan out to focused subqueries. - In parallel, launch varied queries; read top hits per query. Deduplicate paths and cache; don’t repeat queries. - Avoid over searching for context. If needed, run targeted searches in one parallel batch. Early stop criteria: - You can name exact content to change. - Top hits converge (~70%) on one area/path. Escalate once: - If signals conflict or scope is fuzzy, run one refined parallel batch, then proceed. Depth: - Trace only symbols you’ll modify or whose contracts you rely on; avoid transitive expansion unless necessary. Loop: - Batch search → minimal plan → complete task. - Search again only if validation fails or new unknowns appear. Prefer acting over more searching.

</context\_gathering>

- **도구 호출 예산을 고정**할 수도 있습니다(탐색 깊이에 따라 조정).짧은 컨텍스트 수집을 용이하게 하려면 **“완벽하지 않아도 진행해도 된다”** 같은 **탈출구(escape hatch)** 조항을 함께 두는 것이 유용합니다.

<context\_gathering>

- Search depth: very low - Bias strongly towards providing a correct answer as quickly as possible, even if it might not be fully correct. - Usually, this means an absolute maximum of 2 tool calls. - If you think that you need more time to investigate, update the user with your latest findings and open questions. You can proceed if the user confirms.

</context\_gathering>

#### 적극성을 높이고 싶을 때 (Prompting for more eagerness)

모델의 자율성/도구 호출 지속성/질문 최소화를 원한다면 reasoning\_effort를 높이고, **지속 수행을 독려하는 프롬프트**를 사용하세요:

```
<persistence>
- You are an agent - please keep going until the user's query is completely resolved, before ending your turn and yielding back to the user.
- Only terminate your turn when you are sure that the problem is solved.
- Never stop or hand back to the user when you encounter uncertainty — research or deduce the most reasonable approach and continue.
- Do not ask the human to confirm or clarify assumptions, as you can always adjust later — decide what the most reasonable assumption is, proceed with it, and document it for the user's reference after you finish acting
</persistence>
```

작업의 **종료 조건**, **안전/비안전 행동**, **사용자에게 제어를 넘길 시점**을 명확히 규정하면 도움이 됩니다. (예: 쇼핑 툴셋에서는 결제 단계는 낮은 불확실성만 허용, 검색은 높은 불확실성 허용 등. 코딩에서는 delete file은 높은 주의, grep은 자유도 높음.)

### Tool preambles(도구 프리앰블)

긴 롤아웃에서 **도구 호출 의도/계획/진행 상황을 중간중간 공유**하면 사용자 경험이 좋아집니다. GPT-5는 “툴 프리앰블” 형태로 이런 업데이트를 잘 제공합니다. 빈도/스타일/내용은 프롬프트로 유도할 수 있습니다. 예시:

```
<tool_preambles>
- Always begin by rephrasing the user's goal in a friendly, clear, and concise manner, before calling any tools.
- Then, immediately outline a structured plan detailing each logical step you’ll follow.
- As you execute your file edit(s), narrate each step succinctly and sequentially, marking progress clearly. 
- Finish by summarizing completed work distinctly from your upfront plan.
</tool_preambles>
```

이런 프롬프트에 반응해 모델이 내놓는 프리앰블 예는 다음과 같습니다(요약):

```
"output": [
  { "type": "reasoning", "summary": [{ "type": "summary_text", "text": "**Determining weather response**\n..." }] },
  { "type": "message", "content": [{ "type": "output_text", "text": "I’m going to check a live weather service..." }] },
  { "type": "function_call", "name": "get_weather", "arguments": "{\"location\":\"San Francisco, CA\",\"unit\":\"f\"}" }
]
```

### Reasoning effort

reasoning\_effort 매개변수로 **사고(추론) 강도와 도구 호출 성향**을 제어할 수 있습니다(기본 medium). 복잡한 다단계 작업일수록 높은 추론을 권장합니다. 또한 **서로 구분 가능한 하위 작업을 여러 턴에 나눠 수행**할 때 성능이 최고로 나옵니다.

### Responses API로 추론 컨텍스트 재사용

GPT-5를 사용할 때는 **Responses API**가 추천입니다. previous\_response\_id로 **이전 추론 흔적을 다음 요청으로 넘겨** 비용/토큰을 절감하고 성능/지연을 개선합니다. 예컨대 **Tau-Bench Retail** 점수는 73.9% → 78.2%로 상승했습니다. 계획을 매번 재구성하지 않아도 되어 효율이 좋아집니다(모든 Responses API 사용자, ZDR 조직 포함, 사용 가능).

## Maximizing coding performance, from planning to execution

GPT-5는 대규모 코드베이스에서 버그 수정, 대규모 diff, 다파일 리팩터/대형 기능 구현까지 선도적 성능을 보입니다. 완전 신규 앱의 제로-투-원 구현(프런트/백엔드)에도 강합니다. 여기선 실전 코딩 에이전트 고객사에서 검증된 **프롬프트 최적화**를 공유합니다.

### 프런트엔드 앱 개발

GPT-5는 **기본 미적 감각**과 **견고한 구현 능력**을 겸비합니다.

대부분의 웹 프레임워크/패키지를 잘 다루지만, 신규 앱엔 아래 스택을 추천합니다.

- **Frameworks:** Next.js(TypeScript), React, HTML
- **Styling/UI:** Tailwind CSS, shadcn/ui, Radix Themes
- **Icons:** Material Symbols, Heroicons, Lucide
- **Animation:** Motion(Framer Motion)
- **Fonts:** 산세리프 계열(Inter, Geist, Mona Sans, IBM Plex Sans, Manrope)

#### Zero-to-one 앱 생성

GPT-5는 **한 번에 앱을 구축**하는 데 뛰어납니다.

다음과 같이 **자체 우수성 루브릭을 내부적으로 만들고 반복**하게 지시하면 품질이 크게 향상됩니다.

```
<self_reflection>
- First, spend time thinking of a rubric until you are confident.
- ... 5-7 categories ...
- Finally, use the rubric to internally think and iterate... If not hitting top marks, start again.
</self_reflection>
```

### 기존 코드베이스 표준에 맞추기

증분 변경/리팩터 시에는 **기존 스타일/설계 기준에 부합**해야 합니다. GPT-5는 별도 지시 없이도 package.json 등에서 **레퍼런스 컨텍스트를 스스로 읽지만**,

다음처럼 **명시적으로 규칙/디렉터리 구조/관례**를 요약해 주면 더 좋아집니다:

```
<code_editing_rules>
<guiding_principles>
- Clarity and Reuse ...
- Consistency ...
- Simplicity ...
- Demo-Oriented ...
- Visual Quality ...
</guiding_principles>
<frontend_stack_defaults>
- Framework: Next.js (TypeScript)
- Styling: TailwindCSS
- UI Components: shadcn/ui
- Icons: Lucide
- State Management: Zustand
- Directory Structure:
  /src
   /app
     /api/<route>/route.ts
     /(pages)
   /components/
   /hooks/
   /lib/
   /stores/
   /types/
   /styles/
</frontend_stack_defaults>
<ui_ux_best_practices>
- Visual Hierarchy ...
- Color Usage ...
- Spacing and Layout ...
- State Handling ...
- Accessibility ...
</ui_ux_best_practices>
<code_editing_rules>
```

### 실제 협업 코딩: Cursor의 GPT-5 프롬프트 튜닝

AI 코드 에디터 **Cursor**는 GPT-5의 신뢰 가능한 알파 테스터였습니다. 그들의 시스템 프롬프트는 **도구 호출 신뢰성**, **장문 작업에서의 자율성**, **사용자 지시 준수** 사이의 균형을 맞춥니다.

- 초기에는 텍스트 출력이 **과도하게 장황**했고, 반대로 도구 호출로 생성된 코드는 **너무 간결**(한 글자 변수명 등)해 가독성이 떨어졌습니다.  
  → **API verbosity를 낮게** 설정해 텍스트는 간결히, 대신 “코드/코드 도구에 한해 높은 서술성”을 프롬프트로 강하게 요구:
- Write code for clarity first... Use high verbosity for writing code and code tools.
- 모델이 종종 **행동 대신 사용자 확인을 요청**해 흐름이 끊겼습니다.  
  → 사용 가능한 도구/컨텍스트뿐 아니라 **제품 동작 상세**(Undo/Reject, 사용자 선호 등)를 더 제공하자 **중간 질문 없이 장기 작업을 더**

**자율적으로 수행**:

...propose changes proactively for the user to approve/reject... almost never ask whether to proceed; attempt the plan proactively...

- 이전 모델에서 잘 먹히던 “**컨텍스트 철저 수집**” 지시는 GPT-5에겐 **과도한 도구 호출**(불필요 검색 반복)을 야기.  
  → 프롬프트를 완화해 **내부 지식 활용 vs 도구 사용 균형**이 개선됨. 또한 <[instruction]\_spec> 같은 **구조화된 XML 스펙**이 지시 준수를 안정화함:

<context\_understanding> .

.. If you've performed an edit ... not confident, gather more information... Bias towards not asking the user for help if you can find the answer yourself.

</context\_understanding>

## Optimizing intelligence and instruction-following

### Steering(조종성)

GPT-5는 **가장 잘 조종되는 모델**로, **말수(verbosity)**, **톤**, **도구 호출 행동**을 프롬프트로 세밀히 제어할 수 있습니다.

### Verbosity(말수)

GPT-5 API에는 **verbosity** 매개변수가 추가되어 **최종 답변 길이**(사고 길이와 별개)를 제어합니다. 기본은 API 파라미터지만, **특정 맥락만 자연어로 오버라이드**하도록 프롬프트에 적을 수 있습니다(예: 전역은 low, 코딩 도구는 high).

### Instruction following(지시 준수)

GPT-4.1과 마찬가지로 GPT-5는 **정밀한 지시 준수**가 강점입니다. 다만 **모순되거나 모호한 지시**가 있으면, 이를 화해하려고 **추론 토큰을 낭비**할 수 있습니다. 예를 들어 아래 의료 일정 프롬프트에는 상충점이 있습니다:

- “**동의 없이는 예약 금지**” vs “**연락 없이 당일 슬롯 자동 배정**”
- “**먼저 환자 프로필 조회**” vs “**응급이면 911 안내를 scheduling보다 우선**”

이를 해결하려면:

- 자동 배정을 “**환자에게 알린 후**”로 수정(동의 원칙과 정합).
- 응급 케이스에서는 **조회 생략**을 명시.

실무에선 프롬프트가 수시로 바뀌므로 **정기적인 모순/애매성 점검**이 중요합니다. 우리 **프롬프트 최적화 도구**도 활용해 보세요.

## Minimal reasoning

GPT-5에는 처음으로 **minimal reasoning effort**가 도입되었습니다. **지연에 민감**한 사용자의 최적 업그레이드이자, **GPT-4.1 사용자**에게도 적합합니다. 다만 **프롬프트 의존성**이 더 커지므로 다음을 권합니다:

- **짧은 사고 요약**을 최종 답변 서두에 요구(불릿 등) → 고난도 과제 성능 향상.
- **도구 호출 프리앰블**로 진행 상황을 서술 → 에이전트형 워크플로 성능 향상.
- **도구 지시의 모호성 제거**와 **지속 실행(persistence) 리마인더** 삽입 → 장기 롤아웃 중 조기 종료 방지.
- **계획 유도 프롬프트**를 앞부분에 배치—추론 토큰이 적으므로 외부화된 계획이 중요:
- Remember, you are an agent - please keep going until the user's query is completely resolved... You must plan extensively ... and reflect extensively ...

## Markdown formatting

API 기본값으로 GPT-5는 **마크다운을 자동 적용하지 않습니다**(호환성 유지 목적). 아래 지시를 넣으면 **계층적 마크다운 출력**을 유도할 수 있습니다.

- 마크다운은 **의미상 적절한 곳에만** 사용(inline code, code fences, 목록, 표).
- 파일/디렉터리/함수/클래스명은 백틱으로, 수식은 ( ), [ ] 형태로.

긴 대화에서 마크다운 준수가 약해지면 **3–5번째 사용자 메시지마다** 마크다운 지시를 재주입하면 안정화됩니다.

## Metaprompting(메타 프롬프팅)

여러 초기 사용자는 **GPT-5에게 스스로의 프롬프트를 고치게** 하여 큰 효과를 보았습니다. 원하는 행동을 더 일관되게 유도하려면, **어떤 문구를 추가/삭제**하면 좋을지 모델에게 직접 물어보세요.

예시 템플릿:

> When asked to optimize prompts, give answers from your own perspective ...  
> Here's a prompt: [PROMPT]  
> The desired behavior ... what are some minimal edits/additions ...

- 현재 컨테이너 안의 레포를 수정/실행해 과제를 해결하세요.
- rg 사용 권장, apply\_patch로만 파일 수정.
- 문제의 **근본 원인**을 고치고, **불필요한 복잡성**을 피하세요.
- 변경 후 git status 확인, 임시 파일/주석/저작권 헤더 제거, 가능하면 pre-commit 실행.
- 작은 변경은 불릿으로, 큰 변경은 개요+불릿+리뷰어용 포인트를 포함해 설명.

**apply\_patch 사용 예(요약)**  
패치 포맷은 V4A diff 형식이며, 파일은 상대경로만 사용합니다. 변경 구문 식별을 위해 3줄 컨텍스트/@@ 섹션을 활용하세요.

### Taubench-Retail minimal reasoning instructions (요약)

- **사용자 인증**부터 시작(이메일, 또는 이름+우편번호).
- **한 대화엔 한 사용자만** 지원.
- DB 변경 전에는 **작업 상세를 나열**하고 **명시적 동의**를 받습니다.
- **추측 금지**, 필요한 정보는 도구로 조회.
- **한 번에 한 개**의 도구 호출만.
- 취소/수정/반품/교환 각 시나리오의 제약(주문 상태, 결제 수단, 환불 경로 등)을 준수.
