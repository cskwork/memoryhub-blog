**Pitfalls Invisible to Beginners and How to Fix Them**

> "The code works fine. That's precisely what makes it dangerous."
> AI-generated code tends to become 'VIBE - Very Inefficient But Entertaining' code that passes all checks and clicks work. Junior developers are especially vulnerable because they verify only the results without understanding team patterns and design intent. By fixing just these 6 issues, you can transform "working code" into **maintainable code**.

---

## TL;DR

1. **Ignoring team patterns**: Code that violates existing folder structure and layering conventions
2. **One Source of Truth violation**: Type/model definitions duplicated across multiple locations
3. **Magic values hardcoded**: Status/numbers/strings scattered throughout
4. **Poor exception handling**: Happy path only, error handling buried in console logs, `any` overuse
5. **Single Responsibility Principle violation**: UI, business logic, and I/O tangled in one file/function
6. **Lost Shared management**: Reusable utilities duplicated, no common module**

---

## 1) **Team/Project Pattern Disregard**

- **Symptom**: Ignoring directory structure, layered architecture (controllers/services/repos, etc.), naming and file placement different from team conventions.
- **Why it happens**: "As long as the feature works" is the AI's default strategy. It doesn't know team rules unless you tell it.
- **Solution**
  - First, document your team's **CRUD patterns, folder structure, and coding conventions** (read examples and prepare templates).
  - Force AI compliance with **explicit prompts**:
  - Our team pattern:
    - src/
      - modules/{domain}/(controller|service|repo|types)
      - shared/(utils|constants|hooks)
    Follow this structure 100%. First present a summary of files to create/modify and the reasons.

---

## 2) **One Source of Truth Violation** (Duplicate Models/Types)

- **Symptom**: `Product` type defined separately on screen, API, and service. Field changes cause global explosions.
- **Why it happens**: AI prefers **local redefinition** when needed.
- **Solution**
  - Designate a **single source file** (e.g., `src/modules/product/types.ts`) and **import throughout**.
  - PR rule: "When creating new types, first search to confirm whether existing models can be reused"

```
// ❌ Bad example

// page A
type Product = { id: string; status: "CANCEL" | "DONE" }

// page B
type Product = { id: string; status: "CANCELLED" | "DONE" } // slightly different

// ✅ Good example

// src/modules/product/types.ts
export interface Product {
  id: string;
  status: ProductStatus;
}

export enum ProductStatus {
  CANCELLED = "CANCELLED",
  DONE = "DONE",
}

// Usage
import { Product, ProductStatus } from "@/modules/product/types";
```

## 3) **Magic Value Hardcoding** (Constant/Config Separation Failure)

- **Symptom**: Values like `"Cancel"`, `"Complete"`, `7`, `30000` scattered throughout code. Typos and inconsistency issues.
- **Solution**
  - Gather domain constants (statuses, permissions, error messages, periods) in **`shared/constants`** and use globally.
  - Expose intent via **i18n/domain enum/Config**.

```
// src/shared/constants/order.ts
export const ORDER_STATUS = {
  CANCELLED: "CANCELLED",
  DONE: "DONE",
} as const;

// bad
if (order.status === "완료") { ... }

// good
import { ORDER_STATUS } from "@/shared/constants/order";
if (order.status === ORDER_STATUS.DONE) { ... }
```

## 4) **Poor Exception/Error Handling** + `any` Overuse

- **Symptom**: Only happy path passes, errors covered with `console.error` and forgotten. Type blockages → `any`.
- **Why it happens**: AI's default is "happy path optimization".
- **Solution checklist**
  - Write **explicit failure scenarios** (network/permissions/timeouts/duplicate clicks).
  - `try/catch` + user feedback (toast/message) + logging (level/context).
  - Ban `any`, use `unknown` → **narrowing** (type guard).

```
async function submit(order: Order) {
  try {
    await api.orders.create(order);
    toast("Order completed.");
  } catch (e: unknown) {
    log.error("createOrder failed", { e, orderId: order.id });
    toast("There was an issue with your order. Please try again shortly.");
  }
}
```

## 5) **Single Responsibility Principle Violation** (SRP)

- **Symptom**: UI rendering + business rules + API calls + state management tangled in one file/function.
- **Solution**
  - Screen: **Presentation components**
  - Logic: **Services/hooks/utils** (favor pure functions)
  - I/O: **API client/repository** separation

```
/product
  ProductPage.tsx       // UI
  useProduct.ts         // Screen-only state/query combination
  product.service.ts    // Domain rules (discounts, validation)
  product.repo.ts       // API/DB access
```

---

## 6) **Shared Module Management Absence**

- **Symptom**: Similar utils, hooks, components exist as duplicates scattered everywhere. Changes cause cascading breaks.
- **Solution**
  - **Criteria for shared use**:
    - ① Reused in two or more places
    - ② Domain-independent
    - ③ Testable
  - Unified location: `src/shared/{utils,components,hooks,constants}`
  - **Contribution rules**: Include documentation and usage examples when adding, keep breaking change logs when modifying

## Quick Checklist Before Review (2-minute check)

| Item | Question I'd Ask | Pass Criteria |
| --- | --- | --- |
| Pattern compliance | Did you 100% follow team folder/layer rules? | File placement and naming match |
| Single source | Are types/models/schemas defined in only one place? | Only global imports exist |
| Magic values | Are constants/enums/i18n separated? | Zero hardcoding |
| Error handling | Are user/logs clear on failure? | Toast + structured logging |
| SRP | Are screens, logic, and I/O separated? | Dependency direction unidirectional |
| Shared | Did you move reused code to shared? | No duplicate utils |

---

## How to Instruct AI (Prompt Template)

```
Role: Implementation assistant matching our team rules
Mandatory rules:
1) 100% follow the folder/layer structure below
2) Types/models: import only from single file (no new definitions)
3) Constants/states: reference only from shared/constants (no hardcoding)
4) All async paths: include exception handling + user message + logging
5) UI/domain logic/I/O separation (SRP) and maintain dependency direction
6) Reusable functions: promote to shared with usage examples/simple tests

Work sequence:
- (A) Present changed files list/reasons/2 alternatives in table format
- (B) Implementation
- (C) Prove self-checklist compliance
```
