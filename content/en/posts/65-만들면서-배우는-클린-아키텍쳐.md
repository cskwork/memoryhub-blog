## Problems with Layered Architecture?

### What is Layered Architecture?

The web layer receives requests and sends them to services in the domain or business layer.  
Services perform necessary business logic, and call components in the persistence layer to query or modify the current state of domain entities.

### Weaknesses

Induces database-driven design (since the web layer depends on the domain layer, and the domain layer depends on the persistence layer, it naturally becomes dependent on the database).

However, apps we build are usually modeled around behavior rather than state.  
From a business perspective, domain logic takes precedence over database structure.

### Disadvantages of the Persistence Layer

- Since everything is accessible, it becomes increasingly bloated over time.
- Testing becomes difficult (even manipulating a single field leads to implementing domain logic in the web layer -> when expanding use cases, many domain logic is added to the web layer, the app's responsibilities become mixed overall, and core domain logic spreads out with high probability).
- In web layer testing, the persistence layer must be mocked. This increases unit test complexity. As a result, unit test writing takes more time.
- For this reason, finding use cases also becomes difficult.
- Concurrent work becomes difficult. Layered architecture requires building each stage before moving to the next, so specific features can only be worked on by one developer at a time. Even so, merge conflict issues may occur during concurrent work.

## Clean Architecture

### Inverting Dependencies

### Single Responsibility Principle

- A component should have only one reason to change. (Single Reason to Change Principle)

### Dependency Inversion Principle

- Any dependency in code can have its direction reversed (inverted). Introduce an interface in the domain layer to invert dependencies so the persistence layer depends on the domain layer.

### Hexagonal Architecture Characteristics

- There are use cases that interact with domain entities, and
- All dependencies are toward the core (entities)
- Outside the hexagon are various adapters that interact with the app (adapters that interact with web browsers, external systems, and databases)

![](/images/65-만들면서-배우는-클린-아키텍쳐/img_3.png)

### Role of Adapter (Controller)

- HTTP request-to-Java object mapping
- Authority checks
- Input validation
- Map input to port (interface) input models
- Call use cases, map outputs to HTTP
- Return HTTP responses

### Role of Persistent Adapter

- Receive input
- Map input to database format
- Send input to database
- Map database output to app format
- Return output

### Role of Port

- Make each service depend only on the methods it actually needs
- Create a plug-and-play experience with narrow ports
- CRUD method naming for interfaces vs implementing each CRUD method within a single interface

### Code Organization

in - from web (client)  
out - to database (server)
