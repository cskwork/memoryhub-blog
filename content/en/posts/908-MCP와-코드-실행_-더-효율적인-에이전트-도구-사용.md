Direct tool calls consume context for each definition and result. Agents scale more effectively instead by writing code that calls tools. Here's how to implement this in MCP.

Model Context Protocol (MCP) is an open standard for connecting AI agents to external systems. Connecting agents to tools and data traditionally required custom integration for each pair, leading to fragmentation and duplicate work that made it hard to scale truly connected systems. MCP provides a universal protocol. Once developers implement MCP in an agent, an entire ecosystem of integrations opens up.

Adoption has accelerated rapidly since MCP's launch in November 2024. The community has built thousands of MCP servers, SDKs are available for all major programming languages, and the industry has adopted MCP as the de facto standard for connecting agents to tools and data.

Today, developers regularly build agents with access to hundreds or thousands of tools across dozens of MCP servers. However, as the number of connected tools increases, pre-loading all tool definitions and passing intermediate results through the context window slows agent speed and increases costs.

This blog explores how code execution enables agents to interact with MCP servers more efficiently, handling more tools with fewer tokens.

## Tool Definitions Consuming Excessive Tokens Degrade Agent Efficiency

As MCP usage scales, two common patterns can increase agent costs and latency:

1. Tool definitions overload the context window
2. Intermediate tool results consume additional tokens

### 1. Tool Definitions Overload the Context Window

Most MCP clients pre-load all tool definitions directly into context using direct tool invocation syntax exposed to the model. These tool definitions can look like:

```
gdrive.getDocument
     Description: Retrieve a document from Google Drive
     Parameters:
                documentId (required, string): The ID of the document to retrieve
                fields (optional, string): Specific fields to return
     Returns: Document object with title, body content, metadata, permissions, etc.

salesforce.updateRecord
    Description: Update a record in Salesforce
    Parameters:
               objectType (required, string): Salesforce object type (Lead, Contact, Account, etc.)
               recordId (required, string): The ID of the record to update
               data (required, object): Fields to update with new values
     Returns: Updated record object with confirmation
```

Tool descriptions consume more context window space, increasing response time and cost. When an agent is connected to thousands of tools, it must process tens of thousands of tokens just to read the definitions before processing the request itself.

### 2. Intermediate Tool Results Consume Additional Tokens

Most MCP clients allow the model to call MCP tools directly. For example, you can ask an agent to "Download meeting transcripts from Google Drive and attach them to a Salesforce lead."

The model makes calls like:

```
TOOL CALL: gdrive.getDocument(documentId: "abc123")
        → "Discussed Q4 objectives...\n[full transcript text]" returned
           (loaded into model context)

TOOL CALL: salesforce.updateRecord(
            objectType: "SalesMeeting",
            recordId: "00Q5f000001abcXYZ",
              data: { "Notes": "Discussed Q4 objectives...\n[full transcript text written]" }
        )
        (model must write full transcript to context again)
```

All intermediate results must pass through the model. In this example, the full call transcript flows twice. For a 2-hour sales meeting, you might need to process an additional 50,000 tokens. Larger documents can exceed context window limits, breaking the workflow.

When handling large documents or complex data structures, the model is more likely to make mistakes when copying data between tool calls.

The MCP client loads tool definitions into the model's context window and orchestrates a message loop where each tool call and result passes through the model between tasks.

## Code Execution with MCP Improves Context Efficiency

As code execution environments become more generalized for agents, the solution is to expose MCP servers as code APIs rather than direct tool calls. Agents can then write code that interacts with MCP servers. This approach solves both problems. Agents can load only the tools they need, and they can process data in the execution environment before passing results back to the model.

There are several ways to do this. One approach is to generate a file tree of all available tools from connected MCP servers. An implementation using TypeScript looks like:

```
servers
├── google-drive
│   ├── getDocument.ts
│   ├── ... (other tools)
│   └── index.ts
├── salesforce
│   ├── updateRecord.ts
│   ├── ... (other tools)
│   └── index.ts
└── ... (other servers)
```

Each tool then corresponds to a file like:

```
// ./servers/google-drive/getDocument.ts
import { callMCPTool } from "../../../client.js";

interface GetDocumentInput {
  documentId: string;
}

interface GetDocumentResponse {
  content: string;
}

/* Read document from Google Drive */
export async function getDocument(input: GetDocumentInput): Promise<GetDocumentResponse> {
  return callMCPTool<GetDocumentResponse>('google_drive__get_document', input);
}
```

The Google Drive to Salesforce example from above becomes this code:

```
// Read transcript from Google Docs and add to Salesforce lead
import * as gdrive from './servers/google-drive';
import * as salesforce from './servers/salesforce';

const transcript = (await gdrive.getDocument({ documentId: 'abc123' })).content;
await salesforce.updateRecord({
  objectType: 'SalesMeeting',
  recordId: '00Q5f000001abcXYZ',
  data: { Notes: transcript }
});
```

Agents discover tools by exploring the file system. They list the `./servers/` directory to find available servers (like google-drive and salesforce), then read the specific tool files they need (like getDocument.ts and updateRecord.ts) to understand each tool's interface. This allows agents to load only the definitions they need for the current task. This reduces token usage from 150,000 tokens to 2,000 tokens, saving 98.7% of time and cost.

Cloudflare also reported similar results and called code execution with MCP "code mode." The core insight is the same: LLMs are good at writing code, and developers should leverage this strength to build agents that interact with MCP servers more efficiently.

## Benefits of Code Execution with MCP

Code execution with MCP allows agents to load tools on demand, filter data before reaching the model, and execute complex logic in a single step for more efficient context use. This approach also provides security and state management benefits.

### Progressive Disclosure

Models are good at file system exploration. By exposing tools as code in the file system, models can read tool definitions as needed without reading all of them upfront.

Alternatively, add a `search_tools` tool to the server to find relevant definitions. For example, when working with the hypothetical Salesforce server used above, agents can search for "salesforce" and load only the tools needed for the current task. By including a detail level parameter in the `search_tools` tool, agents can choose the level of detail they need (name only, name and description, or full definition with schema), allowing them to conserve context and efficiently discover tools.

### Context-Efficient Tool Results

When working with large datasets, agents can filter and transform results in code before returning them to the model. Consider fetching a 10,000-row spreadsheet:

```
// Without code execution - all rows pass through context
TOOL CALL: gdrive.getSheet(sheetId: 'abc123')
        → 10,000 rows returned in context for manual filtering

// Using code execution - filtered in execution environment
const allRows = await gdrive.getSheet({ sheetId: 'abc123' });
const pendingOrders = allRows.filter(row => 
  row["Status"] === 'pending'
);
console.log(`Found ${pendingOrders.length} pending orders`);
console.log(pendingOrders.slice(0, 5)); // Log first 5 for review
```

Agents see only 5 rows instead of 10,000. Similar patterns work for aggregation, joining across multiple data sources, and extracting specific fields, all without inflating the context window.

### More Robust and Context-Efficient Control Flow

Loops, conditionals, and error handling can be done with familiar code patterns instead of chaining individual tool calls. For example, if you need deployment notifications in Slack, agents can write:

```
let found = false;
while (!found) {
  const messages = await slack.getChannelHistory({ channel: 'C123456' });
  found = messages.some(m => m.text.includes('deployment complete'));
  if (!found) await new Promise(r => setTimeout(r, 5000));
}
console.log('Deployment notification received');
```

This approach is more efficient than alternating between MCP tool calls and sleep commands through the agent loop.

Also, being able to write conditional trees that execute saves "time to first token" latency. Instead of waiting for the model to evaluate an if statement, agents can let the code execution environment do it.

### Privacy Work

When agents use code execution with MCP, intermediate results stay in the execution environment by default. This means only what agents explicitly log or return is visible to the model, and data they don't want to share with the model can flow through the workflow without entering the model's context.

For more sensitive workloads, the agent harness can automatically tokenize sensitive data. For example, suppose you need to pull customer contact details from a spreadsheet into Salesforce. The agent writes:

```
const sheet = await gdrive.getSheet({ sheetId: 'abc123' });
for (const row of sheet.rows) {
  await salesforce.updateRecord({
    objectType: 'Lead',
    recordId: row.salesforceId,
    data: { 
      Email: row.email,
      Phone: row.phone,
      Name: row.name
    }
  });
}
console.log(`Updated ${sheet.rows.length} leads`);
```

The MCP client intercepts the data and tokenizes PII before it reaches the model:

```
// If sheet.rows were logged, here's what the agent would see:
[
  { salesforceId: '00Q...', email: '[EMAIL_1]', phone: '[PHONE_1]', name: '[NAME_1]' },
  { salesforceId: '00Q...', email: '[EMAIL_2]', phone: '[PHONE_2]', name: '[NAME_2]' },
  ...
]
```

Then when data is shared in other MCP tool calls, detokenization happens through the MCP client's lookup. Actual email addresses, phone numbers, and names flow from Google Sheets to Salesforce but don't pass through the model. This prevents agents from accidentally logging or processing sensitive data. It can also be used to define deterministic security rules that choose where data can flow and where it comes from.

### State Persistence and Skills

Code execution with file system access allows agents to maintain state across tasks. Agents can write intermediate results to files to resume work and track progress:

```
const leads = await salesforce.query({ 
  query: 'SELECT Id, Email FROM Lead LIMIT 1000' 
});
const csvData = leads.map(l => `${l.Id},${l.Email}`).join('\n');
await fs.writeFile('./workspace/leads.csv', csvData);

// Later execution resumes from where it stopped
const saved = await fs.readFile('./workspace/leads.csv', 'utf-8');
```

Agents can also keep their code as reusable functions. Once an agent develops working code for a task, that implementation can be saved for later use:

```
// In ./skills/save-sheet-as-csv.ts
import * as gdrive from './servers/google-drive';
export async function saveSheetAsCsv(sheetId: string) {
  const data = await gdrive.getSheet({ sheetId });
  const csv = data.map(row => row.join(',')).join('\n');
  await fs.writeFile(`./workspace/sheet-${sheetId}.csv`, csv);
  return `./workspace/sheet-${sheetId}.csv`;
}

// Later in all agent runs:
import { saveSheetAsCsv } from './skills/save-sheet-as-csv';
const csvPath = await saveSheetAsCsv('abc123');
```

This connects closely to the concept of skills—a folder of reusable instructions, scripts, and resources for agents to improve performance on specialized tasks. Adding SKILL.md files to these saved functions creates structured skills that models can reference and use. Over time, this allows agents to build a higher-level functional toolbox and develop the scaffolding needed to work most effectively.

Note that code execution introduces its own complexity. Running code generated by agents requires a safe execution environment with appropriate sandboxing, resource limits, and monitoring. These infrastructure requirements add operational overhead and security considerations that direct tool calls avoid. The benefits of code execution (reduced token costs, shorter latency, improved tool composition) must be weighed against these implementation costs.

## Summary

MCP provides agents with a foundational protocol to connect to many tools and systems. However, when too many servers are connected, tool definitions and results can consume excessive tokens, degrading agent efficiency.

While many of these problems feel new (context management, tool composition, state persistence), they have known solutions in software engineering. Code execution applies these established patterns to agents, allowing them to interact with MCP servers more efficiently using familiar programming structures.
