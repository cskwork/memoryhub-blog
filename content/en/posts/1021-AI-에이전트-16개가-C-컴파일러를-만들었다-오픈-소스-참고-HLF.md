# 

Compilers are among the most complex software in computer science. GCC is the result of hundreds of developers refining for 40+ years, and LLVM has 20+ year history. Yet in February 2026, 16 AI agents built a 100,000-line C compiler in 2 weeks.

A compiler that actually compiled and booted the Linux kernel. This isn't just "AI writes code well."

**It signals that how software is built is fundamentally changing.**

**TLDR:** Bottom line: Anthropic's agent team experiment shows AI coding's paradigm shifting from "individual assistant" to "autonomous team collaboration," with developer roles moving from "code writer" to "system designer."

## Background

> Agent Teams are how multiple AI instances work in parallel on one codebase and complete projects without human intervention.

Looking back at AI coding tool evolution reveals staggering change speed. Early days meant just tab autocomplete in IDEs. Then GitHub Copilot completed function bodies, and tools like Claude Code and Cursor enabled pair programming.

But all these tools shared one premise: "humans define work, AI executes for seconds to minutes, then return to humans."

Agent Teams broke that premise. Nicholas Carlini, researcher at Anthropic's Safeguards team, put 16 Claude Opus 4.6 instances each in independent Docker containers, shared one Git repository, and set them to work autonomously in infinite loops.

No central managing AI either. Each agent autonomously decided "what's most critical right now" and moved.

The project result: **CCC (Claude's C Compiler)**, a 100,000-line C compiler written in Rust.

## Project Overview: CCC by the Numbers

Project scope summary:

| Item | Number |
| --- | --- |
| Deployed agents | 16 (Claude Opus 4.6) |
| Total Claude Code sessions | ~2,000 |
| Duration | ~2 weeks |
| Input tokens | ~2 billion |
| Output tokens | ~140 million |
| Total cost | ~$20,000 (~29 million won) |
| Code size | ~100,000 lines (Rust) |
| External dependencies | None (Rust stdlib only) |

Compilable project list is impressive: Linux 6.9 kernel (x86, ARM, RISC-V), QEMU, FFmpeg, SQLite, PostgreSQL, Redis all successfully compiled, achieving 99% pass rate on GCC torture test suite.

Even succeeded in the ultimate developer litmus test: compiling and running Doom.

Carlini noted "if I built this compiler directly, costs would be much higher, and with a team, even more so." $20,000 is expensive experimentation, but striking compared to human dev teams.

## Core Design Principles: How Agent Teams Worked

The most interesting part isn't the compiler itself. **It's the environment design enabling agents to autonomously collaborate.**

Carlini spent most time on tests and environment, not code.

### 1. Agent Loop: Endless Work Cycle

Traditional Claude Code waits for human input after finishing. Carlini changed this structure to create infinite loops:

```
#!/bin/bash
while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"
    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

Agents immediately start next work after finishing one. With no stop condition, agent prompts instruct: "divide problems into chunks, track progress, keep going until perfect." One agent anecdote: accidentally executing `pkill -9 bash` terminating itself.

### 2. Parallel Collaboration: Simple Git-Based Sync

16 agents' collaboration mechanism is surprisingly simple.

Each agent creates text files in `current_tasks/` directory when starting work to "lock" those tasks.

If one agent creates `current_tasks/parse_if_statement.txt`, others avoid touching it. When two agents try locking the same task, Git merge conflicts naturally mediate.

Finished agents pull upstream, merge other agents' changes, push theirs, unlock.

No central orchestration agent, no complex communication protocols.

Collaboration happened with minimal rules on top of Git, an already-validated tool.

### 3. Test Harness: Tests Designed for AI

Carlini's most emphasized lesson: "design tests from AI perspective." Tests for humans differ from tests for AI.

**Preventing context pollution is key.** If test harnesses output thousands of lines, AI's context window gets consumed. Instead, output only key summaries, store detailed logs in files. When errors occur, write "ERROR" and cause on same line for easy grep searching.

**Compensating for lack of time sense.** Claude lacks time concepts, so if left alone, runs tests for hours. Fixed with `--fast` option running 1-10% random samples, deterministic per-agent but random across VMs. Covers all files while each agent precisely identifies regression.

**Must maintain self-records.** Each agent starts context-fresh in new containers. To help, instructed to frequently update README and progress files. When stuck, agents developed habit of documenting failed approaches and remaining work.

## Obstacles and Breakthroughs: The Linux Kernel Wall

Parallelization is easy with many independent test cases. Each agent picks different failing tests.

After test suite reached 99% pass rate, agents specialized: each compiling different open-source projects (SQLite, Redis, libjpeg, Lua, etc.).

But Linux kernel was different. Kernel compilation is one massive task, so all 16 agents hit same bugs, tried same fixes, overwrote each other's changes. Running 16 agents or 1 made no difference.

Carlini devised **using GCC as "ground truth oracle"** strategy. Compile most kernel files with GCC, only some with CCC. If kernel works, CCC's files are fine. If breaks, bugs exist in CCC files.

Narrow further by swapping CCC files back to GCC incrementally.

This decomposed one giant problem into multiple small independent ones,

enabling each agent to parallelly track different files' bugs.

This strategy is a variant of **binary bisect**—familiar to developers.

Except 16 AI agents performed it simultaneously.

## Role Specialization: Not All Agents Do the Same

Another parallelization benefit: **specialization**. Not all agents stuck to feature implementation—each took different roles.

| Role | Responsibility |
| --- | --- |
| Feature Implementation Agent | Core functionality: parsers, code generators |
| Deduplication Agent | Integrate duplicated functionality in codebase |
| Performance Optimization Agent | Improve compiler's own execution speed |
| Output Optimization Agent | Improve compiled binary efficiency |
| Code Quality Agent | Suggest structural improvements from Rust perspective |
| Documentation Agent | Maintain README, architecture docs |

LLMs writing code tend to reimplement existing features.

Dedicated deduplication agent was designed to address this weakness. Role differentiation mirrors human dev team structures.

Senior architect defines structure, juniors implement, QA validates, tech writers document.

## Limitations: Where AI Still Struggles

Carlini honestly disclosed limitations. Understanding limitations matters as much as impressive results.

**Generated code efficiency is serious.** CCC with all optimizations enabled produces slower binaries than GCC with all optimizations disabled. One commentator's expression: "grammatically correct but reads like middle schooler's book report essay."

**Failed implementing 16-bit x86 code generator.** Real-mode Linux boot needs 16-bit code, but CCC generates code exceeding 60KB, surpassing Linux's 32KB limit. Ultimately bypassed by calling GCC.

ARM and RISC-V support full standalone compilation.

**Problems intensify with larger codebases.** Passing 100K lines, adding features or fixing bugs frequently broke existing functionality. Humans encounter this too,

but AI agents' "understanding whole codebase" limitation surfaced more rapidly.

**Rust code quality is "reasonable" but not expert-level.** Carlini assessed this as "practical limitation line of autonomous agent coding by current models."

## Best Practices/Pattern Comparison

Design principles from agent team experiment:

| Design Principle | Advantage | Caution |
| --- | --- | --- |
| Infinite loop harness | Continuous work without humans | Agents can unexpectedly terminate themselves |
| Git-based lock file sync | Leverage existing infrastructure, simple implementation | Merge conflicts frequent but agents resolve |
| Oracle comparison testing | Decompose massive tasks into parallelizable units | Need reliable reference compiler (GCC) |
| Role specialization | Handle code quality, documentation alongside core work | Unclear role boundaries cause duplicate work |
| Context-friendly logging | Improve AI judgment accuracy | Requires separate logging design effort |
| Random subsample testing | Balance speed and coverage | Full testing needed in final verification stage |

## Implications for Developers

Misreading this as "AI replaces developers" misses the point. As Carlini emphasized,

agents worked because test harness and environment design were sophisticated. Agents are only as smart as test quality.

The implication is clear:

**Core developer capability is shifting from "ability to write code" to "ability to design systems where AI works correctly."**

Specifically: architecture design, test suite building, success criteria definition, verification pipeline design become more important.

Carlini, with penetration testing background, voiced concerns:

"Deploying software not directly verified by developers raises serious concerns."

Tests passing doesn't end work.

Autonomous development requires new verification dimensions.

## Closing Thoughts

- AI agent teams aren't copilot extensions but paradigm shift changing software development unit from "task" to "project."
- Agent performance determined not by model intelligence but test environment quality, with "verification engineering" emerging as core capability.
- Real-world tip: Audit your current project's test suite asking "can AI judging these results alone decide what to do next?"
