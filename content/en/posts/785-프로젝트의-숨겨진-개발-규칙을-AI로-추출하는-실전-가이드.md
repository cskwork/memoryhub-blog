## Problem Definition: The Dilemma of Implicit Rules

One of the biggest challenges in real-world development is undocumented development rules. New developers joining existing projects or AI coding tools face situations like:

- A project using Repository pattern but Service layer directly calling SQL
- Team members creating inconsistent code because they don't know implicit naming conventions
- Implementations ignoring specific business logic processing sequences

To solve these issues, I present a systematic methodology for rule extraction using AI.

## Core Methodology: Meta-Prompt Based Rule Extraction

### Step 1: Basic Development Rule Extraction Prompt

```
Analyze this codebase and extract explicit rules that must be followed during development.
Base extraction only on patterns actually observed in code, not speculation.

**Analysis Areas:**

1. **Naming Conventions**
   - Class, method, variable name patterns
   - File and package naming rules
   - Constant and enum naming conventions

2. **Code Structure Patterns**
   - Layer-to-layer dependency rules
   - File organization and directory structure
   - Import organization methods

3. **Error Handling Strategies**
   - Exception handling location and methods
   - Logging levels and message formats
   - User-facing error response patterns

4. **Data Access Patterns**
   - ORM/SQL usage rules
   - Transaction boundary settings
   - Data validation locations

**Output Format:**
For each rule, provide:
- Rule specification (classified as MUST/SHOULD/MAY)
- Code evidence (with filenames and line numbers)
- Consistency percentage (adherence percentage among observed cases)
- Exceptions (cases where rules are broken and why)

**Analysis Conditions:**
- Review at least 10 different files
- Only rules showing 70%+ consistency are recognized
- Review configuration files (.editorconfig, checkstyle.xml, etc.)
```

### Step 2: Business Domain Rule Extraction

```
Analyze business logic and domain-specific rules beyond coding style.

**Domain Analysis Items:**

1. **Workflow Patterns**
   - Processing sequences based on user actions
   - State change sequences and constraints
   - Approval/review process implementations

2. **Data Integrity Rules**
   - Required field combination patterns
   - Referential integrity preservation methods
   - Business rule validation logic

3. **External Integration Patterns**
   - API call retry logic
   - Timeout settings and error handling
   - Data synchronization strategies

**Extraction Methods:**
- Trace complete user scenarios in code
- Identify business rules from conditionals and validation logic
- Check configuration files for domain-related constants and constraints
```

## Real-World Application Examples

### Extracted Rule Examples

**Coding Style Rules:**

```
MUST: Controller methods require @Valid for input validation
- Evidence: UserController.java:23, OrderController.java:45, PaymentController.java:67
- Consistency: 89% (30 out of 34 methods confirmed)
- Exception: AdminController (internal API) doesn't follow this rule

SHOULD: Service classes separated into interface and implementation
- Evidence: UserService/UserServiceImpl, OrderService/OrderServiceImpl
- Consistency: 75% (6 out of 8 services)
- Exception: UtilService, ConfigService implemented as single classes
```

**Business Rules Example:**

```
MUST: Validate user authorization and balance before payment processing
- Implementation Location: PaymentService.processPayment() method start
- Validation Sequence: 1) User activation status, 2) Payment authorization, 3) Sufficient balance
- On Failure: PaymentException raised and audit log recorded

SHOULD: Send email notification when order status changes
- Pattern: OrderService.updateStatus() → EmailService.sendStatusUpdate()
- Asynchronous Processing: Using @Async annotation
- Failure Handling: Email sending failure doesn't affect order processing
```

### Rule Compliance Verification Prompt

```
Verify whether the following code changes comply with extracted project rules:

[Insert code changes]

**Verification Checklist:**
- Naming convention compliance
- Layer architecture rule compliance
- Error handling pattern consistency
- Business rule compliance
- Test code inclusion

**Output Format:**
✅ PASS: [Rules being followed]
❌ FAIL: [Rules being violated and how to fix]
⚠️ WARNING: [Areas for improvement]
```

## Tool Integration Strategy

### Integration with Claude Code

Create .claude/CLAUDE.md file in project root:

```
# Project Development Rules

## Must Follow (MUST)
- Use @Valid annotation in Controllers
- Business logic validation in Service layer
- Data access through Repository pattern

## Recommendations (SHOULD)  
- Separate interface and implementation
- Use @Async for asynchronous processing
- Set clear transaction boundaries

## Prohibited
- Return Entity directly from Controller
- Direct HttpServletRequest access in Service
- Hardcoded configuration values
```

### GitHub Copilot Optimization

Configure IDE settings to prioritize these context files:

- DEVELOPMENT_RULES.md / AGENTS.md: Extracted development rules
- ARCHITECTURE_GUIDE.md: Architecture pattern guide
- DOMAIN_CONSTRAINTS.md: Business rules summary

## Methodology Limitations and Cautions

### Method Limitations

**Observation Bias**: Patterns visible in code aren't always intentional rules. Legacy or temporary implementations may be mistaken for incorrect rules.

**Context Deficiency**: AI may not fully understand business requirement changes or reasoning behind technical decisions.

**Static Analysis Limitations**: Runtime behavior and environment-specific configuration differences are hard to grasp from code analysis alone.

### Importance of Verification Process

Extracted rules must undergo the following verification:

1. **Team Review**: Senior developer review and rule approval
2. **Practical Testing**: Test rule application in real development work
3. **Continuous Updates**: Update rules as project evolves

## Operations Guidelines

### Rule Management Process

**Monthly Rule Review**:

- Analyze patterns in newly added code
- Measure rule compliance rates
- Improve rules based on team feedback

**Quarterly Full Re-extraction**:

- Reanalyze entire codebase
- Reflect architectural changes
- Discover new domain rules

### Team Onboarding Process

When new team members join:

1. **Week 1**: Learn extracted rule documentation
2. **Week 2**: Practice rule application with simple tasks
3. **Week 3**: Apply rules in real development using verification tools
4. **Week 4**: Provide rule improvement suggestions and feedback

## Effectiveness Measurement

Adoption effects can be measured through:

**Quantitative Metrics**:

- Code review time reduction ratio
- Bug reduction from rule violations
- Time to first PR approval for new members

**Qualitative Metrics**:

- Team satisfaction with code consistency
- Perceived code quality improvement from AI tools
- Onboarding process systematization evaluation

## Conclusion

Meta-prompt-based development rule extraction is not just a tool but a methodology for systematizing team development culture. Through this approach, implicit knowledge becomes explicit, improving productivity and code quality across the entire team.

The important point is that extracted rules must become living documents that evolve with project growth, maintaining practicality through continuous team feedback.

This systematic approach establishes foundations for development teams in the AI era to produce more efficient and consistent code.
