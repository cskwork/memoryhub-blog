- When you look at `kubectl get pods` and see STATUS filled with `CrashLoopBackOff`, `Error`, or `Terminating`, it's hard to know where to start looking.
- In fact, these messages are all stepwise events unfolding within a larger flow called "lifecycle."
- Understanding the flow makes it clear *where* to start checking when something breaks and *how long* to wait.
- This guide organizes the Pod-centric lifecycle in concept → practice → best practices order, so you can apply it immediately to real-world troubleshooting.

**Kubernetes lifecycle is "the entire journey of a Pod/container from creation → readiness → service → termination," and looking at Phase, Condition, and Container State together makes the root cause visible.**

## Background

- **Why should you know about lifecycle?**
  - "Can't I just create a Deployment and let it run?" → When something breaks, you eventually have to look at Pod-level status.
  - Autoscaling, rolling updates, health checks, graceful shutdown—all these operational features run on top of lifecycle.
- **Scope of lifecycle covered in this guide**
  - Pod lifecycle (core)
  - Container lifecycle & Hooks (postStart / preStop)
  - Brief mention of Job/version lifecycle
- **Terminology**

| Term | Meaning | Example/Note |
| --- | --- | --- |
| Pod Phase | Rough summary of overall Pod status | Pending, Running, Succeeded, Failed, Unknown ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle")) |
| Pod Condition | Flags indicating Pod readiness | PodScheduled, Initialized, ContainersReady, Ready ([LeeHosu](https://leehosu.github.io/k8s-pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle in Kubernetes - LakeScript")) |
| Container State | Detailed execution status of each container | Waiting, Running, Terminated ([Velog](https://velog.io/%40jayoh/%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4-%ED%8C%A8%ED%84%B4-5%EC%9E%A5-%EC%88%98%EB%AA%85%EC%A3%BC%EA%B8%B0-%EA%B4%80%EB%A6%AC?utm_source=chatgpt.com "Kubernetes Patterns - Chapter 5 Lifecycle Management")) |
| Lifecycle Hook | Hooks that run when a container starts/stops | postStart, preStop ([Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/?utm_source=chatgpt.com "Container Lifecycle Hooks")) |
| Grace Period | Time to wait for graceful shutdown on termination (default 30s) | `terminationGracePeriodSeconds` |
| Kubernetes Version Lifecycle | Community minor/patch releases and support period cycles | As of November 2025, v1.34.x recommended as stable version ([Kubernetes](https://kubernetes.io/releases/?utm_source=chatgpt.com "Releases")) |

## Core Concepts

> Kubernetes lifecycle is the entire flow of a Pod/container **creating → scheduling → running → health checking → stopping → cleanup**.

- **Core Summary**
  - A Pod has a Phase of `Pending → Running → (Succeeded | Failed | Unknown)`.([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle"))
  - Simultaneously, Condition (readiness) and Container State (Waiting/Running/Terminated) move separately.
  - On termination, the flow is `preStop → SIGTERM → Grace Period → SIGKILL → resource cleanup`.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
  - Higher-level resources like Job/CronJob and Deployment orchestrate retries and rolling updates on top of this Pod lifecycle.([Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/job/?utm_source=chatgpt.com "Jobs"))

### 1) Pod Phase – "The Big Picture" Status

- **Phase Types** (per Kubernetes official definition)([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle"))
  - `Pending`: Spec created but not yet scheduled on a Node or containers not started due to image pulling, etc.
  - `Running`: Scheduled on a Node, containers created, at least one running
  - `Succeeded`: All containers terminated with exit code 0, not restarted (typically Job)
  - `Failed`: All containers terminated, at least one with non-zero exit code
  - `Unknown`: Unable to determine status due to node communication issues, etc.
- Remember that `CrashLoopBackOff`, `ImagePullBackOff`, etc. shown in the STATUS column are **detailed Reasons, not Phases**.

### 2) Pod Conditions – "Service Readiness"

- Main Conditions ([LeeHosu](https://leehosu.github.io/k8s-pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle in Kubernetes - LakeScript"))
  - `PodScheduled`: Has this Pod been placed on a Node?
  - `Initialized`: Have all Init containers succeeded?
  - `ContainersReady`: Are all containers ready?
  - `Ready`: Can we send traffic to this Pod? (whether it's included in service load balancer pool)
- In practice, just looking at **the time changes in Condition via `kubectl describe pod`** makes it clear "when did traffic start reaching this Pod?"

### 3) Container State – "The Details"

- Each container has its own state: `Waiting`, `Running`, `Terminated`.([Velog](https://velog.io/%40jayoh/%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4-%ED%8C%A8%ED%84%B4-5%EC%9E%A5-%EC%88%98%EB%AA%85%EC%A3%BC%EA%B8%B0-%EA%B4%80%EB%A6%AC?utm_source=chatgpt.com "Kubernetes Patterns - Chapter 5 Lifecycle Management"))
  - `Waiting`: Pulling an image, applying Secrets/Config, etc.
  - `Running`: Running normally
  - `Terminated`: Stopped (with success/failure code)
- If Phase is `Running` but Container State is `Waiting`, suspect image pulling, startup delays, postStart hook issues, etc.

### 4) Startup Lifecycle (Activation)

1. User submits Pod spec (`kubectl apply -f ...`).
2. API Server saves to etcd → Scheduler selects a node.
3. Kubelet on selected node pulls image, creates container, mounts volumes.
4. Init containers → main containers run in order.
5. Container starts, Readiness Probe succeeds, `Ready=True`, Pod included in service traffic targets.

### 5) Termination Lifecycle (Termination)

1. `kubectl delete pod` or higher-level resource (Deployment, Job) requests Pod deletion.
2. API Server sets `deletionTimestamp` on Pod → UI shows `Terminating`.
3. Pod removed from Endpoints → no new traffic enters.
4. Container's `preStop` hook runs → followed by `SIGTERM` sent.
5. System waits `terminationGracePeriodSeconds`, then `SIGKILL` if not finished.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
6. After termination, Pod info removed from etcd.

## Hands-On Practice

## Kubernetes v1.34.x (Latest stable as of November 2025) ([Kubernetes](https://kubernetes.io/releases/?utm_source=chatgpt.com "Releases"))

`kubectl` available, at least 1-node cluster (minikube, kind, EKS, GKE, etc.)

1. **Check environment and prepare namespace**
   - Verify cluster/client version:
   - `kubectl version --short
     kubectl get nodes`
   - Create practice namespace:
   - `kubectl create ns lifecycle-demo
     kubectl config set-context --current --namespace=lifecycle-demo`

2. **Deploy basic Pod and observe Phase/Condition**
   - **Pod manifest (Language: YAML, Target: Kubernetes v1, v1.34)**  
     `simple-pod.yaml`:
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: demo-pod
     labels:
     app: lifecycle-demo
     spec:
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo START && sleep 300"]`
   - Deploy and check status:
   - `kubectl apply -f simple-pod.yaml
     kubectl get pods -w`
   - Expected output (text capture alternative):
   - `NAME READY STATUS RESTARTS AGE
     demo-pod 0/1 Pending 0 3s
     demo-pod 1/1 Running 0 10s`
   - Check detailed status:
     - Confirm Status: Running, Ready=True in Conditions, Container State is Running.
   - `kubectl describe pod demo-pod`

3. **Experience Failed/CrashLoopBackOff with a failing Pod**
   - Example of container that exits immediately (`fail-pod.yaml`):
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: fail-pod
     spec:
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo FAILING && exit 1"]
     restartPolicy: OnFailure`
   - Deploy and observe status:
   - `kubectl apply -f fail-pod.yaml
     kubectl get pods -w`
   - Expected text output example:
   - `NAME READY STATUS RESTARTS AGE
     fail-pod 0/1 Error 0 5s
     fail-pod 0/1 CrashLoopBackOff 1 15s`
   - `kubectl get pod fail-pod -o yaml | grep phase` shows Phase might be `Failed`, events log exit code 1.
   - What you see here:
     - STATUS column's `Error/CrashLoopBackOff` is **the result of container restart policy and failure record**.
     - Pod Phase is "overall lifetime summary", events/State is "detailed cause"—you can feel this difference.

4. **See termination lifecycle with preStop Hook**
   - Pod simulating graceful shutdown (`hook-pod.yaml`):
   - `apiVersion: v1
     kind: Pod
     metadata:
     name: hook-pod
     labels:
     app: lifecycle-demo
     spec:
     terminationGracePeriodSeconds: 20
     containers:
     - name: main
     image: busybox:1.36
     command: ["sh", "-c", "echo RUNNING && while true; do date; sleep 2; done"]
     lifecycle:
     preStop:
     exec:
     command: ["sh", "-c", "echo PRESTOP START; sleep 10; echo PRESTOP END"]`
   - Deploy and check logs:
   - `kubectl apply -f hook-pod.yaml
     kubectl logs -f hook-pod`
   - Delete Pod in another terminal:
   - `kubectl delete pod hook-pod
     kubectl get pod hook-pod -w`
   - Expected log/status flow (text capture alternative):
   - `# logs
     RUNNING
     Fri Nov 14 00:00:01 UTC 2025
     Fri Nov 14 00:00:03 UTC 2025
     PRESTOP START
     PRESTOP END
     # status
     NAME READY STATUS AGE
     hook-pod 1/1 Running 20s
     hook-pod 1/1 Terminating 32s
     hook-pod 0/1 Terminating 40s
     hook-pod 0/1 Completed 41s (then disappears from list)`
   - What you see here:
     - Right after `kubectl delete`, STATUS changes to `Terminating`, during which **preStop + SIGTERM + Grace Period** all happen.([Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/attach-handler-lifecycle-event/?utm_source=chatgpt.com "Attach Handlers to Container Lifecycle Events"))
     - Since preStop used 10 seconds, graceful shutdown timeout should be set to 20+ seconds generously.

## Best Practices / Pattern Comparison

| Pattern | Advantages | Cautions |
| --- | --- | --- |
| Readiness/Liveness Probe + lifecycle-based deployment | Automatically restart broken containers, traffic doesn't go to unprepared Pods | Setting Probe timeout/failureThreshold too aggressively can mark normal startup delays as failures ([Velog](https://velog.io/%40jayoh/%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4-%ED%8C%A8%ED%84%B4-5%EC%9E%A5-%EC%88%98%EB%AA%85%EC%A3%BC%EA%B8%B0-%EA%B4%80%EB%A6%AC?utm_source=chatgpt.com "Kubernetes Patterns - Chapter 5 Lifecycle Management")) |
| preStop Hook + sufficient Grace Period | Enable stable shutdown: DB connection cleanup, session flush, etc. | If preStop takes longer than `terminationGracePeriodSeconds`, still ends with SIGKILL; design hooks lightly ([Kubernetes](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/?utm_source=chatgpt.com "Container Lifecycle Hooks")) |
| Job/CronJob with explicit `backoffLimit` and `restartPolicy` | Clearly control retry count and failure criteria for one-off/batch work | Using default (e.g., backoffLimit=6) without thought lets failed Jobs retry too long, consuming resources ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/job/?utm_source=chatgpt.com "Jobs")) |
| Monitor Pod status looking at Phase + Condition + Container State together | Quickly understand "when did it become Ready and why did it fail?" instead of just one STATUS line | Habit of watching Phase alone in dashboards makes it easy to miss real causes (image pull fail, hook error, probe fail, etc.) ([Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/?utm_source=chatgpt.com "Pod Lifecycle")) |
| Regular upgrades aligned with version lifecycle (e.g., staying on v1.34 track) | Stable reflection of security/bug patches before support ends | Without cluster/app test strategy, upgrades become "big events" and progress stalls ([Kubernetes](https://kubernetes.io/releases/?utm_source=chatgpt.com "Releases")) |

## Closing Remarks

- Kubernetes lifecycle is not "a concept to memorize once and for all," but a **frame for interpreting Pod status**.
- Checking Phase (big picture) → Condition (service readiness) → Container State/events (details) in order definitely speeds up troubleshooting.
- (Practical tip to share with your team)
  - At your next team meeting, try framing it like this: **"STATUS is just the cover; you have to look at Pod lifecycle together to see the real cause of a failure."**
