**Written:** September 26, 2025
**Authors:** Kenton Varda, Sunil Pai
**Reading Time:** 9 minutes

It turns out we've all been using MCP wrong.

Currently, most agents use MCP by directly exposing "tools" to LLMs.

But we tried a different approach. We converted MCP tools into TypeScript APIs and then asked the LLM to write code calling this API.

The results were surprising.

When providing tools as TypeScript APIs instead of directly exposing them, agents could handle many more and much more complex tools. This is probably because LLM training data contains huge amounts of real TypeScript code, but few artificial examples of tool calls.

This approach particularly shines when agents need to chain multiple calls together. In the conventional approach, the output of each tool call has to pass through the LLM's neural network and be simply copied as input to the next call, wasting time, energy, and tokens. But if the LLM can write code, it can skip all this and just read the final result it needs.

In summary: LLMs are better at writing code that calls MCP than directly calling MCP.

## What is MCP?

For those unfamiliar, the Model Context Protocol is a standard protocol that gives AI agents access to external tools. It allows them to not just chat but actually perform tasks directly.

From another perspective, MCP provides an integrated way to:

- Expose APIs for doing something
- Documentation needed for LLM understanding
- Handle authentication out of band

MCP has received significant attention throughout 2025, greatly expanding AI agent capabilities.

The "API" exposed by MCP servers is represented as a series of "tools". Each tool is essentially a remote procedure call (RPC) function. Called with parameters, it returns a response. Most modern LLMs have the ability to use "tools" (sometimes also called "function calling"). That is, they're trained to output text in a specific format when they want to call tools. The program calling the LLM recognizes this format, calls the tool as specified, then passes the result back as input to the LLM.

## Structure of Tool Calling

Internally, LLMs generate a stream of "tokens" representing output. Tokens can represent words, syllables, punctuation, or other text components.

But tool calls include tokens that have no text equivalent. LLMs are trained (or more often fine-tuned) to output special tokens meaning "the following should be interpreted as a tool call" and another special token meaning "end of tool call". Between these two tokens, LLMs typically write tokens corresponding to a JSON message describing the call.

For example, if you connect an agent to an MCP server providing weather information and ask about weather in Austin, Texas, the LLM might internally generate output like this. Here, words between `<|` and `|>` represent special tokens, but don't actually represent text. This is for explanation:

```
I'll use the weather MCP server to find weather for Austin, Texas.

<|tool_call|>
{
  "name": "get_current_weather",
  "arguments": {
    "location": "Austin, TX, USA"
  }
}
<|end_tool_call|>
```

When the harness detects these special tokens in the output, it interprets this sequence as a tool call. After confirming the end token, the harness pauses LLM execution. It parses the JSON message and returns as separate components of structured API results. The agent calling the LLM API recognizes the tool call, calls the relevant MCP server, then sends the result back to the LLM API. The LLM harness then passes the result back to the LLM using another set of special tokens:

```
<|tool_result|>
{
  "location": "Austin, TX, USA",
  "temperature": 93,
  "unit": "fahrenheit",
  "conditions": "sunny"
}
<|end_tool_result|>
```

The LLM reads these tokens exactly like it reads user input. Except users can't generate these special tokens, so the LLM knows this is a tool call result. The LLM then continues generating output normally.

Different LLMs may use different formats for tool calling, but the basic idea is the same.

## What's the Problem?

The special tokens used for tool calls are things LLMs have never seen in real environments. They must be specially trained on synthetic training data to use tools. That's why they don't always do it well. If you give LLMs too many tools or overly complex tools, they may struggle to choose the right tool or use it correctly. As a result, MCP server designers recommend providing APIs to developers that are significantly simplified compared to the underlying APIs.

Meanwhile, LLMs are becoming really good at writing code. In fact, when asked to write code targeting complete, complex APIs typically exposed to developers, LLMs seem to handle it without major difficulty. So why should the MCP interface be "simplified"? Code writing and tool calling are almost the same thing, yet LLMs seem much better at one than the other.

The answer is simple. LLMs have seen a lot of code. They haven't seen many "tool calls". In fact, tool calls LLMs have seen are probably limited to artificial training sets constructed by LLM developers themselves for training. On the other hand, they've seen real code from millions of open-source projects.

Having LLMs perform tasks using tool calls is like giving Shakespeare a month of Chinese lessons and asking him to write a play in Chinese. His greatest works won't come out.

## But MCP is Still Useful. Because of Uniformity.

MCP was designed for tool calling, but doesn't actually need to be used that way.

The "tools" exposed by MCP servers are really just RPC interfaces with attached documentation. You don't need to expose them as tools. You can take tools and convert them into programming language APIs.

But why do that when programming language APIs already exist independently? Almost every MCP server is just a wrapper around an existing traditional API. Why not expose that API?

MCP actually does something else that's really useful. It provides a unified way to connect to and learn APIs.

AI agents can use MCP servers even if the agent developers have never heard of that specific MCP server, and MCP server developers have never heard of that specific agent. This rarely happened with traditional APIs in the past. Usually, client developers always knew exactly what API they were coding against. As a result, every API could do basic things like connections, authentication, and documentation slightly differently.

This uniformity is also useful when AI agents write code. We want AI agents to run in a sandbox where they can only access the tools we provide. By handling connections and authentication in a standard way independent of AI code, MCP allows agent frameworks to implement this. Also, AIs don't need to search the internet to find documentation. MCP provides documentation directly in the protocol.

## So How Does It Work?

We've already extended Cloudflare Agents SDK to support this new model!

For example, suppose an app built with ai-sdk looks like this:

```
const stream = streamText({
  model: openai("gpt-5"),
  system: "You are a helpful assistant",
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ],
  tools: {
    // tool definitions
  }
})
```

You can use it in the app by wrapping tools and prompts with the `codemode` helper:

```
import { codemode } from "agents/codemode/ai";

const {system, tools} = codemode({
  system: "You are a helpful assistant",
  tools: {
    // tool definitions
  },
  // ...settings
})

const stream = streamText({
  model: openai("gpt-5"),
  system,
  tools,
  messages: [
    { role: "user", content: "Write a function that adds two numbers" }
  ]
})
```

With this change, the app now begins generating and executing code that calls the tools you defined (including MCP servers). In the near future, we plan to introduce variants for other libraries. See the documentation for more details and examples.

## Converting MCP to TypeScript

When connecting to an MCP server in "code mode", Agents SDK fetches the MCP server's schema and converts it into a TypeScript API with documentation comments based on the schema.

For example, connecting to an MCP server at `https://gitmcp.io/cloudflare/agents` generates TypeScript definitions like this:

```
interface FetchAgentsDocumentationInput {
  [k: string]: unknown;
}
interface FetchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsDocumentationInput {
  /**
   * Search query to find relevant documentation
   */
  query: string;
}
interface SearchAgentsDocumentationOutput {
  [key: string]: any;
}

interface SearchAgentsCodeInput {
  /**
   * Search query to find relevant code files
   */
  query: string;
  /**
   * Page number to search (starting from 1). Each page contains 30 results.
   */
  page?: number;
}
interface SearchAgentsCodeOutput {
  [key: string]: any;
}

interface FetchGenericUrlContentInput {
  /**
   * URL of the documentation or page to fetch
   */
  url: string;
}
interface FetchGenericUrlContentOutput {
  [key: string]: any;
}

declare const codemode: {
  /**
   * Fetches complete documentation files from GitHub repository cloudflare/agents.
   * Useful for general questions. When asked about cloudflare/agents,
   * always call this tool first.
   */
  fetch_agents_documentation: (
    input: FetchAgentsDocumentationInput
  ) => Promise<FetchAgentsDocumentationOutput>;

  /**
   * Semantically searches within documentation fetched from GitHub repository
   * cloudflare/agents. Useful for specific queries.
   */
  search_agents_documentation: (
    input: SearchAgentsDocumentationInput
  ) => Promise<SearchAgentsDocumentationOutput>;

  /**
   * Searches code within GitHub repository "cloudflare/agents" using GitHub Search API
   * (exact match). Returns matching files that can be queried further if relevant.
   */
  search_agents_code: (
    input: SearchAgentsCodeInput
  ) => Promise<SearchAgentsCodeOutput>;

  /**
   * Generic tool that fetches content from any absolute URL while respecting robots.txt rules.
   * Use to search for reference URLs (absolute URLs) mentioned in previously fetched documentation.
   */
  fetch_generic_url_content: (
    input: FetchGenericUrlContentInput
  ) => Promise<FetchGenericUrlContentOutput>;
};
```

This TypeScript is loaded into the agent's context. Currently, the entire API is loaded, but future improvements could allow agents to discover and explore the API more dynamically. Much like what agent coding assistants do.

## Running Code in Sandbox

Instead of being provided all tools from all connected MCP servers, agents receive just one tool: executing TypeScript code.

The code then runs in a safe sandbox. The sandbox is completely isolated from the internet. The only access to the outside world is through the TypeScript API representing connected MCP servers.

These APIs are backed by RPC calls that call back into the agent loop. There, Agents SDK routes the calls to the appropriate MCP server.

Sandbox code returns results to the agent in an obvious way: by calling `console.log()`. When the script completes, all output logs are passed back to the agent.

## Dynamic Worker Loading: No Containers Here

This new approach requires access to a safe sandbox that can execute arbitrary code. So where can we find it? Do we need to run containers? Is it expensive?

No. No containers. There's something much better. Isolates.

The Cloudflare Workers platform has always been based on V8 isolates—isolated JavaScript runtimes powered by the V8 JavaScript engine.

Isolates are much lighter than containers. They use only a few megabytes of memory and can start in just a few milliseconds.

Because isolates are so fast, we can create a new isolate for every code snippet the agent executes. No need for reuse. No need for pre-warming. Just create when needed, run the code, and discard. Everything is so fast that overhead is negligible. It's almost like directly `eval()`-ing the code. But security is maintained.

## Worker Loader API

But until now, there was no way for Workers to directly load isolates containing arbitrary code. All Worker code had to be uploaded through the Cloudflare API, and then deployed globally so it could run anywhere. But that's not what we want with agents. We want the code to run right where the agent is.

To enable this, we added a new API to the Workers platform: the Worker Loader API. This lets us load Worker code on demand. It looks like this:

```
// Get a Worker with the given ID. If it doesn't exist, create it.
let worker = env.LOADER.get(id, async () => {
  // If the Worker doesn't exist yet, this callback is called to fetch the code.

  return {
    compatibilityDate: "2025-06-01",

    // Specify the Worker's code (module files)
    mainModule: "foo.js",
    modules: {
      "foo.js":
        "export default {\n" +
        "  fetch(req, env, ctx) { return new Response('Hello'); }\n" +
        "}\n",
    },

    // Specify the dynamic Worker's environment (`env`)
    env: {
      // Can contain basic serializable data types...
      SOME_NUMBER: 123,

      // ... and bindings to the parent Worker's exported RPC interface
      // using the new `ctx.exports` loopback binding API
      SOME_RPC_BINDING: ctx.exports.MyBindingImpl({props})
    },

    // Redirect the Worker's `fetch()` and `connect()` to proxy through
    // the parent Worker to monitor or filter all internet access.
    // Can also pass `null` to completely block internet access.
    globalOutbound: ctx.exports.OutboundProxy({props}),
  };
});

// Now get the Worker's entrypoint and send it requests.
let defaultEntrypoint = worker.getEntrypoint();
await defaultEntrypoint.fetch("http://example.com");

// Can also get non-default entrypoints and specify `ctx.props` values
// to pass to the entrypoint.
let someEntrypoint = worker.getEntrypoint("SomeEntrypointClass", {
  props: {someProp: 123}
});
```

You can use this API right now when running workerd locally with Wrangler (check the documentation), and can register for beta access to use it in production.

## Workers is a Better Sandbox

Workers design excels at sandboxing, especially for this use case. There are a few reasons:

### Faster, Cheaper, Disposable Sandboxes

The Workers platform uses isolates instead of containers. Isolates are much lighter and start faster. It takes only a few milliseconds to start a new isolate, and it's so cheap we can create a new isolate for every code snippet the agent generates. No need to worry about pooling or pre-warming isolates for reuse.

We haven't finalized pricing for the Worker Loader API yet, but because it's based on isolates, we should be able to offer it at much lower cost than container-based solutions.

### Isolated by Default, But Connected Through Bindings

Workers excel at handling isolation.

In code mode, we forbid the sandboxed worker from communicating with the internet. The global `fetch()` and `connect()` functions throw errors.

But this is a problem on most platforms. On most platforms, the way to access private resources typically starts with general network access. Then you use that network access to send a request to a specific service and pass some kind of API key to authorize private access.

But Workers have always had a better answer. In Workers, "environment" (the env object) doesn't just contain strings—it contains live objects also called "bindings". These objects can access private resources directly without normal network requests.

In code mode, we grant the sandbox access to bindings representing connected MCP servers. So agents can specifically access those MCP servers without general network access.

Restricting access through bindings is much cleaner than network-level filtering or HTTP proxies. Filtering is hard for both LLMs and supervisors. The boundaries are often unclear. Supervisors might struggle to identify exactly what traffic is legitimately needed to communicate with an API. Meanwhile, LLMs might struggle to guess what kinds of requests will be blocked. With the binding approach, it's clearly defined. Bindings provide a JavaScript interface, and you can use that interface. This approach is much better.

### No API Key Leaks

An additional benefit of bindings is hiding API keys. The binding itself provides an already-authenticated client interface to the MCP server. Every call made here first goes to the agent supervisor, who holds the access token and adds it to requests sent to MCP.

This means AI cannot write code that leaks keys, solving a common security problem in AI-generated code today.
