In a class with 1 teacher and up to 12 students, you want to create a web application that shares drawings on the teacher's canvas with all students **in near real-time (with latency of less than 1 second)**. Basically, **drawing permission belongs to the teacher**, but in some cases, **students also draw and transmit to the teacher**. Total participants are **small-scale (1 to 12)**, and **real-time responsiveness is very important** (response within 1 second). In this scenario, web communication technologies like **WebSocket**, **WebRTC**, **Server-Sent Events (SSE)**, and **HTTP Polling** are considered. Let me compare their **advantages/disadvantages** and **implementation considerations**. The following table compares these technologies across major aspects:

## WebSocket vs WebRTC vs SSE vs HTTP Polling Comparison

| **Category** | **WebSocket** | **WebRTC** | **Server-Sent Events (SSE)** | **HTTP Polling** |
| --- | --- | --- | --- | --- |
| **Communication Method** | Persistent server-client connection (TCP-based): After initial HTTP handshake, upgrades to dedicated WebSocket protocol for bidirectional message exchange through central server. Once connected, multiple messages exchanged in same session (full-duplex communication). | Peer-to-peer (P2P) direct connection: Direct data exchange between browsers. Primarily uses UDP-based media streams (video/audio) + SCTP-based data channels. No need for central server after initial signaling, but uses server for initial signaling. Basic mesh connection: n peers form maximum n(n-1)/2 connections (e.g., 45 connections with 10 people) → P2P complexity increases with more participants. | Server→Client unidirectional streaming: Maintains existing HTTP connection where server pushes data unilaterally. Sends continuous response stream with text/event-stream MIME type (clients receive via EventSource API). HTTP-based protocol: Operates without separate upgrade, leverages HTTP/1.1 or HTTP/2 long-connection features. | Periodic HTTP requests: Client periodically requests from server if new updates exist, or Long Polling style where server delays requests until data is ready then responds. Restarts new connection after each request-response. |
| **Bidirectional Data Transmission Support** | Full-duplex: Both server and client can freely transmit data. Teacher sends drawing content to students, and student feedback can also be transmitted through same server channel. | Bidirectional P2P: Enables direct real-time data exchange between clients via DataChannels. Teacher and each student establish individual P2P connections to exchange data. (However, connection count increases rapidly with n people.) | Unidirectional: Server → Client only. Cannot send data from client to server via SSE; requires separate AJAX/fetch requests. Hard to handle student→teacher transmission with SSE alone; needs additional channel. | Quasi-bidirectional: Basically client request → server response half-duplex. To implement real-time bidirectional, must emulate with client→server polling and server→client response/long-response. Natural simultaneous bidirectional interaction is difficult. |
| **Latency (Real-time)** | Low latency: After initial connection, data transmits immediately in persistent connection state without additional handshakes enabling instantaneous delivery. No HTTP headers repeated per message minimizing latency. Real-world tests show WebSocket highest real-time performance. Near-real-time (<0.1 second) updates possible. | Very low latency: P2P direct connection and UDP usage minimize retransmission on packet loss, media stream protocol designed for minimum delay. Thus optimal for real-time streams like audio/video. Drawing data transmission maintains very low latency. However, initial connection setup (SDP exchange, NAT traversal) takes some time. Simultaneous peer increase complicates P2P mesh latency control. | Low latency: Server immediately pushes to all clients on event occurrence, so transmission itself near real-time. Frequent updates within 1 second possible via SSE stream. However, transmission data is text-based so binary drawing images need encoding adding overhead and latency factors. For small text events, latency similar to WebSocket. | Relatively high latency: Without tight polling intervals, must wait until next request after event occurrence causing latency. 1-second polling cycle causes ~0.5 second average latency; shorter intervals increase server load. Long polling can reduce latency by responding immediately, but reconnection time after response disadvantages continuous events. Overall, real-time capability falls short compared to other technologies. |
| **Data Format and Bandwidth** | Supports both text/binary: WebSocket supports binary data frames enabling direct transmission of bitmap image data without conversion. No additional encoding needed—efficient. Low overhead: Maintained connection means no HTTP header per message; frame-unit communication efficiently handles very small messages. Frequent drawing sends without repeated header transmission provide high bandwidth efficiency. | Media stream optimized: WebRTC specialized in continuous stream transmission like video/audio. Transmits large binary data (video frames) via UDP, adjusts bandwidth based on network quality. However, P2P structure requires transmitting identical data separately per participant. Example: teacher sending drawing to 12 students requires uploading identical image 12 times, creating heavy teacher uplink load. (SFU server enables one upload then distribution, but then little advantage over WebSocket.) Thus simple drawing sharing may be bandwidth-inefficient. | Text-based transmission: Supports UTF-8 text streams only; must text-encode image binaries via Base64 etc. Causes 30%+ additional payload increase and encoding/decoding cost. Inefficient for frequent image transmission. Broadcast efficiency: Server sends identical text events to each client separately, somewhat relieved with HTTP/2 single connection multiplexing. Better suited for small text event streams than large binary data. | HTTP header overhead: Every request carries HTTP header round-trip transmission with significant extra data. Frequent polling makes header bandwidth ratio larger than actual payload—inefficient. Unnecessary data transmission: Regular requests generate responses and overhead even without changes, consuming unnecessary bandwidth. Frequent image data sending repeats identical images or triggers requests despite no changes. Overall unsuitable for real-time bulk transmission. |
| **Server Configuration and Implementation Difficulty** | Requires dedicated server: Needs WebSocket-handling backend server (e.g., Node.js ws or Socket.IO library). Server must handle multiple persistent connections via event-loop-based implementation. Load balancer or reverse proxy needs WebSocket protocol support configuration (HTTP Upgrade support). Implementation difficulty: Browser provides basic WebSocket API enabling relatively easy connection, but additional auth/reconnection/extension handling needed. Socket.IO and similar libraries improve implementation convenience. | Complex infrastructure required: Needs signaling server (initial connection negotiation) and STUN/TURN servers (securing P2P path). 13 people P2P connection increases management complexity rapidly. Generally requires SFU/MCU media servers for WebRTC multi-party communication—expert solution implementation (e.g., Janus, mediasoup) with high difficulty. Implementation difficulty: WebRTC API exists in browser but peer connection acceptance/management and error handling are difficult. P2P-only configuration complicates app, server-relay structure reduces WebRTC advantages. | Easy implementation: SSE only requires generating HTTP response stream, simple implementation with existing web servers (e.g., Express) by keeping Content-Type: text/event-stream response open. Client easily receives via browser EventSource API. No special protocol upgrade or complex handshake needed. Server load handling: Maintaining response stream connections constantly per client makes async-efficient servers advantageous. HTTP/2 enables multiplexing multiple SSE channels over single TCP connection though browser implementation issues exist. | Low implementation difficulty: Needs no special server functionality—implementable via simple REST API. Client easily implements repeated requests with setInterval or recursive fetch. Works in legacy environments. Server load management: Easy implementation but polling interval adjustment critical. Short intervals cause server request surge, long intervals reduce real-time quality. Long polling requires server to hold requests specific duration, requiring thread or async processing consideration. |
| **Browser Compatibility** | Broad support: WebSocket (RFC 6455) basically supported by all major browsers. Compatible with IE10+, Chrome, Firefox, Safari, Edge, etc. Mobile also supported through WebView—very high compatibility. | Modern browsers and apps: Chrome, Firefox, Safari, Edge support. Mobile apps leverage WebRTC native APIs. However, legacy browsers (old IE) not supported; browser implementation differences occasionally cause compatibility issues. Private network environments face P2P constraints—TURN server absence causes operation problems. | Limited compatibility: EventSource API supported in Chrome, Firefox, Safari but not legacy IE browsers. (Pre-Chromium Edge also unsupported) Thus requires fallback (e.g., hidden iframe, polling) for those browsers. Otherwise good compatibility on most browsers. | Universal compatibility: Uses only HTTP requests functioning on all browsers. Not special API—highest compatibility including legacy environments. (Works wherever AJAX functions). |
| **Scalability (Multiple Access)** | Server resource consumption: WebSocket maintains open server sockets for persistent connections; increasing users increases memory/connection resources. 1:12 scale no issue, but thousands require horizontal scaling or message brokers. Yet real-world cases handle tens of thousands connections per server. | P2P scaling limit: Peer increase rapidly multiplies connections—practically P2P Mesh impractical for 3+ person groups. 12-person class all P2P connections hard to manage. Large scale requires SFU etc., loading server with increased complexity. Essentially WebRTC suited for small real-time communication (few people), unsuitable for 10+ simultaneous participants. | Increasing server load: Server must send client-count messages on event occurrence; more participants increase load. Also browser connection limits (6 per domain) impact; multiple tabs limit new SSE connection creation. 12-person scale no issue, but SSE for thousands requires browser constraint and server memory considerations. | Non-linear load increase: Increasing clients increases request frequency linearly—12 people polling every second = 12req/s, 100 people = 100req/s. Server burden processing mostly unnecessary responses when considering load. Worst scalability. Large services experience network overload and increased server costs via polling. |
| **Representative Advantages** | True real-time bidirectional communication: Server and client freely exchange information when needed enabling interactive app implementation. Examples: chat, multiplayer games, online whiteboard collaboration. Low overhead and high performance: Maintaining connection removes repeated request/response overhead, efficiently handles high-frequency messages. Particularly advantageous for event-based updates (drawing changes) real-time broadcasting. Easy binary transmission: Transmit binary data like images and files without conversion. | Ultra-low latency P2P communication: Designed for high-quality low-latency media (video/audio) transmission. Optimal for video conferencing, live streaming. Direct inter-participant communication without central server improves bandwidth efficiency (small groups) and privacy. Multimedia and P2P collaboration: Real-time media sharing (camera/mic access) and screen sharing, file transfer without central server. DataChannel enables P2P file transfer and document collaboration. | Simple implementation and auto-reconnection: Can simply implement server push functionality; browser auto-reconnection support aids recovery from temporary network instability. Without special framework operates via HTTP stream enabling relatively easy and lightweight real-time feature addition. HTTP-friendly: Advantages passing existing firewalls/proxies; naturally integrates in HTTP environment. WebSocket protocol-specific advantages minimize infrastructure changes. | Simplicity and universality: Conceptually simplest—easy implementation. No additional protocol—just periodic REST API calls making debugging straightforward. Works in legacy systems or limited environments—highest compatibility. No special server configuration: Works on standard web servers enabling rapid implementation in small scale or budget-limited systems. |
| **Representative Disadvantages** | Server and infrastructure burden: Persistent connection maintenance risks socket and memory exhaustion if server poorly handles multiple connections. Proxy/firewall constraints sometimes block WebSocket traffic requiring fallback. Manual reconnection: Basic WebSocket API lacks automatic retry on connection loss requiring separate implementation. (Socket.IO has built-in support). Security also requires post-handshake authentication/authorization direct management without additional headers. | Implementation complexity/extension limits: Requires multiple server components (STUN/TURN) and complex procedures (WebRTC signal exchange)—high learning curve and difficult debugging. Browser compatibility issues exist. P2P becomes unpractical with participant increase; large-scale expansion unsuitable. Central control difficulty: Server unavailability scatters all data making central logging/control difficult; P2P network formation failure handling complex. (Actually multi-party needs server assistance reducing advantages vs WebSocket.) | Unidirectional limitation: No client→server transmission path making complete bidirectional applications difficult. May require SSE + AJAX mixing causing complexity. Real-time collaborative tools limited to one-directional feeds. Binary data inefficiency: Cannot send binary data directly requiring text conversion—CPU/capacity burden. Unsuitable for large-scale real-time transmission (high-resolution continuous canvas transmission). Legacy browser compatibility issues exist. | Low efficiency & latency: Short polling intervals cause server load and network waste. Conversely, long intervals worsen real-time quality—dilemma. Long-term, lower efficiency vs other technologies, burden increases with update frequency. Real-time bulk transmission unsuitable: Polling fundamentally unsuitable for real-time bulk event streams. Merely simulates server push, quickly reaching limits with increased users or high event frequency. |

**Key Considerations Summary:** For small classroom (1 to 12) **real-time drawing sharing**, **bidirectional communication**, **low latency**, and **efficient data transmission** are essential. Synthesizing the above comparison:

- **HTTP Polling**: Simple implementation but worst in latency and overhead. Achieving sub-1-second latency requires very frequent polling causing **bandwidth waste and server load**. Even Long Polling improvements hit limits with frequent drawing updates. **→ Unsuitable for this scenario.**
- **Server-Sent Events (SSE)**: One-way server→client streaming suitable for **teacher broadcasting drawings to students** with auto-reconnection convenience. Real-time performance adequate. However, **student→teacher drawing transmission** uneasy with SSE alone requiring separate AJAX, ultimately awkward for complete real-time bidirectional. Image binary transmission via SSE requires **text encoding** causing inefficiency. **→ Limitations in bidirectional drawing sharing.**
- **WebRTC**: Excels at **few-participant video/audio sharing** but practically difficult to establish P2P connections for all 13 (10 people mutual connections need 45 connections; 3+ groups P2P Mesh "practically impossible"). Avoiding this requires complex servers like SFU with very high implementation difficulty. Drawing sharing not continuous like video, small scenario where P2P direct connection unnecessary for performance. **→ WebRTC excessive choice; implementation complexity and infrastructure burden outweigh benefits.**
- **WebSocket**: Bidirectional communication via persistent connection ideal for **real-time broadcasting teacher drawings to all students**, with student drawings sent to teacher **via same channel if needed**. **Very low latency** supporting sub-1-second updates; many **real-time collaboration tools (whiteboards) adopt WebSocket**. Implementation difficulty far lower than WebRTC, binary data transmission straightforward. Mature browser and server support provides stability.

**In conclusion, WebSocket approach most recommended for this class scenario.** WebSocket fulfills all requirements of **real-time bidirectionality**, **low latency**, and **efficient broadcasting** while providing relatively smooth implementation and operation. SSE usable as auxiliary broadcast technology but bidirectional limitations exist; Polling fails modern real-time requirements; WebRTC unnecessarily complex. Thus **WebSocket is optimal technology for small-scale real-time drawing-sharing web apps**.
