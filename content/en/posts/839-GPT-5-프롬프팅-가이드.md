## Overview

GPT-5 represents a major breakthrough in agentic task performance, coding, raw intelligence, and steerability—our latest flagship model. It already works excellently across a wide range of domains with just "out-of-the-box" usage, but this guide shares practical prompting techniques learned through real-world application. We cover improving agentic task performance, instruction following, leveraging new API features, and optimizing frontend/software engineering coding—particularly the prompt tuning insights from Cursor, the AI code editor, working with GPT-5. While the best practices and recommended tools shared here have delivered significant results, prompting is never a one-size-fits-all solution.

To find the approach that best fits your specific problem, we recommend experimenting and iterating on this guide.

## Agentic workflow predictability

To optimize developer experience, GPT-5 strengthens tool calling, instruction following, and long-context understanding. If adopting GPT-5 in agent/tool-calling flows, we recommend upgrading to the **Responses API**. This API **preserves reasoning across tool calls**, enabling more efficient and intelligent outputs.

### Controlling agentic eagerness

Agent scaffolding spans a spectrum from delegating many decisions to the model, to strongly directing with programmatic branching logic. GPT-5 is trained to work well across this entire spectrum—from high-level decision-making in ambiguous situations to precisely defined tasks.

This section covers how to balance **model proactivity and responsiveness**.

#### When you want less eagerness

By default, GPT-5 tends to collect sufficient context to ensure correct answers.

To reduce "leaky" exploration in tool calls and minimize delays to final answers:

- **Lower reasoning\_effort.** This reduces search depth but improves efficiency and response latency. Many workflows achieve consistent results with medium or low settings.
- **Explicitly specify problem exploration criteria in the prompt.** Guide the model to avoid unnecessarily reviewing many ideas:

<context_gathering>

Goal: Get enough context fast. Parallelize discovery and stop as soon as you can act. Method: - Start broad, then fan out to focused subqueries. - In parallel, launch varied queries; read top hits per query. Deduplicate paths and cache; don't repeat queries. - Avoid over searching for context. If needed, run targeted searches in one parallel batch. Early stop criteria: - You can name exact content to change. - Top hits converge (~70%) on one area/path. Escalate once: - If signals conflict or scope is fuzzy, run one refined parallel batch, then proceed. Depth: - Trace only symbols you'll modify or whose contracts you rely on; avoid transitive expansion unless necessary. Loop: - Batch search → minimal plan → complete task. - Search again only if validation fails or new unknowns appear. Prefer acting over more searching.

</context_gathering>

- **Fix a tool-call budget** (adjustable by search depth). To enable concise context gathering, it's useful to include an **escape hatch** clause like **"it's okay to proceed even if not perfect"**.

<context_gathering>

- Search depth: very low - Bias strongly towards providing a correct answer as quickly as possible, even if it might not be fully correct. - Usually, this means an absolute maximum of 2 tool calls. - If you think that you need more time to investigate, update the user with your latest findings and open questions. You can proceed if the user confirms.

</context_gathering>

#### When you want more eagerness

If you want model autonomy, sustained tool calling, and minimal questioning, raise reasoning\_effort and use **prompts encouraging persistent execution**:

```
<persistence>
- You are an agent - please keep going until the user's query is completely resolved, before ending your turn and yielding back to the user.
- Only terminate your turn when you are sure that the problem is solved.
- Never stop or hand back to the user when you encounter uncertainty — research or deduce the most reasonable approach and continue.
- Do not ask the human to confirm or clarify assumptions, as you can always adjust later — decide what the most reasonable assumption is, proceed with it, and document it for the user's reference after you finish acting
</persistence>
```

It helps to clearly define **task termination conditions**, **safe/unsafe actions**, and **when to hand control back to the user**. (For example: in shopping toolsets, checkout steps allow only low uncertainty; search allows high uncertainty. In coding, deleting files requires high caution; grep has high freedom.)

### Tool preambles

During long-running tasks, **sharing tool-call intent, plans, and progress mid-way** improves user experience. GPT-5 naturally provides such updates in "tool preamble" form. Frequency, style, and content can be guided via prompts. Example:

```
<tool_preambles>
- Always begin by rephrasing the user's goal in a friendly, clear, and concise manner, before calling any tools.
- Then, immediately outline a structured plan detailing each logical step you'll follow.
- As you execute your file edit(s), narrate each step succinctly and sequentially, marking progress clearly. 
- Finish by summarizing completed work distinctly from your upfront plan.
</tool_preambles>
```

Here's an example of the preamble the model produces in response (summarized):

```
"output": [
  { "type": "reasoning", "summary": [{ "type": "summary_text", "text": "**Determining weather response**\n..." }] },
  { "type": "message", "content": [{ "type": "output_text", "text": "I'm going to check a live weather service..." }] },
  { "type": "function_call", "name": "get_weather", "arguments": "{\"location\":\"San Francisco, CA\",\"unit\":\"f\"}" }
]
```

### Reasoning effort

The reasoning\_effort parameter controls **reasoning intensity and tool-calling tendency** (default: medium). For complex multi-step tasks, higher reasoning is recommended. Performance is also maximized when **distinct subtasks are distributed across multiple turns**.

### Reusing reasoning context with Responses API

When using GPT-5, the **Responses API** is recommended. By passing previous reasoning traces to the next request via previous\_response\_id, you reduce token costs, improve performance, and decrease latency. For example, **Tau-Bench Retail** scores improved from 73.9% to 78.2%. There's no need to reconstruct plans on each request, improving efficiency (available to all Responses API users, including ZDR organizations).

## Maximizing coding performance, from planning to execution

GPT-5 delivers leading performance for bug fixes in large codebases, massive diffs, multi-file refactoring, and implementing large features. It's also strong at zero-to-one implementation for completely new apps (frontend/backend). Here we share **prompt optimization techniques** validated with real agentic coding customers.

### Frontend app development

GPT-5 combines **good aesthetic sense** with **solid implementation capability**.

While it handles most web frameworks/packages well, for new apps we recommend this stack:

- **Frameworks:** Next.js (TypeScript), React, HTML
- **Styling/UI:** Tailwind CSS, shadcn/ui, Radix Themes
- **Icons:** Material Symbols, Heroicons, Lucide
- **Animation:** Motion (Framer Motion)
- **Fonts:** Sans-serif families (Inter, Geist, Mona Sans, IBM Plex Sans, Manrope)

#### Zero-to-one app generation

GPT-5 excels at **building complete apps in one shot**.

Instructing the model to **internally create its own quality rubric and iterate** significantly improves output quality:

```
<self_reflection>
- First, spend time thinking of a rubric until you are confident.
- ... 5-7 categories ...
- Finally, use the rubric to internally think and iterate... If not hitting top marks, start again.
</self_reflection>
```

### Matching existing codebase standards

For incremental changes and refactoring, you must **conform to existing style and design conventions**. GPT-5 naturally reads **reference context** from package.json and similar files without explicit instruction, but

providing **explicit summaries of rules, directory structure, and conventions** improves results further:

```
<code_editing_rules>
<guiding_principles>
- Clarity and Reuse ...
- Consistency ...
- Simplicity ...
- Demo-Oriented ...
- Visual Quality ...
</guiding_principles>
<frontend_stack_defaults>
- Framework: Next.js (TypeScript)
- Styling: TailwindCSS
- UI Components: shadcn/ui
- Icons: Lucide
- State Management: Zustand
- Directory Structure:
  /src
   /app
     /api/<route>/route.ts
     /(pages)
   /components/
   /hooks/
   /lib/
   /stores/
   /types/
   /styles/
</frontend_stack_defaults>
<ui_ux_best_practices>
- Visual Hierarchy ...
- Color Usage ...
- Spacing and Layout ...
- State Handling ...
- Accessibility ...
</ui_ux_best_practices>
<code_editing_rules>
```

### Real-world collaborative coding: Cursor's GPT-5 prompt tuning

The AI code editor **Cursor** was an early alpha tester of GPT-5. Their system prompt balances **tool-calling reliability**, **autonomy in long-running tasks**, and **instruction adherence**.

- Initially, text output was **excessively verbose**, while tool-generated code was **too terse** (single-letter variable names), reducing readability.  
  → **Lower API verbosity** to keep text concise, but strongly prompt for "high verbosity specifically for code and code tools":
- Write code for clarity first... Use high verbosity for writing code and code tools.
- The model frequently **asked for user confirmation instead of acting**, interrupting flow.  
  → Provide **detailed product behavior context** (Undo/Reject, user preferences, etc.), not just available tools and context, to enable **longer autonomous task execution**:

...propose changes proactively for the user to approve/reject... almost never ask whether to proceed; attempt the plan proactively...

- Previous model guidance like "**thoroughly gather context**" created **excessive tool calls** (repeated unnecessary searches) with GPT-5.  
  → Relaxing the prompt improves the **balance between internal knowledge and tool use**. Additionally, **structured XML specs** like <instruction_spec> stabilize instruction adherence:

<context_understanding>

.. If you've performed an edit ... not confident, gather more information... Bias towards not asking the user for help if you can find the answer yourself.

</context_understanding>

## Optimizing intelligence and instruction-following

### Steering

GPT-5 is **the most steerable model**, allowing fine-grained control via prompts over **verbosity**, **tone**, and **tool-calling behavior**.

### Verbosity

The GPT-5 API includes a **verbosity** parameter that controls **final answer length** (separate from reasoning length). While it's an API parameter by default, you can override it for specific contexts using natural language in the prompt (e.g., global: low, coding tools: high).

### Instruction following

Like GPT-4.1, GPT-5 excels at **precise instruction following**. However, **contradictory or ambiguous instructions** can waste reasoning tokens as the model tries to reconcile them. For example, this medical scheduling prompt has conflicts:

- "**No booking without consent**" vs "**Auto-assign same-day slots without contact**"
- "**Check patient profile first**" vs "**For emergencies, prioritize 911 guidance over scheduling**"

To resolve this:

- Modify auto-assignment to "**after informing the patient**" (aligns with consent principle).
- For emergency cases, **explicitly permit skipping the lookup**.

In practice, prompts change frequently, so **regular audits for contradictions and ambiguities** are important. Try our **prompt optimization tools** as well.

## Minimal reasoning

GPT-5 introduces **minimal reasoning effort** for the first time. It's the optimal upgrade for **latency-sensitive users** and also suits **GPT-4.1 users**. However, **prompt dependency increases**, so we recommend:

- **Request brief reasoning summaries** at the start of final answers (bullets, etc.) → improves high-difficulty task performance.
- **Use tool-call preambles** to narrate progress → enhances agentic workflow performance.
- **Remove ambiguity from tool instructions** and **insert persistence reminders** → prevents early termination during long-running tasks.
- **Place plan-inducing prompts upfront**—reasoning tokens are limited, so externalized plans are important:
- Remember, you are an agent - please keep going until the user's query is completely resolved... You must plan extensively ... and reflect extensively ...

## Markdown formatting

By API default, GPT-5 does **not auto-apply markdown** (for compatibility). Adding this instruction enables **hierarchical markdown output**:

- Use markdown **only where semantically appropriate** (inline code, code fences, lists, tables).
- Wrap filenames, directories, functions, and class names in backticks; format formulas as ( ), [ ].

In long conversations, if markdown adherence weakens, re-injecting markdown instructions every **3–5 user messages** stabilizes it.

## Metaprompting

Several early users saw major wins by **having GPT-5 fix its own prompts**. To more consistently induce desired behavior, ask the model directly **what phrases to add or remove**:

Example template:

> When asked to optimize prompts, give answers from your own perspective ...  
> Here's a prompt: [PROMPT]  
> The desired behavior ... what are some minimal edits/additions ...

- Solve the task by modifying/running the repo inside the current container.

- Fix the **root cause** of the problem and **avoid unnecessary complexity**.

### Tau-Bench Retail minimal reasoning instructions (summary)

- **Start with user authentication** (email, or name + postal code).
- **Support only one user per conversation**.
- Before DB changes, **list task details** and **obtain explicit consent**.
- **No guessing**—use tools to query needed information.
- **One tool call at a time**.
- Respect constraints for each scenario: cancel/modify/return/exchange (order status, payment method, refund path, etc.).

### Terminal-Bench prompt (summary)

- Solve tasks by modifying/running code in the container.
- Follow the **Plan—Explore—Validate—Optimize** principle and check regularly during execution.
